# ondra-router

> O-055 · 通道公共层 · 档位〔研〕 · 服务键 `ondra-router`

一条消息来了，先问三件事：该不该叫醒她、同时来的好几路怎么排、这个通道到底能发什么。

---

## 一、职责

1. **唤醒判断**：一条入站消息该 `wake` / `reply` / `queue` / `ignore` / `deny`，并给出**原因码**。
2. **多会话排队**：某个会话正被她处理时，后来的消息按会话先进先出排队；占用结束一次性交出。
3. **能力查询**：某通道单条能发多长、支不支持图/语音/贴纸/文件、群里是不是必须点名。
4. **唤醒身份纪律（P0，手册 §5.4）**：主动叫醒她时，投递正文恒为 `...`，执念详情走说明段；**绝不替主人说话**。

## 二、明确不负责

| 不做 | 归谁 |
|---|---|
| 判「此刻该不该主动说」（静默时段 / 日额度 / 放弃率） | `ondra-proactive-gate`（O-042） |
| 真的把消息发出去、协议、鉴权、重连 | 各适配器（O-058 ~ O-067） |
| 平台频控、退避、抖动、错误码熔断 | 各适配器（手册 §5.3 六道闸在发送侧） |
| 分条、停顿、打字速度 | `ondra-rhythm`（O-038）；平台硬上限切分归 `ondra-channel-kit`（O-056） |
| 会话上下文、冻结前缀、历史提交 | `ondra-dialogue`（O-033） |
| 把说明段注册进提示词 | 组装方（O-023 / O-024 / O-036）——见下 |

### 三条刻意的「不做」，理由写在这里而不是藏在代码里

1. **不内置通道能力表。** 手册 §9.11 那张实测表（telegram 4000 / wechat-official 800 / qq-official 1200 …）是旧项目实读值，而 master-plan §9.12 明确要求「字段定义由各插件用 `Config` 声明」。内置一份就有两个数：用户改适配器配置、这里还是旧数，症状是「消息被平台截断」——查不出跟谁有关。**空表 + `undefined` 返回值**比一张会过期的表诚实。
2. **不注册唤醒说明段。** 段注册会动到会话前缀，而前缀是冻结的（手册 §8.5）。谁冻结前缀谁注册段；本插件只交「该段该写什么」。两个地方按不同 order 拼同一段，会让命中率在一个没人注意的路径上掉下去。
3. **不发消息、不注册工具。** 注册 `wake_me`，模型就能自己决定「现在该叫主人」——那等于让被叫的人自己按门铃。发消息则会让本插件变成第 10 个适配器，而且是唯一一个不知道自己跑在哪条协议上的适配器。

### 与 O-042 的边界（最容易混的一条）

两者都叫「该不该说话」，但：

| | 看什么 | 什么时候跑 |
|---|---|---|
| `ondra-proactive-gate` | 时间（静默时段、额度、冷却、放弃率） | 她想主动开口**之前** |
| `ondra-router` | 来信（谁发的、群里有没有叫她、她正忙不忙） | 一条消息**到达之后** |

两处都做「时机」就会互相打脸：proactive 说该说、router 说不该唤醒，而用户只会看到「她有时听不见我」。

## 三、服务键与方法

```
ondra-router        ← 连字符，不是 ondra:router
```

| 方法 | 说明 |
|---|---|
| `admit(input)` | 判定 + 占位（或排队）。**永不抛出。** 返回 `Admission` |
| `release(id)` | 结束占用，**一次性交出**该会话积压（交出即离开队列） |
| `pending(id)` | 只读某会话积压 |
| `queued()` | 全部积压，按全局入队顺序 |
| `forget(id)` | 忘掉一个会话（通道关闭时调），返回清掉的条数 |
| `registerChannel(spec)` | 登记能力；返回判别联合 `{ok:true,dispose}` / `{ok:false,reason}` |
| `capabilities(id)` | 读能力；未登记为 `undefined`（**不是「零能力」**） |
| `channelIds()` | 已登记通道 id |
| `wakeDelivery()` | `{ body:'...', section:{name,order,text,chars}, why }` |
| `stats()` | 见下 |
| `available` / `reason` | 前者只看配置开关；关掉时 `reason='disabled'` |

`stats()`：`available / channels / busy / queued / admitted / woken / replied / ignored / skipped / denied / queuedTotal / released / dropped / lastReason?`

> `dropped` = **没被处置**的条数（队列满被拒 + 通道关闭清空）。它不为 0 就说明有消息没走到她面前，值得看一眼。

### 一条必须记住的使用纪律

`admit()` 返回 `reserved: true` 时，**处理完必须 `release(conversationId)`**。
不 release 的症状是「这个会话永远正忙」——后续消息全部排队，队列满了开始 `queue-full`。
这是本插件唯一一处「漏一步就坏」的地方，所以做成显式字段而不是靠文档提醒。

`release()` 交出的条目**已经离开队列**，调用方按序处置，**不得再回 `admit()`**：
再判一次会让它们重新排队，形成「一释放就排回去」的死循环。

## 四、判定表

| 顺序 | 闸门 | 条件 | 动作 | 原因码 |
|---|---|---|---|---|
| 1 | 总开关 | `enable=false` | ignore | `disabled` |
| 2 | 防回声 | `self=true` | ignore | `self-echo` |
| 3 | 白名单 | `whitelisted=false`，或 `undefined` 且 `strictWhitelist` | deny | `not-whitelisted` |
| 4 | 空消息 | 无正文且无附件 | ignore | `empty` |
| 5 | 群聊主动 | `group` + `active` | ignore | `group-active-ignored` |
| 6 | 私聊 | `kind=private` | **wake** | `private-message` |
| 7 | 群点名 | `group` + `mention` | reply | `group-mentioned` |
| 8 | 群关键词 | `group` + `keyword` 且 `replyOnKeyword` | reply | `group-keyword` |
| 9 | 群其他 | `group` + `message`，或关键词关了 | ignore | `group-not-addressed` |

判定之后还有四道**状态闸**（在 `service.ts`，不在纯判定里）：

| 顺序 | 闸门 | 动作 | 原因码 |
|---|---|---|---|
| A | 同一条消息 1 秒内重复投递（按平台消息 id） | ignore | `duplicate` |
| B | 私聊按 `wakeProbability` 这次没叫 | ignore | `wake-skipped` |
| C | 目标会话正忙 → 入队 | queue | `busy-queued` |
| D | 队列满 → 不入队 | deny | `queue-full` |

### `wake` 与 `reply` 为什么要分开

「唤醒」= 把她从闲置里叫起来，可能要提到前台、可能要 resume 冷会话；
「回复」= 回一条，不抢前台。这个区分直接来自 P0 纪律的反面——
**主动叫醒只发生在私聊**（手册 §5.4 / §5.6），群里被 @ 只是回复。
压成一个布尔，适配器就只能靠猜「这次算不算把她叫起来了」。

### `ignore` 与 `deny` 为什么要分开

前者是「本来就轮不到她」，后者是「本该轮到她但被挡住了」。
合成一个，日志里就分不出「群里 200 条闲聊」和「三个人被白名单挡在外面」——
后者是配置错误，必须一眼看见。

## 五、配置

| 键（camelCase） | 段字段（kebab） | 默认 | 依据 |
|---|---|---|---|
| `enable` | `enable` | `true` | — |
| `replyOnKeyword` | `reply-on-keyword` | `true` | 手册 §6.1「@ 机器人或关键词」 |
| `wakeProbability` | `wake-probability` | `1` | 手册 §14.3 通道唤醒三口径合一（见下） |
| `strictWhitelist` | `strict-whitelist` | `false` | 白名单数据归适配器；默认拒会让未实现的通道全哑 |
| `maxQueue` | `max-queue` | `8` | 自定（见「待裁决」） |
| `maxConversations` | `max-conversations` | `64` | 自定 |
| `dedupeMs` | `dedupe-ms` | `1000` | 手册 §5.4「1 秒去重」 |
| `verbose` | `verbose` | `true` | — |

**没有「群聊主动」这个开关。** 手册 §5.7 把「群聊不主动」列为**节制红线**
（背景是批量小号与 AI 互刷引发的社区反感，甚至有人写了屏蔽插件）。
红线做成开关，等于把「一装就可能被举报封号」变成群里一个可以点的小勾。

## 六、多方案说明（master-plan §14.3「通道唤醒」）

手册把通道唤醒的三种做法并列，本插件按 §12.1「能融会贯通 → 融」处理成**一个参数 + 一条分支**，而不是三套代码：

| 口径 | 在本插件里是什么 |
|---|---|
| 全量响应 | `wakeProbability = 1`（**默认**，最稳：不漏消息） |
| 本地唤醒（`wakeProbability`） | `0 < p < 1`，私聊有时不回 |
| 关键词唤醒 | 群聊那条分支（`mention` / `keyword`），与概率无关 |

**默认取 `1`** 而不是「本地唤醒」：§14.2 要求「默认最稳，不是最快也不是最省」。漏掉一条私聊消息不可恢复，而「每次都回」只是少了一点拟人。

概率**只作用于私聊的 `wake`**：群里被点名还掷骰子，就是失礼。

## 七、唤醒身份纪律（P0）

`wakeDelivery()` 交出两样东西：

- `body: '...'`——手册原话「投递的正文只有三个点」：「既然每一条渲染路径都把正文留着，就让正文本身没有内容。」
- `section.text`——「你收到的那条只写着 `...` 的消息，是你的潜意识在叫你——不是主人在说话，也不是主人在问你。」

三个点本身不携带信息，所以模型必须有地方得知那是什么；而正文一旦有内容，
就等于她借了主人的嘴——`SOUL.md` 明令禁止。

段名用 `ondra-router:wake`。**段名不是服务键/工具名/配置键**，不受 §8.4 正则约束
（那三类必须是纯连字符）；提示词段名沿用上游 `namespace:section` 惯例（上游有 `plan:policy`）。

## 九、隔离五问（master-plan §16.4）

1. **关掉我，谁受影响？** 只有通道层：适配器拿不到判定，会退回「收到就回」。
   记忆、人格、对话链、语音一律不受影响（本插件不发消息、不进提示词）。
2. **我的状态存在哪？** 只在内存：占用集合、排队、去重表、能力表。
   **不落盘**——重启清零。代价见「已知限制 1」。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.router`；
   面板读 `stats()` 的 `denied` / `dropped` / `lastReason`。
4. **我依赖谁？缺席时怎么降级？** `ondra-config-schema`（退回本地校验）、
   `ondra-clock`（退回 `Date.now()`）、`ondra-identity`（退回固定命名空间）。三个都是 `undefined` 判断后安静退化，**没有任何一个是硬依赖**。
5. **我和同域的谁共享可变状态？** 没有。能力表由适配器**交出**声明，本插件不读适配器的内部；
   排队与占用按会话 id 分组，通道之间互不可见（§16.2 隔离第 4 条）。

## 十、已知限制

1. **队列不落盘。** 进程重启后积压丢失。缓解方式写在使用契约里：**在 `release()` 之前不要推进平台游标**
   （`getUpdates` 的 offset、`sync_msg` 的 cursor），重启后适配器重投即可。真正落盘要 O-006 的表，
   而那会让本插件从「公共层」变成「有存储依赖的域插件」——不在本轮范围。
2. **去重只在有平台消息 id 时生效。** 没有标识就无法区分「重复投递」与「用户真的连发两遍」。
3. **占用集合不设上限。** 泄漏由「必须 release」这条纪律兜住，症状是「该会话永远正忙」，一眼可见。
   刻意不用「超上限就淘汰最早的」——淘汰会让两个回合并发跑同一个会话，历史交错。
4. **能力表出厂为空。** 适配器不登记就查不到上限；`capabilities()` 返回 `undefined` 而不是猜一个数。
5. **`order: 100` 是自定值。** 手册没给提示词段的排序刻度（只给「疤痕 -1e4」这个极端值）。
6. **不判人格一致性、不判内容合规。** 前者归 `ondra-filter-chain` / `ondra-persona-assemble`，
   后者归 `ondra-privacy`。
7. **未实装运行。** 本轮只做静态自检，未 `install` / 未 `build` / 未 `tsc` / 未启动 app。

## 十一、待裁决

1. `maxQueue = 8`（单会话）与 `maxConversations = 64` 是否合适——手册没给这两个数。
2. `wakeProbability` 默认 `1`（全量）还是 `0.9`（略拟人）——手册 §14.3 把「本地唤醒」写成默认，
   但 §14.2 又要求「默认最稳」。本轮按 §14.2 取 `1`。
3. 队列满时是否该让适配器回一句「我有点跟不上了」——目前只给原因码，话术归适配器。
4. `strictWhitelist` 默认 `false` 是否太松——取决于各适配器多快能交出白名单。
5. 唤醒说明段的 `order = 100` 是否合适（相对位置由组装方最终决定）。
