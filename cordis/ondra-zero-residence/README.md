# ondra-zero-residence

> O-143 · 〔研〕自研 · 手册 §8.6「上下文经济」 · P1 · 批次 B6（运行时治理）
> 服务键 **`ondra-zero-residence`**（连字符，符合 §8.4）

## 一、职责

用**确定性指针**替换常驻正文，被遮的每个字都能**逐字**恢复。

手册 §8.6 只有一句：「零常驻上下文（O-143）：确定性指针替换常驻内容，被遮字节可从 session log
逐字恢复（可逆可审计）；压缩前状态先写 SQLite」。这一句里有四个动作，也就是手册给的四个名字：

| 手册 | 本包 | 它回答什么 |
|---|---|---|
| `zr_compact` | `compact()` | 这段能不能换成指针？换完省多少？换完还能取回来吗？ |
| `zr_recall` | `recall()` | 这个指针原来是什么？**还能不能一字不差取回来？** |
| `zr_ledger` | `ledger()` | 账上有什么？谁在什么时候被遮了多少字？ |
| `zr_fast` | `fast()` | 不写盘也不建账，纯算一遍要省多少（预算预览） |

与「压缩成摘要」的差别不是省钱，是**性质**：摘要是损失（细节没了，只留大意），
零常驻是位移（原文还在，只是不在上下文里了）。所以它可以审计——账上写着遮了多少字，
取回来还能对指纹。

## 二、明确不负责

| 不做 | 归谁 |
|---|---|
| **不做替换动作**（不接管消息序列、不改历史数组） | O-033 `ondra-dialogue` 的历史裁剪与应用外壳；本包只交「替换文本 + 可恢复凭据」 |
| 不拼提示词、不做注入装箱、不管易变段追加 | O-036 `ondra-prompt-inject` / O-142 `ondra-inject-dedupe` |
| 不判断「哪一段该被压缩」 | 调用方。本包看不到消息序列，猜出来的边界会在同一条用户消息里触发两次 |
| 不调模型、不做摘要 | 本包的全部收益来自「不调模型」；要摘要请找 O-019 `ondra-memory-dream` |
| 不读 session log | 会话日志的格式与路径归应用外壳（`desktop/`）；本包给 `attachSource()` 插口，谁有谁接 |
| **不做界面：不画账本视图、不做日志视图、不做提示词预览面板、不做 Toast、不定义设计令牌与主题** | **应用外壳（`desktop/`）。L8 界面 14 个插件（O-085~O-096、O-124、O-125）已于 2026-11-03 整批下线，永久不再新建 `ondra-ui-*`** |
| 不落「谁的上下文超了多少」这类读数 | `ondra-startup-check` 与外壳的体检面板 |

### 三条刻意的「不做」

1. **不在 `agent/pre-step` 里偷偷改消息。** 那条路能改，但改错了没有任何人查得出来：
   原文归属权在对话编排手里，第三方插件拿不到「这一段原来是什么」的完整视图。
   宁可少做一步，也要把这一步留在有资格做的地方。
2. **不装定时器。** 零常驻的触发条件是「用户回合边界」，那是一个事件，不是一个周期。
   装定时器只会在两个回合之间压一次中间态，然后被下一轮的原文又盖回去。
3. **不淘汰旧记录。** 账本满了拒收并计数。淘汰最老的 = 删掉一条别人手里还握着指针的证据，
   之后 `recall` 返回 `not-found`，而调用方以为「压缩是安全的」。

## 三、三条写死的判定

### 1. 指针是内容的函数，不是时间的函数

```ts
const id = 'zr-' + fnv1a64(sessionId + '\0' + text).slice(0, 12)
```

同一段正文、同一个会话，压两次得到**同一个字符串**。这一条不是洁癖：
§8.5 的第 1 条是「会话内冻结前缀」，零常驻会在用户回合边界改写一次前缀——这是它付的代价。
但如果每次改写的指针都不同，就不是「改一次」而是「每轮都改」，缓存直接归零
（手册实测命中 99.3–99.6%，¥879.97 → ¥19.96，就是这么丢的）。

**会话参与哈希**：一条记录只能指向一个会话的证据。跨会话共用会让恢复指错人。
代价是同一段正文在两个会话里得到两个指针——这是对的，它们指向两份不同的东西。

### 2. 压缩只发生在用户回合边界

`compact()` 要调用方显式传 `atUserTurnBoundary: true`。本包不自己猜：看不到消息序列时，
任何「距上次压缩超过 N 秒」的猜测都会在同一条用户消息里触发第二次。

### 3. 没有存储就不发指针

顺序写死：**建表 → 事务写库 → 入账 → 才交出指针**。任何一步失败都在交出之前返回拒绝。
写不进去还交指针，就是把一条通向空处的链接塞进上下文：三十分钟后模型问「刚才那个文件叫什么」，
账上是有的、库里是空的，而且**没有任何报错**。

## 四、配置

段键 `zero-residence`（O-005 配置真源），字段键全连字符。

| 字段 | 默认 | 说明 |
|---|---|---|
| `mode` | `observe` | `off` / `observe`（只算不干，**默认**）/ `compact`（真写盘真交指针） |
| `max-span-chars` | 4000 | 单条记录上限；超了在段落 / 空行 / 句号 / 空格处切开，切成多条 |
| `min-savings-chars` | 64 | 省下的字不够这个数就不压（一条指针约 20 字） |
| `max-records` | 512 | 账本上限；满了拒收，**不淘汰** |
| `require-durable` | true | 手册要求「先写 SQLite」；关掉后没库也能压，但重启即丢 |
| `verify-on-recall` | true | 恢复时校验长度与指纹 |
| `verbose` | false | 每次压缩一行日志 |

**只有 `require-durable` 有手册依据**（它是「压缩前状态先写 SQLite」的顺序约束，落在布尔位上）。
其余六个是工程取值，见第十二节「待裁决」。

### 为什么默认是 `observe`

省错了只是多花字，压错了是**内容消失**。所以第一版只算不干：先把 `fast()` 与 `ledger()` 的数
看一遍，再翻 `compact`。与 O-138 的 `observe` 同一套迁移纪律。

## 五、服务面

```ts
const zr = ctx.get('ondra-zero-residence')   // 装载顺序无关；缺席即 undefined

zr?.available / zr?.reason / zr?.mode
zr?.fast(text, 'resident', sessionId)     // 纯预览：段数、指针、省多少
zr?.compact({                             // 真压
  sessionId,
  text,
  kind: 'resident',                       // persona / worldbook / boundary 一律拒收
  atUserTurnBoundary: true,               // 不传就拒：中途重写前缀会废掉这一轮缓存
})
// → { ok, pointers, ids, charsIn, charsOut, savedChars, records, durable, advisory, note }

zr?.recall('[zr-3f2a9c1b2d4e/1420]')      // → { ok, text, verified, source, reason? }
zr?.ledger(sessionId)                     // → { records, chars, capacity, recent[≤20] }
zr?.expand('…[zr-.../1420]…', sessionId)  // 整段展开；换不回来的原样保留并计数
zr?.attachSource((id, sessionId) => …)    // 挂外部恢复源，返回卸载函数
zr?.stats() / zr?.dispose()
```

**恢复来源按顺序试三条**：内存账本 → 存储后端 → 外部源。三条都没有就是 `not-found`，
**不猜、不近似、不返回空串**。

**`verified` 与 `ok` 是两个字段。** 取到了但长度或指纹对不上时 `ok=true, verified=false,
reason='mismatch'`：正文照给（可能调用方只要个大概），可信标记照实说。
把已经拿到手的内容扔掉、只回一个「对不上」，等于让它重新去问一遍。

## 六、为什么不发工具，只发服务

手册写的是四个工具名（`zr_compact/recall/ledger/fast`）。本包把它落成**四个同名服务方法**，
没有 `tools.register`：

- 上游的工具注册面要求完整的 schema 与执行契约，而**手册没给这四个工具的参数**。
  凭空定一套参数，就是让模型按一份编出来的说明书调用——它会在某个参数上一直错，
  而错误表现是「零常驻不好用」；
- 服务方法的调用方是**代码**（O-033 或外壳），不是模型。零常驻的决策不该由模型发一轮请求来触发：
  那一轮请求本身就带着要被遮掉的原文，纯亏。

若将来手册补齐参数，接法是加一层薄壳把服务方法包成工具，不动本包的实现。

## 七、隔离五问（§16.4）

1. **关掉我，谁受影响？** 调用方的 `compact()` 拿到 `undefined`（服务缺席），走原来的有损裁剪路径。
   **不影响对话、不影响存储、不影响任何已入账数据的可读性**——库里那些记录还在，只是没人再发新指针。
2. **我的状态存在哪？** 元数据在内存索引（随进程生死），正文在 `zr_record` 表（唯一持久化落点）。
   没有存储后端时正文留在内存，`stats().durable = false` 明说。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.zero-residence`；
   服务上 `available` / `reason` / `stats().storeErrors` / `stats().byReason` 四个读数。
   `storeErrors > 0` 是唯一「交不出指针」的硬故障信号。
4. **我依赖谁？缺席时怎么降级？** `ondra-store-sqlite`（**软**：不在就 `available=false`、
   `reason=no-store`，不发指针）、`ondra-config-schema`（软，注册失败退回插件实例配置）、
   `ondra-identity`（软，只取日志命名空间）、`ondra-clock`（软，取不到用 `Date.now()`）。
5. **我和同域的谁共享了可变状态？** 没有。账本独占；`zr_record` 表也独占（表名带 `zr_` 前缀）。

## 八、多方案分支说明（§12）

| 能力 | 方案 | 处理 |
|---|---|---|
| 替换常驻内容的方式 | A 确定性指针 + 逐字恢复（本包） / B LLM 摘要 / C 直接丢弃 | **A**。B 有损且多一次模型调用（正是本包要省的那笔钱）；C 会让她「忘了刚才在做什么」——手册对这件事的原话是「压缩后忘了在编辑哪些文件」 |
| 指针 id 的构成 | A 内容+会话指纹（本包） / B 自增序号 / C 时间戳 | **A**。B 与 C 都会让同一段内容每次压缩得到新指针，前缀缓存归零 |
| 记录存放 | A 索引在内存、正文在库（本包） / B 全文都进内存 / C 全文都进库 | **A**。B 让「零常驻」插件自己常驻 2MB；C 每次列账都要读全文 |
| 写入时机 | A 先写库后交指针（本包） / B 先交指针后补写 | **A**。B 在写失败时留下一批指向空处的指针，且没有报错 |
| 无法恢复时 | A 原样保留指针并计数（本包） / B 猜一段填进去 | **A**。B 用编造顶替证据，且长得和正常内容一样，事后查不出 |

**档位判定：〔研〕自研。** 生态里的「上下文压缩」清一色是**摘要类**（会丢细节、要调模型）；
「指针 + 逐字恢复」只有 agent-body 一家在做，且它的实现绑定自己的会话日志格式，
本仓拿不到那份格式（会话日志归应用外壳）。所以机制照抄、实现自写、恢复源留插口。

## 十、已知限制

1. **本包不做替换。** 这是边界不是缺陷（见第二节）。要让它真正生效，必须由 O-033 或外壳
   把 `pointers` 拼回上下文。**没人调它就等于没装。**
2. **跨进程恢复依赖存储后端。** `recall()` 的三条来源里，只有存储后端跨进程；
   外部源要应用外壳挂 `attachSource()`。两样都没有时，重启后旧指针全部 `not-found`。
3. **`session log` 逐字恢复这一条，本包只做到「等价」而不是「同源」。** 手册说的是从 session log 读；
   本包把原文自己存了一份到 SQLite（因为拿不到 session log 的读取接口）。
   两者内容相同、证据强度略有差别：**本包这份副本被改过时，指纹会报出来；session log 被改过时，本包不知道**。
4. **`max-span-chars` 切段是「尽量在语义边界切」而不是「保证在语义边界切」。** 一整段没有
   分隔符的长串会硬切，切点保证在完整码位之后（不会切坏 emoji），但不保证不在句子中间。
5. **同一段正文在同一个会话里被压两次会复用同一条记录**（`records` 少于段数，`note` 会写「复用 N 段」）。
   这是刻意的：重复入账会让账本条数虚高，且第二条永远不会被引用。
6. **指纹是 48 位。** 撞号概率极低但非零；真撞了会换 `-2` 后缀，`planFor()` 最多试 64 个候选，
   全满则拒收（`id-exhausted`），不猜。
7. **`observe` 模式的回报是「计划省下」而不是「实际省下」。** `stats().savedChars` 两种模式都累加，
   `stats().pointers` 只计真交出去的——两个数要一起看才不会被自己骗。
8. **不加密。** §17-3 的裁决：本地加密对同机同用户几乎无防护。库文件权限由 O-006 的 0600 负责，
   本包不额外加一层。**这意味着 `zr_record` 里的正文与 session log 同等敏感。**

## 十一、待裁决

1. **六个工程取值没有手册出处**：`max-span-chars 4000` / `min-savings-chars 64` / `max-records 512` /
   `verify-on-recall true` / `mode observe` / `verbose false`。只有 `require-durable` 有依据。
2. **四个动作要不要真做成工具？** 本包按「服务方法」实现，理由见第六节。若主人要模型能主动喊
   「把这段收起来」，需要先定四个工具的参数——手册没给。
3. **压缩粒度由谁定？** 本包按「调用方给一段、本包切段」。另一种做法是「给整段历史、本包自己决定切哪」，
   但那样本包就要理解消息结构，也就跨过了第二节那条边界。
4. **账本要不要按会话自动清理？** 现在只按条数封顶，不按时间。旧会话的记录会一直占着容量，
   直到触顶拒收。若要清理，需要一条「记录可以删」的裁决——而删证据这件事本包不敢自己决定。
