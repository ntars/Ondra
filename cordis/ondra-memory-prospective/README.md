# ondra-memory-prospective

> O-016 ｜ L2 记忆域 ｜ 档位 **〔研〕自研** ｜ 批次 B2（记忆纵深 P0 第五项）

说好的事与要做的事。一句话职责：**「答应过的」必须能兑现、能结算、能解释；「要做的事」只是提醒，不许污染记忆。**

---

## 职责

1. **抽取**：`detect(text)` —— 纯正则从一句话里认出承诺 / 待办（不调模型）。
2. **承诺**：`remember(text)` —— 锁原文、写记忆（`category=promise`，8000 小时基线）、落清单。
3. **待办**：`addTodo(text)` —— 最多 3 条、3 天没提起自动过期、说「做好了」就删相关那条。
4. **到期提醒**：`dueForReminder()` —— 提前 24 小时、宽限 24 小时、**不按条数砍**。
5. **结算**：`settle(id, 'kept' | 'broken')` —— 只出关系增量建议，**不写情绪**。
6. **反向权重**：`urgencyOf()` / `listOpen()` —— 越近越重，供注入块 ①【说好的事】取材。
7. **清理**：`expire()` —— 过宽限 3 天转 `expired`；待办过期与已完成行一并清掉。

## 明确不负责

- **不写情绪**。手册 §3.4 的违约金 `{trust−0.05, warmth−0.03, tension+0.04}` 与履约奖
  `{trust+0.02, warmth+0.02}` 由本插件**算出来交出去**，关系域归 **O-026**。
  `SettleOutcome.applied` 的类型是字面量 `false`——想让它变成 `true` 必须先改类型。
- **不调模型**。手册 §2.8 原话「纯正则不调模型」。故**不消费** `ondra-llm-gateway`：
  承诺本来就有明确时间词可认，为它每条消息过一次 API 不划算。
- **不算寿命、不衰减**。承诺的强度与半衰期由 **O-010** 算（`category=promise` 走它自己的
  8000 小时基线）。本插件一次 `Math.pow` 都不写。
- **不做注入**。「哪些承诺该进提示词、装不下怎么折叠」归 **O-036**；本插件只给
  `listOpen()` 这个取材端，且**不按条数砍**。
- **不做承诺闸门**（拦截动作）。手册 §3.6 的「承诺闸门」带三道解锁与 20 分钟 TTL，
  是**行为约束**不是记忆，落点是 O-129 或单列 `ondra-commitment-gate`。
  本插件只回答「有没有这条承诺、结算了没有」。
- **不装定时器**（`autoExpire` 默认 `false`）。清理是写操作，时机由 O-033 回合边界
  或 O-019 夜巡显式给——交给一个「不知道第几个装载」的定时器，会让
  「为什么这条承诺没了」永远查不出来。

## 服务键

| 项 | 值 |
|---|---|
| 服务键 | **`ondra-memory-prospective`**（连字符，符合 `^[a-z][a-z0-9_-]{1,63}$`） |
| 提供 | `ctx.provide('ondra-memory-prospective', service)` |
| 消费 | `ondra-memory-core`（**承诺的必要条件**，缺席则 `promiseWritable=false`）；`ondra-store-sqlite` / `ondra-store-memory`（**硬依赖**：都没有则 `available=false`）；`ondra-clock`（软，只借 `startOfDay()` 做日历算术）；`ondra-config-schema`（软）；`ondra-identity`（软，日志命名空间） |

**为什么 `available` 与 `promiseWritable` 是两个布尔**：内核缺席时待办照常工作
（它本来就不进记忆链）。把两件事压成一个 `available`，会让「待办也不能用了」
这种假象传出去，而排查方向会完全错。

## 两张表为什么必须分开

```
memory_promise（承诺）              working_todo（待办）
├─ 进记忆：写 memory_fact           ├─ 不进记忆：只在本表
├─ category = promise（8000h）      ├─ 不参与衰减、不进星云图
├─ kept / broken 结算               ├─ 最多 3 条、3 天没提起自动过期
└─ 锁原文、提前 24h、宽限 24h        └─ 说「做好了 / 发过去了」就删
```

手册 §2.8 原话「待办与承诺分表」，语料 §17 给了理由。合并的代价不是「字段冗余」，
是**两个统计同时失真**：

- 待办按 `promise` 的 8000 小时活着 → 长期霸占注入名额，且永远不「过期」；
- 承诺按 `todoIdleDays` 三天过期 → 静默丢掉一件答应了的事，而且**没有任何报错**。

### 表结构

`memory_promise`（四个索引）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | `p-<factId>`。确定性主键，重放同一句话直接 `upsert`，不会产生两条 |
| `fact_id` | TEXT | 指回 `memory_fact.id`。**不建外键**（见下） |
| `text` | TEXT | **锁住的原文**。不存摘要 |
| `due_at` | INTEGER | 到期时刻。`0` = 无期限（「下次」） |
| `remind_at` | INTEGER | `due_at − 24h` |
| `grace_until` | INTEGER | `due_at + 24h` |
| `state` | TEXT | `open` / `kept` / `broken` / `expired` |
| `created_at` | INTEGER | 写入时刻 |
| `settled_at` | INTEGER | 结算时刻。`0` = 未结算 |
| `reminded_at` | INTEGER | 最近一次被提醒。`0` = 没提醒过（**防重复提醒**） |
| `time_word` | TEXT | 命中的时间词（解释用） |

`working_todo`（两个索引）：`id` / `text` / `created_at` / `last_mentioned_at` /
`expires_at` / `done`。

**不建外键**：`fact_id` 指向 `memory_fact.id`，但记忆会被 `forget()` 真删。
外键级联会把「她忘了一件事」变成「她忘了自己答应过」——后者该由本插件显式处理
（`expire()` 里发现事实不在时转 `expired` 并记 issue），不该由数据库替我们决定。

## 反向权重：一条与记忆强度方向相反的时间轴

这是本插件最容易被抄错的地方：

```
记忆强度   0.5^(Δt/S)          越久越淡  ── 单调递减
承诺紧迫   随剩余时间倒数上升   越近越急  ── 单调递增
```

一条 `promise` 类记忆有 8000 小时基线，按强度算法它写下来之后大半年都「很新鲜」。
但承诺的价值不在「新鲜」，在「快到了」。若沿用强度排序，注入块 ① 会在到期前
2 小时把一条三天前的琐事排在它前面。

```
urgency(d) = 1                                       d ≤ 0（到期日与宽限期内）
           = floor + (1−floor) × (1 − d/horizon)     0 < d < horizon
           = floor                                    d ≥ horizon
```

`d` 是剩余天数，`horizon` 默认 7 天、`floor` 默认 0.2。三个性质都是刻意的：
`d = horizon` 时正好落到 `floor`（曲线连续、无跳变）；`d ≤ 0` 恒为 1（**不是继续上升**
——过期后的「更急」由提醒表达，不让一个 0–1 的数溢出）；非 `open` 状态恒为 0
（结算完的承诺不该继续占注入位）。

## 多方案分支说明（master-plan §14）

本插件**不设运行期分支**，落在 §14 的第一档「能融会贯通 → 融」：

| 表面上的多方案 | 怎么融的 | 没有做成分支的理由 |
|---|---|---|
| 「承诺」与「待办」 | **不融**：两张表、两套生命周期，共用同一个抽取器与同一张时间词表 | 这不是同一功能的两套实现，而是**两个不同对象**。融成一张表就是本 README 上一节说的「两个统计同时失真」 |
| 「今晚 / 周末 / 下周 / 一会儿 / 下次」 | 一张 `TIME_WORDS` 表 + 一个 `resolveDue()` 的 `mode` 分支 | 六种时间词只差「怎么算那一天」，没有行为差异。按词写六份代码是最典型的「为一个字段抄六遍」 |
| 「SQLite」与「内存后端」 | 只走表级 CRUD（`raw` 面刻意不用），两个后端同一份代码 | 一旦用上自定义 SQL，内存后端立刻失效，而它存在的理由正是「SQLite 打不开」 |

分区判定依据：§14.1「能融就融，能兼容就做兼容层，都不能才做分支」。
本插件唯一的「不融」是承诺与待办——那是**数据模型**层面的分界，不是实现层面的选择。

## 隔离五问（master-plan §16.4）

1. **关掉我，谁受影响？** 注入块 ①【说好的事】空着；O-042 主动消息少一类话由（承诺到期）；O-043 的话由排序里「承诺 > 待办」两档消失。记忆、召回、衰减全不受影响。
2. **我的状态存在哪？** 两张表（走端口，落 `~/.ondra` 下的库）。计数器只在内存。
3. **我崩了，界面怎么知道？** 日志命名空间 `ondra.memory-prospective`；`stats()` 给出 `available` / `reason` / `promiseWritable` / 各状态条数 / `issues`。
4. **我依赖谁？缺席时怎么降级？** 存储端口缺席 → `no-store`，全部接口降级为空；内核缺席 → 只记待办、不记承诺（`promiseWritable=false`）；时钟缺席 → 本地日历推算；O-005 缺席 → 只用插件实例配置。
5. **我和同域的谁共享可变状态？** 没有。两张表是本插件独占的；`memory_fact` 只经 O-010 的公开方法写（`addFact`），不碰任何列。

## 已知限制

1. **「反向权重」的曲线是本插件定的，手册没给。** 手册只写「反向权重」四个字。
   本插件取分段线性（7 天窗口、底 0.2），两个参数都可配。**待裁决**：真实产品里
   「多久开始催」应该是几天？裁决后只改 `urgencyHorizonDays` 的默认值，代码不动。
2. **待办没有存成 `working.json`，而是存表 `working_todo`。** 手册 §2.8 说
   「存 `working.json`」，那是旧项目单文件实现的形状。本插件用表承载同一语义
   （字段同构、可原样导出成那个 JSON），理由是不新开文件通道、复用端口的事务与迁移。
   若要那个文件，由 O-002 的路径服务写一个导出器即可，不需要改本插件。
3. **「下周」是宽口径。** 手册没定义「下周」是哪一天，本插件取「下周日结束前」。
   严格口径（下周一）会让「下周二」这类说法落到下周一之前，反而更错。
4. **时钟缺席时到期日按本地日历推算。** 若产品时区（O-003 配置）与系统时区不同，
   「明天 23:59:59」会差几小时。生产环境应当装载 O-003。
5. **`completeByText()` 是启发式，两道闸 + 一次归一化。**
   先剥掉待办开头的标记词（`记得` / `待会` / `提醒我` 不是内容），
   再用**双向包含度取较大者**算相似度（门槛 0.5），找不到就**什么都不做**。
   - 剥标记词：不剥的话分母被两个无关的字撑大，`牛奶买好了` 只有 0.25，删不掉；
   - 双向取大：用户说完成的那句天然比待办长，单向按「被待办覆盖多少」算会系统性偏低。
   12 组用例（`买牛奶做好了` / `牛奶买好了` / `周报交了` / `还没做好` / `做好了，不错` /
   `我心情好了` …）全部符合预期。
   代价：只报「做好了」而不提内容的句子**不会删任何待办**——它可能指任何一件事，
   猜一条去删是最不该做的事。与 O-012 的判重**不是同一把尺子**（那边阈值 0.4，
   问的是「要不要合并」），口径不同不可互搬（裁决⑥）。
6. **上限是拒绝，不是淘汰。** 承诺 20 条、待办 3 条，满了抛错并记 issue。
   删一条承诺等于替用户决定哪件事不重要——这与核心池上限 32「满了直接拒绝」
   是同一条纪律。代价是用户必须自己清，所以 `stats()` 必须把「满没满」报出来。
7. **`expire()` 会把已完成的待办行删掉。** 它们留着只为了 `completeTodo()` 能返回一次
   结果，没有二次用途。若将来界面要「已完成列表」，需要另加一列而不是留着这些行。
8. **承诺的 `subject` 固定为 `'user'`。** 承诺的受益方是用户，故按「关于用户的事」记。
   若将来要区分「她自己的承诺」（例如「我明天要去学习」），需要新增一个 `self` 分支。
