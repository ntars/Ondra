# ondra-narrative-log

> O-135 · 主动与节制 · 档位〔薄〕（台账原标〔研〕，判定见 §七）· 服务键 `ondra-narrative-log`

「她刚才为什么那么冷淡？」——这个插件不回答她，它回答**你**。它把每一轮回复背后的判定收成一条记录：选了哪一档、被什么推的、哪道闸改过、引用了哪几条依据。只追加，只读，不进提示词。

---

## 一、职责

1. **收**：`record()` 收下上游交来的结构化判定（`chosen / factors / gates / refs / excerpt / note`），洗净、脱敏、截断、按 `|weight|` 排序。
2. **存**：内存环（默认 200 条，供面板翻页）+ 一天一个 JSONL 文件（`user/narrative/YYYY-MM-DD.jsonl`，0600，只追加）。
3. **说**：`explain(turnId)` / `why(entry)` 把一条记录说成一句中文——**给面板与审计读，不进提示词**。
4. **清**：`prune()` 按保留期删掉自家命名的旧文件。**只在被调用时执行**，没有定时器。

## 二、明确不负责

- **不进提示词**。没有 `prompt()` / `inject()` 出口。这段文字天然带计数（「拦了 2 处」），拼进上下文会直接撞上禁止报数铁律；也会让「解释自己」变成一种表演。
- **不推断理由**。本包不知道 `emotion.tension` 的语义，也不知道 `filter.narration` 是什么闸。因子与判定由上游交，交了什么记什么，没交就写「上游没交」。
- **不改不删单条**。没有 update、没有 delete。要「忘掉某一条」只能整份清（`prune()` 按天），这是刻意的：审计日志一旦可改，就不再是审计。
- **不存正文全文**。只留她说出口那一小段（默认 60 字，可关）。用户原话、记忆正文、提示词一律不存。
- **不做模型调用、不做统计推断**。「最近是不是更容易冷淡」这类问题归记忆审计（O-027）与语感统计（O-137）。
- **不装定时器、不订阅事件**。零常驻：写入由上游调用触发，清理由面板触发。
- **不画界面**。日志视图、筛选、时间轴、折叠展开、复制、Toast、成长面板、提示词预览**全部归应用外壳（`desktop/`）**，本包只交出 `recent()` / `explain()` / `read()` 的数据，不渲染任何东西。

## 三、服务键与方法

```
ondra-narrative-log        ← 连字符，不是 ondra:narrative-log
```

| 方法 | 说明 |
|---|---|
| `record(input)` | 记一条。**永不抛错**，返回 `{ok, id, stored, reason?, message?}` |
| `explain(turnId)` | 按回合 id 解释。先查内存环，再查当天文件；找不到返回 `undefined` |
| `recent(query?)` | 最近若干条，**新的在前**；可按 `conversationId` / `producer` / `since` 过滤 |
| `read(dayKey)` | 读某一天的文件（`YYYY-MM-DD`）；格式不对返回空数组 |
| `why(entry)` | 把一条记录说成人话（纯函数） |
| `prune()` | 删掉早于保留期的自家文件，返回删了几个 |
| `stats()` | `available / stored / entries / capacity / dir / counters` |
| `dispose()` | 卸载（幂等） |

`record()` 的入参全是可缺的：能补的补（`at` 补现在、`turnId` 补「时刻+序号」），**一个可用字段都没有就拒收**——只有时间与 id 的记录对审计毫无用处，收下只会让面板出现一堆空条目。

`reason` 五值闭集：`ok / disabled / invalid / no-store / write-failed`。

## 四、配置

| 键（camelCase） | 段字段（kebab） | 默认 | 说明 |
|---|---|---|---|
| `enable` | `enable` | `true` | 总开关。关掉后服务照常注册，`record()` 返回 `disabled` |
| `maxEntries` | `max-entries` | `200` | 内存环条数 |
| `maxExcerptChars` | `max-excerpt-chars` | `60` | 她说出口那段留多少字 |
| `maxFactors` | `max-factors` | `12` | 一条最多几个因子 |
| `maxGates` | `max-gates` | `8` | 一条最多几道闸 |
| `maxRefs` | `max-refs` | `12` | 一条最多几个引用 id |
| `retentionDays` | `retention-days` | `14` | 保留天数，**只在 `prune()` 时生效** |
| `maskSensitive` | `mask-sensitive` | `true` | 脱敏手机号 / 邮箱 / 证件号 / 卡号 |

`Config` 是 camelCase，而配置键正则不认大写，所以段声明 / 用户层归一化 / 结果回填**三处全部由 `KEY_PAIRS` 派生**（`src/settings.ts`），不手写第二份。

## 五、关键裁决（每条都对应一个真实失败）

1. **没有提示词出口。** 「让她知道自己为什么这么回」听起来很美，但这份记录里全是计数与档位名，进了上下文就是报数；而且她会开始**为了日志好看**而选档。想看原因的是人，不是她。
2. **写盘失败不回滚内存。** 磁盘满时这一条仍在环里，面板还能看到「刚刚为什么」。回滚的代价是连看都看不到，而不回滚的代价只是重启后没了。
3. **`explain()` 先环后文件。** 只查环，重启后第一次追问答「找不到」；只查文件，跨天的那一条要读两个文件。先环（快、跨天）再当天文件（补位）是两种失败的最小交集。
4. **坏行跳过，不整体失败。** 断电会留下半截行，手改也会写坏一行。逐行 `JSON.parse`、坏的跳过，其余照读——一整天的记录不该因为一行而全废。
5. **保留期不做自动清理。** 自动删的风险不对称：删对了没人知道，删错了（时区、日期格式、面板误触）就永久丢掉唯一线索。所以它是**动作的参数**，不是后台行为。
6. **`prune()` 只删 `YYYY-MM-DD.jsonl`。** 这个目录在共享的 `user/` 下，一个通配式实现迟早删到别人的东西。不递归、不通配、日期键还要过正则。
7. **id 用「时刻+序号」而不是随机数。** 审计要按时间对齐别的日志（通道、模型网关）；随机 id 好看但对不上账。
8. **先证件号再卡号再手机号。** 顺序反了，18 位身份证会被卡号规则先咬掉一段，剩下的位数对不上，掩码就变成了「看起来脱敏了、其实还留着」。
9. **只有时间与 id 的记录拒收。** 收下会让面板出现一堆空条目，而空条目比没有更糟：它让人以为「这一轮没有判定」。
10. **`truncated` 不只标正文截断。** 因子/闸门/引用被上限砍掉也算——否则「为什么少了三个因子」会变成一个查不出来的谜。

## 六、多方案说明

**存储**有两种做法：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A 一天一个 JSONL（默认，已实现）** | 追加写、逐行解析、坏行跳过 | 零迁移、可 `grep`、坏一行不影响别的行；代价是没有索引，按字段查要全量扫 |
| B SQLite 表 | 建表、加索引、按 `turnId` 查 | 查询快、可聚合；代价是要迁移、要跟 O-008 的库抢生命周期 |

选 A 的理由：这份日志的用途是**低频事后追查**（「昨天 14 点那次为什么冷淡」），一天几百行、一年几万行，全量扫也就几十毫秒；而建表要付出的迁移与生命周期成本是持续的。B 保留为「面板要做聚合统计时」的升级路径，不是现在。

**清理**有两种做法：自动（启动时按保留期删）vs 显式（`prune()`）。选显式，理由见 §五-5。

## 八、隔离五问

1. **关掉我，谁受影响？** 只有「事后追查」这一件事消失。上游的 `record()` 会拿到 `disabled`（或 `undefined` 服务时的判空分支），对话与记忆完全不受影响——本包不在任何决策路径上。
2. **我的状态存在哪？** 内存环（默认 200 条）；磁盘 `user/narrative/YYYY-MM-DD.jsonl`（0600，只追加）。没有表、没有数据库、没有索引文件。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.narrative-log`（有 O-001 时走 `identity.loggerName('narrative-log')`）。`stats().counters` 给出 `rejected / writeFailed / pruned`，`stored` 直接说明「现在到底有没有在写盘」。
4. **我依赖谁？缺席时我怎么降级？** 四个软依赖：O-002（路径，缺了只进内存环，`record()` 返回 `no-store`）、O-003（时间，缺了用本机时区分片）、O-005（配置四层，缺了用实例配置）、O-001（日志命名空间，缺了用固定名）。四个都不阻断装载。
5. **我和同域的谁共享了可变状态？** 没有。内存环与文件都是本包私有；与 O-134 `ondra-climb` 同批但零共享——它记「群里谁说了什么」，本包记「她为什么这么回」，两者不读对方任何字段，也不互相 import。

## 九、已知限制

1. **只记交来的东西。** 上游不交 `factors`，这里就只有一句「她这么回」。本包不会替你推断，也不去别处捞——捞来的东西无法归因。
2. **`explain()` 只补查当天文件。** 跨天追查请用 `read(dayKey)` 指定日期；这是刻意的（不为了一个低频动作去扫整目录）。
3. **内存环重启即空。** 历史在文件里，`recent()` 只看环；重启后面板要先 `read(今天)` 再显示。
4. **不做 `fsync`。** 断电可能丢最后几行。审计日志的价值在「事后」，不在「崩溃前最后一毫秒」；为它付每次写入一次 fsync 的代价不值。
5. **多进程同时写同一文件可能交错。** 单行追加通常原子，但文件系统不保证；本产品是单进程宿主，这条只在「用户开了两个实例」时成立。
6. **脱敏只覆盖四类。** 地址、姓名、公司名、聊天里的第三人信息不在覆盖范围；`storeExcerpt` 关掉是更彻底的选择。
7. **没有按字段索引。** `read(dayKey)` 全量解析（一天几百行，毫秒级）；要聚合请走 SQLite 分支（§六 B）。
8. **不提供导出。** 要导出直接拷 `user/narrative/*.jsonl`——它本来就是纯文本。
9. **`truncated` 只说「有东西被砍」，不说砍了什么。** 具体哪一项超限要靠 `factors.length` 与配置上限对账。

## 十、待裁决（本包自定值，手册无出处）

台账只写「只读追加，供 UI 与 audit 查」，master-plan §9 没有决策日志这一节。以下值全部是本包自定的工程值，依据写在 `FIELD_SPECS` 的 `doc` 里：

1. `maxExcerptChars = 60`（追查要的是「那一句什么调子」，不是整段回复）。
2. `retentionDays = 14`（追查通常发生在「昨天 / 上周」；更久的问题该看记忆审计 O-027）。
3. `maxEntries = 200`（一屏 20 条，翻十页够用；约 60KB）。
4. `maskSensitive` 默认开、`storeExcerpt` 默认开：前者去掉与判定无关的风险，后者保留追查需要的调子。
5. **要不要记用户原话**：现在不记。若主人认为「她为什么这么回」必须对照「主人当时说了什么」，需要新增一个 `promptExcerpt` 字段——那会把聊天记录写进日志，本包不主动做。
6. **`explain()` 的文本要不要给模型看**：现在不给，且没有任何出口。若将来要做「她自己复盘」，应当走一条**单独的、脱敏后的**通路，而不是把这份日志直接塞进上下文。
