# ondra-channel-kit

> O-056 · 通道公共层 · 档位〔研〕 · 服务键 `ondra-channel-kit`

十个通道里真正一样的那三件事：问一句、切一条、记十二句。

---

## 一、职责

1. **问人格（`callPersona`）**：走 O-033 对话链跑一轮，返回可发出去的正文；给了平台上限就连切条一起给。
2. **切条（`chunk`）**：按平台单条上限切，优先句末、其次句内标点、最后硬切；**拼回等于原文**。
3. **对端历史（`history`）**：每通道一份、仅内存、上限 12 条的缓冲区工厂；实例归适配器。

## 二、明确不负责

| 不做 | 归谁 |
|---|---|
| 唤醒判断、多会话排队、通道能力表 | `ondra-router`（O-055） |
| 拟人分条（40 字 / 最多 4 条 / 停顿 / 打字速度） | `ondra-rhythm`（O-038） |
| 人格四段拼装、世界书、注入预算 | `ondra-persona-assemble` / `worldbook` / `prompt-inject`（O-023 / O-024 / O-036） |
| 冻结前缀、历史提交、压缩 | `ondra-dialogue`（O-033） |
| 模型选路、超时重试、跨来源降级 | `ondra-llm-gateway`（O-035） |
| 九步输出过滤、收尾六道闸 | `ondra-filter-chain`（O-037） |
| 频控、退避、抖动、错误码熔断 | 各适配器（手册 §5.3 六道闸在发送侧） |
| 消息落盘、跨通道共享历史 | **谁都不做**（master-plan §16.2-4） |

### 四条刻意的「不做」，理由写在这里而不是藏在代码里

1. **不自己拼提示词。** 老做法是「人格 `buildPrompt()` + 网关流式」，看起来少一跳，实际把对话链的三件事重做一遍：冻结前缀、历史提交、收尾判定。真做了就有两条对话通路，差异只会在很晚才暴露——比如通道里那几句进了历史、主界面那几句没进，于是「她在两个地方记得的事不一样」。
2. **不按通道 id 缓存历史。** 缓存会让「关掉通道」不释放内存，也会让两个适配器不小心共用一份——那正是串味的来源。做成工厂，每次新的。
3. **不给切条设默认上限。** 手册 §9.11 的九个上限是各通道属性，真源在适配器 `Config`。这里放个「默认 4000」，就是把微信的 800 撑成 4000，症状是消息被平台**静默截断**——查不出跟谁有关。
4. **不限流、不重试。** 各平台语义不同（discord 停重连码 4004、dingtalk 要先回 empty 再异步）。公共段一旦限流，就会出现「Telegram 被 QQ 的阈值卡住」这种没法解释的现象。

## 三、服务键与方法

```
ondra-channel-kit        ← 连字符，不是 ondra:channel-kit
```

| 方法 | 说明 |
|---|---|
| `callPersona(input)` | 问一轮。**永不抛出**，失败折成 `CallResult.failure` |
| `chunk(text, max)` | 纯函数切条。`max<=0` 按 1 处理 |
| `history(options?)` | 造一份对端历史（`capacity` 默认取配置，上限 12） |
| `peerHistoryLimit` | 恒为 12，供面板展示 |
| `available` / `reason` | 前者只看配置开关；关掉时 `reason='disabled'` |

### `callPersona` 的入参与结果

```
CallInput  { conversationId, text, maxChars?, timeoutMs?, signal? }
CallResult { ok, text, chars, pieces, failure?, partial, reason? }
```

- `conversationId` 会经 `toConversationId()` 归一化（小写、非法字符换 `-`）。
  不归一化的话，`tg:123456` 这类 id 塞进对话链的结果**不是报错**，是那条消息没有会话可用——表现为「用户发了消息，她永远不回」。
  被洗过的 id 会加 `ch-` 前缀并附 8 位指纹，防止 `tg:1` 与 `tg.1` 塌成同一个会话。
- `text` 在 `ok=false` 时**也可能非空**（超时前已经吐了半句）。刻意保留给日志与对拍，**但默认不要发半句**。
- `pieces` 只在给了 `maxChars` 时才切；没给就是整段一片。

### 失败原因（六值闭集）

| 码 | 中文 | 该干什么 |
|---|---|---|
| `disabled` | 公共段已关闭 | 看配置 |
| `no-dialogue` | 没有对话链 | 去装 O-033；装好自动恢复，不用重启插件 |
| `timeout` | 等太久已中止 | 看网关块间隔；**已 `abort()`，本轮不写历史** |
| `aborted` | 被取消 | 用户按了停止，正常 |
| `empty` | 她这轮没说出话 | 看过滤链是不是清空了全文 |
| `error` | 对话链报错 | 看日志里的那句 detail |

## 四、切条的三条不变量

1. **`pieces.join('') === text`**——不吞空格、不补句号。补一个句号就等于替她说话。
2. **每片 ≤ `max`，且不为空串**。
3. **不切开代理对**——硬切时末位若是高位代理（emoji 前半个）就退一格。不退的后果是半截 emoji，某些平台渲染成 `?`，某些直接拒收。

优先级：先句末（`。！？!?…\n`）→ 再句内（`，、；：,;: 空格`）→ 最后硬切。
句末之后会顺带带走收尾符号（`」』】》"` 等），否则下一片会以「」开头。

> **顺序必须是「先拟人、后平台」**：先用 O-038 分成 4 条 40 字，每条再看要不要按平台上限继续切。反过来做，40 字会被 4000 字的上限「合并」回一整段。

## 七、多方案说明（master-plan §14）

本插件涉及两条已登记的多方案项，处理方式都是「融」而不是「分支」：

| 项 | 口径 A | 口径 B | 怎么处理 |
|---|---|---|---|
| 切条粒度 | 拟人分条（O-038，40 字 × 4 条） | 平台硬上限（本插件） | **两级串联**：先拟人、后平台。一个接口两段职责，各自单一归属 |
| 对话入口 | 直连 `llm-gateway`（少一跳） | 走 `dialogue`（多一跳但前缀/历史统一） | **只走 dialogue**。少的那一跳换来的是「第二条对话通路」，代价远高于收益 |

## 八、隔离五问（master-plan §16.4）

1. **关掉我，谁受影响？** 只有通道层：适配器拿不到 `callPersona`，只能自己拼（那是它们不该做的事）。
   对话链、人格、记忆、界面一律不受影响——本插件不注册工具、不进提示词、不碰会话。
2. **我的状态存在哪？** **哪里都不存。** 三件能力里两件是纯函数，`history()` 每次造新实例，
   实例归适配器。`stats()` 挂在实例上，不在插件上。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.channel-kit`；
   `callPersona` 的失败码与 `FAILURE_ZH` 是给面板读的。
4. **我依赖谁？缺席时怎么降级？** `ondra-dialogue`（缺席给 `no-dialogue`，**每次现取、能自愈**）、
   `ondra-config-schema`（退回本地校验）、`ondra-identity`（退回固定命名空间）。三个都判空后安静退化。
5. **我和同域的谁共享可变状态？** 没有。历史实例由调用方持有，插件本体**零字段**
   （只有两个只读配置引用），这是刻意的（见「不负责」第 2 条）。

## 九、已知限制

1. **不读人格。** 与手册 §9.11 写的「运行期只取人格服务并调 `buildPrompt?.()`」**刻意偏离**：
   人格四段已在对话链的冻结前缀里（§8.5），再读一次会有两条人格通路，且第二遍会挤动已冻结的前缀。
2. **超时只中止这一轮，不换模型、不重试。** 换来源会让「偶发限流」变成「悄悄换了个笨模型」，
   而用户只会觉得「她今天变笨了」（与 O-035 同一条裁决）。
3. **对端历史无去重。** 同一条消息重复 `push` 会占两格。去重归 O-055 的 1 秒去重
   （按平台消息 id），公共段不猜。
4. **`at` 不可信时记 0**，不编一个「现在」。历史里时间只用于展示。
5. **切条不处理代码块。** 围栏代码块被切开后，平台侧渲染会断。
   真要保住代码块，得让调用方先把代码块摘出来单独发——那是适配器的事。
6. **未实装运行。** 本轮只做静态自检，未 `install` / 未 `build` / 未 `tsc` / 未启动 app。

## 十、待裁决

1. `callTimeoutMs = 60s` 是否合适——手册没给单轮超时，只给了 `maxTokens 800`。
2. 对端历史要不要按角色各留 6 条而不是共享 12 条（当前按手册的「12 条总数」）。
3. `PEER_TEXT_MAX = 4000` 是否需要按通道上限再压一次（当前是固定值）。
4. 切条时要不要保住围栏代码块（当前不保，见已知限制 5）。
5. `toConversationId` 会把大小写抹平（`ABC-123` 与 `abc-123` 归同一个会话）。
   平台 id 是否可能只差大小写、需要区分，得各适配器确认。
