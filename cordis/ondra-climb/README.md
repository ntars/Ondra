# ondra-climb

> O-134 · 主动与节制 · 档位〔薄〕（台账原标〔研〕，判定见 §七）· 服务键 `ondra-climb`

群里有四十条没看，她不该装作没发生，也不该把四十条一口气念完。这个插件只做一件事：把积压压成一份**能一口气读完**的清单，并且只在私聊交出去。

---

## 一、职责

1. **收积压**：通道适配器把群消息交进来，本包洗净（去链接、并空白、去零宽）、判重（`messageId` 优先，否则「群号+时刻+正文」指纹）、按时刻插进队列。
2. **排清单**：按组轮转取件（防刷屏群饿死别的群），输出按时间升序，带**群名+群号、时刻、说话人、正文**，受三重上限约束（群数 / 行数 / 总字数）。
3. **交出去**：只在私聊 `plan()` 出东西；群里恒空。最终发不发由 O-042 门控决定。
4. **推进游标**：`commit(planId)` 才推进。没确认就不推进——发失败不丢消息。

## 二、明确不负责

- **不调模型做概括**。摘要 = 确定性截取。真概括归对话链（O-033 手里的模型）或记忆提炼（O-011）。
- **不在群里发言**。`plan({chatKind:'group'})` 恒返回空计划。群里没有清单，就没有「刷屏」这条路。
- **不判「此刻能不能发」**。静默时段（23:00–08:00）、日额度、冷却、内容红线全在 O-042。本包只答「这一轮可以提」。
- **不存群聊原文**。只落游标（`user/climb-state.json`，0600）。重启靠通道重推补齐。
- **不做图片、语音、引用、回复链**。只吃纯文本；其余模态归 O-126/O-127/O-128。
- **不装定时器、不订阅事件**。零常驻，所有时刻从入参或 `now()` 取。
- **不画界面**。未读角标、清单视图、折叠展开、Toast、日志视图、成长面板、提示词预览**全部归应用外壳（`desktop/`）**，本包只经服务键交出 `pending()` 与 `plan().text`，不渲染任何东西。
- **不做「已读回执」**。平台侧已读状态归适配器；本包只记自己的游标。

## 三、服务键与方法

```
ondra-climb        ← 连字符，不是 ondra:climb
```

| 方法 | 说明 |
|---|---|
| `ingest(items)` | 收一批积压。返回 `{accepted, duplicate, rejected, pending}`，**永不抛错** |
| `plan(input?)` | 排清单。`input.chatKind` 缺省 `private`；`group` 恒空（`reason: 'group-only'`） |
| `commit(planId)` | 确认已交付，推进游标并清掉已交付的条目。计划不存在返回 `false` |
| `pending()` | 各群积压视图（计数与时刻，**不出正文**），按最旧一条升序 |
| `stats()` | `available / stored / pending / groups / lastPlanAt / counters` |
| `reset(groupId?)` | 清积压与游标（调试与「我不想补了」用） |
| `dispose()` | 卸载（幂等） |

`DigestPlan` 的关键字段：`lines`（清单行）、`groups`、`chars`、`folded`（本轮没装下的条数，**不进正文**）、`expired`、`wake`、`reason`、`text`（可直接注入的块，首行是固定 marker `[爬楼]`）。

`reason` 七值闭集：`ok / disabled / group-only / no-backlog / all-seen / too-long / empty-input`。

## 五、关键裁决（每条都对应一个真实失败）

1. **`plan()` 不改游标，必须 `commit()`。** 排完清单不等于清单交出去了：发送可能被通道断开、被门控拦、被用户切走。自动推进的后果是那 12 条**永远没人再提**，而且不报错——主人只会觉得「她好像漏看了」。两步分离的代价只是调用方多调一次。
2. **群里恒空，不是「群里也返回但不许发」。** 靠调用方记得「群里别贴」等于没有约束；让群里根本拿不到东西，那条路才走不通。
3. **摘要里不写「还有 N 条没看」。** 手册 §12.1 的禁止报数铁律管的是她说话时不许报内部计数。折叠数只进 `plan.folded`（日志与面板），不进 `plan.text`。
4. **折叠不等于丢弃。** 本轮没装下的条留在队首，下一轮继续；只有 `maxAgeHours` 过期与 `maxPendingPerGroup` 溢出是真丢，两者都计数。
5. **积压正文不落盘。** 群里的话是别人说的，落盘就是一份没人同意的语料。丢一次补读（通道会重推）好过留一份不该留的原文。
6. **判重优先 `messageId`，没有才用「群号+时刻+正文」。** 这条口径的代价是「编辑过的消息算新消息」；反过来的代价是「两条不同消息算同一条」，后者会让一句话凭空消失。
7. **取件按组轮转、输出按时间。** 只按时间取，一个刷屏群会把其他群全饿死；只按轮转输出，读起来是「14:05 / 9:12 / 14:03」，不像话。
8. **时刻走 O-003，不走 `new Date()`。** 跨时区部署时，「14:05」必须是主人眼里的 14:05，否则清单会整体错几小时，而这种错不会报错。
9. **单条都装不下时给 `too-long`，不给空清单。** 空清单加 `ok` 会让调用方以为「没有积压」，而实际上有一堆——只是配置的 `maxDigestChars` 比一条还小。

## 六、多方案说明

「摘要」有两种做法：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A 确定性截取（默认，已实现）** | 去链接、并空白、句界截断 | 零延迟、零费用、结果可复现、不会编造；代价是「不是真概括」 |
| B 模型概括 | 把一批消息交给 O-035 生成两三句 | 更像人话；代价是每轮一次模型调用，失败时她会说出一段像自己编的群聊内容 |

选 A 的理由：爬楼是**每轮都可能发生**的路径，把模型调用放进来等于给每一轮加一次延迟与一次失败面；而失败的表现（半截的、像编的摘要）比不补读更糟。B 保留为调用方的可选增强：调用方可以自己用 O-035 概括 `plan().lines`，再自行拼进提示词——本包不拦。

**存储**只有一种：内存队列 + 游标文件。没有做「积压正文落盘」的分支，理由是 §五-5，不是没来得及。

## 八、隔离五问

1. **关掉我，谁受影响？** 只有「补读」这一件事消失。通道照常收发，对话照常进行，主动照常（O-042 不依赖本包）。`plan()` 不再被调用即可，没有副作用残留。
2. **我的状态存在哪？** 内存里是待补读队列、已读指纹、游标；磁盘上只有 `user/climb-state.json`（0600，只有游标与指纹，**没有群聊正文**）。没有表、没有数据库。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.climb`（有 O-001 时走 `identity.loggerName('climb')`）。`stats().counters` 给出 `rejected / expired / overflowed / writeFailed` 四个能指向具体故障的计数。
4. **我依赖谁？缺席时我怎么降级？** 四个软依赖：O-002（路径，缺了游标只在内存）、O-003（时间，缺了用本机时区）、O-005（配置四层，缺了用实例配置）、O-001（日志命名空间，缺了用固定名）。四个都不阻断装载。
5. **我和同域的谁共享了可变状态？** 没有。队列与游标都是本包私有；与 O-135 `ondra-narrative-log` 同批但零共享——它记的是「她为什么这么回」，本包记的是「群里谁说了什么」，两者不读对方的任何字段。

## 九、已知限制

1. **摘要不是概括**。它把一句话截到 60 字，不会合并「三个人在聊同一件事」。要真概括，请调用方用 O-035 处理 `plan().lines`。
2. **积压正文不落盘**，所以重启后要靠通道重推。拉取式通道（如某些公众号/客服通道）没有重放能力时，重启期间的积压会永久丢失。
3. **`maxAgeHours` 过期是真丢**。这是唯一会主动放弃消息的开关，默认 72 小时；主人若希望「一条都不许丢」，把它调到 720（30 天）并接受清单可能很长。
4. **单群上限 200 条会挤掉最旧的**。一个群积压 500 条时，前 300 条不会出现在清单里（有 `overflowed` 计数与 warn 日志，但消息本身回不来）。
5. **只吃纯文本**。图片、语音、引用、回复链、表情包一律按「没有正文」拒收。
6. **私聊积压在开关关闭时按 `rejected` 计**。不是坏了，是本包不接这一类；面板看到 `rejected` 增长时先看 `include-private-backlog`。
7. **群号可能很长**（QQ 群号 6–12 位、部分平台是长 id）。`showGroupId` 关掉后清单只剩群名，同名群会分不清。
8. **不做跨轮记忆**。上一轮提过哪个群、主人当时什么反应，本包不记；重复提及由对话链自己避免。
9. **`pending()` 最多列 64 个群**（面板上限），超出的群仍在内存里正常补读，只是不在视图里。
10. **没有 per-group 开关**。要「这个群不补」，只能调用方在 `ingest()` 前自己过滤。

## 十、待裁决（本包自定值，手册无出处）

台账只写「带上限」，master-plan §9 没有爬楼这一节。以下九个值全部是本包自定的工程值，挑值依据写在 `FIELD_SPECS` 的 `doc` 里：

1. `maxItemsPerDigest = 12`、`maxDigestChars = 600`（「一口气读完」的量级，与 O-036 注入预算同档）。
2. `maxGroups = 6`、`maxCharsPerItem = 60`（一行约 30 字，60 字能带一句解释）。
3. `maxAgeHours = 72`（三天前的群聊补给她也没用）。
4. `maxPendingPerGroup = 200`（200 × 60 字 ≈ 12KB）。
5. `showGroupId = true`（主人说「那个群」时只有群号能对上账）。
6. **摘要要不要交给模型**：现在确定性截取；若主人要「像人话的概括」，改由 O-035 生成，本包只提供 `lines`。
7. **`includePrivateBacklog` 默认关**：私聊消息本来走正常回合，补读清单对它没有意义；若主人希望「离线期间的私聊也补一句」，打开即可。
