**五处最容易出错的地方**（先记住，能省一轮返工）：

1. `trafficLightPosition.y` 填 **16** 不是 22。22 是红绿灯中心，不是顶边。
2. **本文件 §4.1 的 14 个 `--static-*` 令牌名里有 11 个在 `tokens.css` 里不存在**（`paper-*` / `ink-*` / `teal-*` / `sand-*` / `line` / `danger`）。它们是设计层命名，不是现成变量。只有 `--static-primary-500` 与 `--static-red-600` 是真的。逐个对应关系见 §11.2；**在组件里写一个不存在的 `var()` 不会报错，只会静默失效**。
3. 场景层 13 项绑定的键**已逐一核对过真实存在**（§5.13），写的是 `段 id.字段 kebab`。KEY_PAIRS 查表，不能靠字符串替换推。
4. **组件与打断形态的尺寸只在 §5 定义一次**（Toast 见 §5.10，Sheet/Dialog 见 §5.12）。§7.3 只补打扰维度，不重复数值——早期版本两处各写一份，出现了 Sheet 宽 480 对 420、圆角 20 对 16 的矛盾。
5. 插件总数 **134** = `members` 数组条目数，不等于"有 README 的插件数"（132）。`ondra-memory-intake` 与 `ondra-theater` 有代码、在 `members` 里、但没有 README。

## 0. 文档定位

本文件是界面实现的**唯一依据**。任何视觉、尺寸、动效、文案的争议，以本文件为准；本文件未覆盖的内容，按 Apple HIG（macOS 分支）处理。

本文件回答五个问题：

1. 界面长什么样，每个尺寸是多少。
2. macOS 与 Windows 如何做到同宗同源。
3. 134 个插件如何按 L0–L9 分类，以及界面以什么形式通用地承载它们。
4. 同一套界面如何落到九端（桌面三端 / 平板 / 手机三端 / Web·CLI / 内核）。
5. 每一项改动落在哪个文件的哪一行。

本文件**不**包含：业务逻辑、插件内部实现、模型协议、数据格式。这些属于各插件的 README 与 `docs/` 下的其他文档。

### 0.1 三条不可协商的约束

1. **820 × 580 是电脑三端的设计基准，不是下限，且只约束电脑三端**。macOS / Windows / Linux 的默认窗口就是最小窗口，用户第一次打开看到的就是最紧凑的形态。所有布局必须在此尺寸下完整可用；窗口放大只增加留白与列宽，不新增控件、不改变信息层级。**移动端与 Web·CLI 不受此约束**：移动端按屏幕全屏渲染，尺寸由设备决定（§3.6、§10.1）。
2. **同源平台界面相同、操作相同**。桌面三端（macOS / Windows / Linux）的差异只允许出现在第 2.2 节列出的两处。除此之外，任何"Windows 上这样、macOS 上那样"的实现都属于缺陷。移动三端（iPad / iOS / Android / 鸿蒙）因屏幕与输入方式不同而降级形态，但**同一控件在不同端的行为语义必须一致**——不能出现"桌面上右键、手机上没替代"。
3. **首页与会话态是两个形态，不是两个页面**。首页保持极简；进入会话后才展开双脊与检查器。不允许在首页显示会话列表、状态读数或设置入口的展开形态。

## 1. 设计原则

### 1.1 Apple HIG 的七条落地映射

| HIG 原则 | 在本项目中的具体含义 | 可验证的判据 |
| --- | --- | --- |
| Clarity | 信息优先于装饰。全界面三个色相、三种圆角、一种线宽 | 无渐变、无投影、无发光、无玻璃拟态 |
| Deference | 界面让位于内容。双脊合计 104px，主列占 87% | 正文区宽度 ≥ 716px @ 820 窗口 |
| Depth | 用层级表达深度，不用阴影。抽屉靠"浮现 + 单线描边" | 全界面只有一种阴影（`--shadow-lv3`），仅用于浮层菜单 |
| Direct Manipulation | 状态可直接拖动、参数可即时预演 | 滑杆拖动时预演句同步改写，无"保存"按钮 |
| Feedback | 任何操作 100ms 内必有可见反馈 | 按钮进入 pending 态、脊线转灰、回声生效 |
| Consistency | 两端一致；同类控件行为一致 | 同一控件在设置、检查器、引导中行为完全相同 |
| Accessibility | 颜色永不单独承载信息；键盘可完成全部操作 | 所有读数配文字标签；Tab 可遍历全部控件 |

### 1.2 本项目追加的三条原则

1. **记忆可见，才可被信任**。任何由记忆驱动的回复，必须能追溯到具体条目，且该条目可修改、可删除。
2. **主动开口必须可解释**。她主动说话时，界面必须给出一行判据；用户必须能在 3 秒内撤回这次打扰。
3. **不做假装**。不播放已生成完毕的逐字动画，不伪造"在线"状态，不伪造正在输入。真实的不响应优于虚假的响应。

### 1.3 冲突时的裁决顺序

设计里一定会遇到两条原则互相打架。这时不靠感觉，按固定顺序裁决，序号小的赢：

| 序 | 原则 | 为什么排这个位置 |
| --- | --- | --- |
| 1 | **不丢用户数据** | 任何美感、一致性、性能都不能成为丢数据的理由 |
| 2 | **可撤回** | 已经发生的误操作必须能退，退不回的必须二次确认 |
| 3 | **可达性** | 读屏、键盘、对比度是底线，不能"后续优化" |
| 4 | **同源一致** | 桌面三端必须一样，例外只许两处（§2.2） |
| 5 | **性能与流畅** | 掉帧的动画不如没有动画 |
| 6 | **简洁** | 能删就删，但不能为了简洁牺牲 3 与 4 |
| 7 | **视觉精致** | 最后一层。前六条都满足了才谈好看 |

**用三条真实冲突验证这张表**：

| 冲突 | 按表裁决 | 结果 |
| --- | --- | --- |
| 水位用颜色表达心情（简洁）vs 色弱用户读不出（可达性） | 3 > 6 | 保留颜色，但检查器必须给文字标签 |
| 自绘标题栏更统一（一致）vs Linux 平铺 WM 拖不动（可用） | 3 > 4 | Linux 允许切换系统标题栏（§10.5） |
| 落字动画更好看（精致）vs 长回复时卡顿（性能） | 5 > 7 | 积压超阈值时合并落字（§8.4） |

### 1.4 一句话自检

写完任何一个界面，用这四问过一遍。四问有一问答不上，就是没做完：

1. **它坏了会怎样？** 断网、宿主崩、插件报错，这个界面还能用吗？（→ §12.13）
2. **不用鼠标能做完吗？** 只用键盘、只用读屏，能完成同一件事吗？（→ §9）
3. **它会打扰人吗？** 这个提示是用户要的，还是我想告诉他的？（→ §7）
4. **它有依据吗？** 每个数字（宽度、时长、圆角）在本文件里能找到出处吗？（找不到就是臆造）

## 2. 平台同源

本章定义**桌面三端（macOS / Windows / Linux）**的同源契约。Linux 在界面与操作上与 macOS、Windows 完全一致，只有 §10.5 登记的六项环境补偿；移动端的形态降级见第 10 章，语义仍受本章约束。

### 2.1 同源契约（桌面三端必须完全一致）

| 维度 | 契约 |
| --- | --- |
| 窗口内容尺寸 | 820 × 580 |
| 标题栏高度 | 44px |
| 标题位置 | 主列水平居中，垂直居中于 44px |
| 左侧脊 | 48px，图标从 y=64 起 |
| 右侧脊 | 56px |
| 主列 | 716px（= 820 − 48 − 56） |
| 正文字号 | 14px / 行高 1.75 |
| 圆角 | 容器 16px，控件 8px，薄片 4px |
| 线宽 | 0.5px，单色 `#E4DFD3` |
| 快捷键 | 全部一致，修饰键按平台替换（mac `Cmd` ↔ win `Ctrl`） |
| 动效时长 | 全部一致 |
| 设置层级 | 全部一致 |
| 滚动条 | 自绘 overlay，宽 8px，不占布局 |
| 焦点环 | 2px `--static-teal-600`，圆角，offset 2px |
| 关闭语义 | 关闭窗口 = 隐藏到托盘，不退出应用 |
| 右键菜单 | 自绘，禁用系统菜单 |

### 2.2 允许不同的两处（仅此两处）

**Windows 端同样遵循 Apple HIG，不采用 Windows 设计语言（Fluent）的控件形态、动效曲线与色彩体系。** Windows 只提供操作系统层面的差异——窗口控制的位置、安装器的形态，其余一律按本文件执行。

| 项 | macOS | Windows | Linux |
| --- | --- | --- | --- |
| 窗口控制 | 系统红绿灯，左上 | 自绘三键，右上 | 自绘三键，**可切换为系统标题栏**（§10.5） |
| 安装器 | `.dmg` 拖拽安装，无自定义界面 | NSIS 自定义界面，410 × 290 | deb / rpm / AppImage，无自定义界面 |

**应用菜单不列入差异**：macOS 走系统菜单栏，Windows 与 Linux 在标题栏左上角放一个「≡」按钮打开同一套菜单项（见 §2.3）。三端菜单的结构、顺序、快捷键提示完全相同。

**Linux 的窗口控制有两个合法形态**：自绘三键（与 Windows 同款）或系统标题栏。这不是"第三个差异"，因为它是**用户设置项**而非平台事实，见 §10.5。

除此之外的任何差异——间距、圆角、字号、图标、动效曲线、滚动条、焦点环、右键菜单——均视为缺陷。

### 2.3 标题栏规格（仅电脑三端）

标题栏是**窗口**的部件，移动端没有窗口标题栏——手机与 iPad 的顶栏是应用内自绘的 48px 行（含安全区），见 §10.3。本节全部规格不适用于移动端。

标题栏是全窗第一条水平带，高度固定 44px，横跨整个窗口宽度。

```
┌──────────────────────────────────────────────────────────────┐ 0
│ ● ● ●              [ 今天 ]                         ▁ ▢ ✕    │ 44  macOS
│ ≡                  [ 今天 ]                         ▁ ▢ ✕    │ 44  Windows
├────────┬───────────────────────────────────────┬─────────────┤
│  Rail  │              Column                   │    Spine    │
│  48px  │              716px                    │    56px     │
└────────┴───────────────────────────────────────┴─────────────┘ 580
```

**macOS 参数**（`src-tauri/tauri.conf.json`）：

```json
"titleBarStyle": "Overlay",
"hiddenTitle": true,
"trafficLightPosition": { "x": 16, "y": 16 }
```

红绿灯直径 12px，间距 8px，总宽 52px，占位区间 x ∈ [16, 68]，垂直中心 y = 22（= 44 ÷ 2）。
`y` 由当前的 `22` 调整为 `16`：`trafficLightPosition` 的 `y` 是顶边坐标，`16 + 12 ÷ 2 = 22` 才与 44px 标题栏垂直居中。当前配置 `22` 会使红绿灯整体下移 6px。

**Windows 参数**：

```json
"decorations": false
```

自绘三键规格：

| 项 | 值 |
| --- | --- |
| 单键尺寸 | 46 × 32 |
| 三键总宽 | 138（46 × 3，无间距） |
| 位置 | 右对齐，`right: 0`，`top: 6`（= (44 − 32) ÷ 2） |
| 图标 | 10px 网格，1px 线宽，颜色 `--static-ink-2` |
| 悬停底色 | `--static-paper-2`，`--motion-fast` fluid |
| 关闭键悬停 | `--static-danger` 底 + 白色图标。红色取自 HIG 的 destructive 语义，不是 Windows 平台约定 |
| 按下 | 底色加深至 `--static-paper-3` |
| 焦点环 | 2px `--static-teal-600`，offset −2px（向内，避免出窗） |
| 图标尺寸 | 16px，`minimize` / `maximize` / `x` 三个 morphicons 图标 |

**取舍说明**：Windows 上 `decorations: false` 会失去 Windows 11 的 Snap Layouts（悬停最大化键弹出分屏布局）。保留 Snap Layouts 必须使用系统标题栏（32px 高），届时两端标题栏高度不一致，违反同源契约。本项目选择前者，并在"已知限制"中登记。拖拽至屏幕边缘吸附、`Win + 方向键` 属于系统级行为，不受影响。

#### 2.3.1 Windows 菜单按钮

Windows 没有全局菜单栏，若只靠快捷键，功能将不可发现。因此在标题栏左上角放一个菜单按钮，位置与 macOS 红绿灯对称。

| 项 | 值 |
| --- | --- |
| 尺寸 | 32 × 32 |
| 位置 | `left: 8`，`top: 6` |
| 图标 | `menu`（三横线），16px，1.5 线宽 |
| 悬停 | 底色 `--static-paper-2`，圆角 8，`--motion-fast` fluid |
| 展开 | 浮层菜单宽 240，按钮下方 4px |
| 不可拖拽 | 是 |

菜单项与 macOS 菜单栏一一对应，**顺序与分组完全相同**：

```
关于空谷 Ondra
偏好设置…                    Ctrl + ,
检查更新
──────────────────────
隐藏到托盘
退出                         Alt + F4
```

macOS 侧对应五组：应用菜单（关于/偏好设置/服务/隐藏/退出）、文件（新建对话/导出）、编辑（撤销/复制/粘贴/全选）、显示（主题/字号/切换脊）、窗口、帮助。

### 2.4 标题让位

标题不放在左上角，而是**在主列内水平居中**。这一决定同时解决两端让位问题：

| 平台 | 左侧占用 | 右侧占用 | 标题可用区间 |
| --- | --- | --- | --- |
| macOS | 0 – 68（红绿灯） | 0 | 68 – 820 |
| Windows | 8 – 40（菜单按钮） | 682 – 820（三键） | 40 – 682 |

主列区间为 [48, 764]，中心点 x = 406。两端均不与占用区重叠，因此标题位置完全相同。

**标题规格**：

| 项 | 值 |
| --- | --- |
| 字号 / 字重 | 15px / 500 |
| 字距 | −0.01em |
| 颜色 | `--static-ink-1` |
| 最大宽度 | 420px（`min(420px, 主列宽 − 96px)`） |
| 溢出处理 | 单行省略号，悬停显示完整标题的浮层提示 |
| 副标题 | **不在标题栏显示**。"相处第 12 天"移至时间轴首个日期分隔行右侧 |

不设副标题的原因：44px 高度内放两行会破坏垂直居中，且 Windows 侧三键占位后水平空间不足。

### 2.5 拖拽区

| 区域 | 可拖拽 | 说明 |
| --- | --- | --- |
| 标题栏 44px 全宽 | 是 | `data-tauri-drag-region` |
| 左侧脊顶部 44px | 是 | 与标题栏连成一片 |
| 右侧脊顶部 44px | 是 | 同上 |
| 红绿灯区 [16,68] | 否 | 系统处理 |
| Windows 三键区 [682,820] | 否 | 按钮不标记拖拽属性 |
| 标题文字 | 是 | 文字不拦截拖拽 |

双击标题栏的缩放/最大化行为交由系统处理，不自实现。原因：macOS 的"双击标题栏"行为受系统偏好设置控制（缩放 / 最小化 / 无操作），自实现会覆盖用户偏好。

### 2.6 Windows 自绘三键的实现前提

当前 `src-tauri/capabilities/default.json` 只开放了 `core:window:allow-start-dragging`，不足以支撑自绘三键。需追加：

```json
"core:window:allow-minimize",
"core:window:allow-toggle-maximize",
"core:window:allow-close",
"core:window:allow-is-maximized"
```

前端调用：`getCurrentWindow().minimize() / toggleMaximize() / close()`。
最大化状态需监听 `onResized` 并比对 `innerSize` 与 `currentMonitor().size`，用于切换最大化/还原图标。

### 2.7 Windows 端的 HIG 适配

Windows 与 macOS 的渲染栈不同，直接套用同一份 CSS 会出现肉眼可见的偏差。以下九项是必须做的适配，做完之后两端应达到"并排看不出平台"的程度。

| 项 | 做法 | 原因 |
| --- | --- | --- |
| 字体渲染 | `[data-platform="win"] body { font-variation-settings: "wght" 450; }` | DirectWrite 渲染 MiSans VF 比 CoreText 细约 8%，不加权则 14px 正文发虚 |
| 滚动条 | 两端统一自绘 overlay：默认透明，滚动时出现，停止 800ms 后淡出，宽 8px，悬停 12px | Windows 常驻滚动条占 17px，会把 716px 主列压到 699px，两端布局立刻不一致 |
| 焦点环 | `*:focus { outline: none }` + 自绘 2px 圆角环 | Windows 默认焦点样式是 1px 直角虚线，与 HIG 的圆角环冲突 |
| 右键菜单 | 自绘 `Menu` 组件，禁用系统菜单 | 系统菜单无法套用宣纸底色与 0.5px 线 |
| 关闭语义 | 点关闭 = 隐藏到托盘；首次关闭时提示，可勾选"以后直接退出" | HIG：关闭窗口不等于退出应用。Windows 用户默认认为关闭即退出，因此首次必须解释，不能默默改行为 |
| 修饰键 | `Cmd` → `Ctrl`，其余不变 | |
| 快捷键可发现性 | 无菜单栏，所有快捷键必须在右键菜单或悬停提示中可见 | HIG 的 discoverability。Windows 没有菜单栏可挂，只能靠菜单按钮与右键菜单补齐 |
| 高 DPI | 0.5px 线用 `box-shadow: 0 0 0 0.5px` 实现；`devicePixelRatio` 为非整数（125% / 150%）时降级为 1px | 125% 缩放下 0.5px 会被渲染成 0 或 2 物理像素，线会消失或发粗 |
| 窗口动画 | 最小化 / 还原 / 最大化交给系统 | 不模仿 macOS 的 genie 效果，两端各自使用系统动画是合理的 |
| 全屏 | `F11`，对应 macOS 的 `Ctrl + Cmd + F` | |

### 3.5 窗口放大时，什么变、什么不变

820 × 580 是基准。用户拖大窗口后，各区块的行为必须逐项定死，否则会出现"越放大越难看"。

| 区块 | 820 基准 | 放大时的行为 | 上限 |
| --- | --- | --- | --- |
| Rail | 48 | **不变** | 48 |
| Spine | 56 | **不变** | 56 |
| 正文宽度 | 588 | **不变** | 588 |
| 输入卡片 | 620 | **不变** | 620 |
| 主列两侧留白 | 各 64 | **吸收全部新增宽度**，均分 | 无上限 |
| 消息滚动区高度 | 436 | 吸收全部新增高度 | 无上限 |
| 检查器 | 无 | ≥ 1200 时**可**常驻，宽 300 | 300 |
| 标题栏高度 | 44 | **不变** | 44 |

**核心裁决：正文宽度封顶 588，多余宽度全部给留白。** 这是 §3.2 已定的规则，此处明确它在放大时的优先级——**留白优先于加宽正文**。

为什么不做"自适应加宽"：一行 42 个汉字已在舒适区上限。拉到 60 个汉字时，眼睛从行尾回到行首会跳行，阅读速度反而下降。用户想要更宽，应该是开大字号，不是拉长行宽。

**放大后的视觉平衡**：820 时正文占主列 82%，1920 时占 33%。这时两侧各 528px 的留白会显得空。补救两条，不加第三条：

| 宽度 | 补救 |
| --- | --- |
| ≥ 1200 | 检查器可常驻右栏（宽 300），把右侧留白吃掉一半 |
| ≥ 1440 | 时间轴首条与末条之外，上下各留 24px 见底背景，让"内容居中"这件事看得出来 |

**不做的事**：不加大字号（用户自己会调）、不加宽正文、不把 Rail 变成带文字的侧栏。这三件都是"放大即重设计"，与 §0.1 第 1 条冲突。

### 3.6 820 × 580 只约束电脑三端

这一条必须先划清边界，否则整章的尺寸数字会被误用到手机上。

**820 × 580 是 macOS / Windows / Linux 三端的窗口尺寸**，`width`、`height`、`minWidth`、`minHeight` 四个值都保持 820 × 580，**不做任何下调**。

移动端（iPad / iOS / Android / 鸿蒙）**没有"窗口尺寸"这个概念**，它按屏幕全屏渲染，尺寸由设备决定，与 820 × 580 无关。

| 端 | 尺寸来源 | 是否受 820 × 580 约束 |
| --- | --- | --- |
| macOS | 窗口，用户可缩放 | ✓ 默认 = 最小 = 820 × 580 |
| Windows | 窗口，用户可缩放 | ✓ 同上 |
| Linux | 窗口，用户可缩放 | ✓ 同上 |
| iPad | 屏幕 / 分屏 / 台前调度 | ✗ 按实际内容宽度走容器查询（§10.1） |
| iPhone | 屏幕全屏 | ✗ 同上 |
| Android | 屏幕全屏 | ✗ 同上 |
| 鸿蒙 | 屏幕全屏 | ✗ 同上 |

**为什么电脑端不把最小尺寸降到 640**：降到 640 会让用户在桌面端把窗口拖成一条竖条，进入 compact 形态——而 compact 是为手机设计的形态，脊被收进标题栏、按钮放大到 44px，在鼠标环境下并不好用。桌面端的最小尺寸应当是"双脊仍可用"的下限，820 正是这个下限。**下限的意义是保护可用性，不是迁就屏幕**。

**那桌面端遇到小屏怎么办**（如 1366×768 缩放 175%，有效宽度 780）：不缩小最小尺寸，而是**首次启动时按屏幕可用宽度决定初始尺寸**：

| 屏幕可用宽度 | 初始窗口 |
| --- | --- |
| ≥ 820 | 820 × 580（默认） |
| < 820 | 取屏幕宽 × 0.92，且不低于 640；高度同比例，不低于 500 |

此时窗口可以小于 820，但**这是"初始尺寸"，不是"最小尺寸"**——`minWidth` 仍是 820，用户不能手动拖到 780。两者不矛盾：程序可以开得比最小尺寸小，用户不能拖得比最小尺寸小。

**电脑端空间不足时的压缩优先级**（窗口高度被系统压缩时先压谁）：

```
1. 底部留白 12 → 8          （先压无信息区）
2. 输入区上间距 12 → 8
3. 输入卡片 76 → 64         （单行态可压）
4. 消息滚动区 436 → 剩余     （最后压，它承载内容）
5. 标题栏 44                （不压，压了拖不动）
```

## 4. 视觉系统

### 4.0 主题

**默认跟随系统**。三档取值：`system`（默认）/ `light` / `dark`，存 `localStorage['ondra.theme']`。未设置时按 `system` 处理。

**深色不是浅色的反色**。反色有三个具体问题，必须逐条避开：

1. **光晕**。纯黑底配纯白字会产生 halation（笔画外扩发虚），14px 中文尤其明显。因此底色取 `#141715`（带一点绿的深墨，不是 `#000000`），正文取 `#E8E6DF`（不是 `#FFFFFF`）。
2. **细线消失**。0.5px 线在纯黑上不可见、在纯白上刺眼。线色由暖灰 `#E4DFD3` 换为冷灰 `#2C3230`，是重新对齐亮度，不是取反。
3. **主色对比不足**。`#2E4A45` 放在 `#141715` 上几乎融进背景，必须提亮到 `#7FA79B`。这是全表唯一"必须改亮度"的令牌。

**语义不随主题变**：teal 永远表示主操作与水位，sand 永远表示暖度与关系，danger 永远表示危险。只换具体色值，不换语义。

**映射表**（浅 → 深，逐项说明处理方式）：

| 令牌 | 浅色 | 深色 | 处理方式 |
| --- | --- | --- | --- |
| `--static-paper-0` | `#FFFDF9` | `#141715` | 保留纸的暖调，只压亮度 |
| `--static-paper-1` | `#F7F4EE` | `#1A1E1C` | 与 paper-0 保持约 4% 亮度差，"脊略暗于主区"的关系不变 |
| `--static-paper-2` | `#F2EEE4` | `#222725` | 同上 |
| `--static-paper-3` | `#E9E4D6` | `#2C3230` | 按下态 |
| `--static-line` | `#E4DFD3` | `#2C3230` | 暖灰换冷灰，避免深底上发黄 |
| `--static-ink-1` | `#1C1F1D` | `#E8E6DF` | 不用纯白，保留 8% 灰 |
| `--static-ink-2` | `#5A625E` | `#B4B8B0` | |
| `--static-ink-3` | `#6E7570` | `#8A908A` | 深底上对比度 4.6:1 |
| `--static-ink-4` | `#9A9E96` | `#5F6560` | 仅占位符 |
| `--static-teal-600` | `#2E4A45` | `#7FA79B` | 提亮，深底必需 |
| `--static-sand-500` | `#B08A5A` | `#C9A578` | 提亮 |

**首帧不闪白**，三处必须同时做：

1. `index.html` 的 `<head>` 内联脚本（不超 6 行），在样式表加载前读取 `localStorage` 并写入 `document.documentElement.dataset.theme` 与 `style.colorScheme`。
2. `src-tauri/tauri.conf.json` 的 `backgroundColor` 当前固定为 `#fbfbfd`，深色系统下启动会闪一帧白。改为在 Rust 的 `setup` 中按系统主题调用 `window.set_background_color()`，两套值分别为 `#FFFDF9` 与 `#141715`。
3. `:root { color-scheme: light dark; }`，让原生滚动条、输入框、右键菜单跟随主题。

**切换动效**：不做整屏渐变（会拖帧）。只在用户手动切换时做 `--motion-fast` 的 `background-color` / `color` 过渡；跟随系统切换时瞬时生效（`--motion-0`）。

### 4.2 字体

**MiSans VF** 已内嵌于 `src/assets/fonts/MiSansVF.woff2`（8.3 MB，可变字重 150–700），授权见 `src/assets/fonts/LICENSE-MiSans.md`。

```css
@font-face {
  font-family: "MiSans";
  src: url("./assets/fonts/MiSansVF.woff2") format("woff2-variations");
  font-weight: 150 700;
  font-style: normal;
  font-display: block;
}
```

`font-display: block` 而非 `swap`：桌面应用不存在"字体加载慢"的场景，但存在首帧闪烁的场景。用 `block` 换取零闪烁，代价是最多 100ms 的空白。

**字阶表**：

| 名称 | 字号 | 字重 | 行高 | 字距 | 用途 |
| --- | --- | --- | --- | --- | --- |
| Display | 22px | 500 | 1.3 | −0.02em | 引导页主标题 |
| Title | 15px | 500 | 1.4 | −0.01em | 窗口标题、面板标题 |
| Body | 14px | 400 | 1.75 | 0 | 对话正文 |
| Body-strong | 14px | 500 | 1.75 | 0 | 用户消息 |
| Caption | 12px | 400 | 1.5 | 0 | 记忆薄片、时间戳 |
| Label | 11px | 400 | 1.4 | +0.01em | 读数标签、分组标题 |
| Label-strong | 11px | 500 | 1.4 | +0.01em | 数值读数 |
| Code | 13px | 400 | 1.6 | 0 | 代码块（`SF Mono` → `Menlo` 回落） |

**数字**：所有读数（62、+0.30、0.40）必须加 `font-variant-numeric: tabular-nums`。水位跳动时数字不左右抖动，这是"科技感"最廉价也最有效的一处。

**不采用 HIG 的 13px 正文**：HIG 的 Body 是 13pt，对应拉丁字母。中文在 13px 下笔画粘连，实测需 14px 起步。这是本项目对 HIG 的唯一字号偏离，理由记录于此。

### 4.3 几何

| 项 | 值 | 用途 |

| 圆角 | 16px | 窗口、抽屉、检查器、输入卡片 |

| 线宽 | 0.5px | 全部边框与分隔线 |
| 焦点环 | 2px `--static-teal-600`，offset 2px | 键盘焦点 |

**同心圆角**：内层圆角 = 外层圆角 − 内边距。例如 16px 容器配 8px 内边距时，内层控件用 8px，视觉上同心。不做这一条，圆角会显脏。

### 4.4 图标

**引擎**：morphicons 2.0.2（MIT，已在 `src/package.json` 的依赖中）。全应用图标一律通过 `morphicons/react` 的 `<MorphIcon>` 渲染，不手绘、不混用组件库。

**唯一入口**：`src/components/Icon.tsx`。该文件封装 `<MorphIcon>` 并锁定全部默认参数。业务代码只允许 `import { Icon } from './Icon.tsx'`，禁止直接引用 `morphicons/react`、`lucide-react` 或任何图标组件包。

```tsx
// src/components/Icon.tsx —— 全应用唯一的图标出口
import { MorphIcon } from "morphicons/react"

export function Icon({ icon, size = 16, label }: Props) {
  return (
    <MorphIcon
      icon={icon}
      size={size}
      strokeWidth={1.5}
      absoluteStrokeWidth
      spring={{ stiffness: 320, damping: 34 }}
      reducedMotion="user"
      label={label}
    />
  )
}
```

**为什么必须 `absoluteStrokeWidth`**：morphicons 继承 lucide 的尺寸缩放规则，`size` 变化时线宽会等比缩放。16px 与 20px 两个尺寸下会出现 1.5px 与 1.9px 的视觉差。开启该属性后线宽恒为 1.5px，这是"线条粗细一致"的唯一实现方式。

**为什么弹簧参数写死**：`bouncy` 会产生回弹，违反第 8.2 节的禁止清单。`{ stiffness: 320, damping: 34 }` 是临界阻尼，形变到位不回弹，耗时约 140ms，落在 120–180ms 的动效区间内。

**图标数据源**：

| 项 | 规则 |
| --- | --- |
| 主集 | Iconoir `outline`（298 个，24 × 24 网格，1.5 描边，圆头圆角） |
| 补充集 | Lucide（ISC 许可），仅当 Iconoir 缺该图形时使用 |
| 引入方式 | 从 `lucide` 包引入 `IconNode` 数据，不从 `lucide-react` 引入组件 |
| 非 24 网格 | 用 `fitIcon(icon, 32)` 归一，禁止直接缩放 |
| 禁止 | 手绘 `<path>`、emoji 当图标、字体图标、同一界面混用两套线宽 |

**形变对**（只在下列成对关系中允许 morph，不允许任意两个图标互变）：

| 位置 | 状态 A | 状态 B | 触发 |
| --- | --- | --- | --- |
| 发送键 | `arrow-up` | `square` | 开始生成 / 停止 |
| 左侧脊·今天 | `sun` | `moon` | 主题切换 |
| 抽屉开关 | `panel-left` | `x` | 展开 / 收起 |
| 检查器开关 | `sidebar-right` | `x` | 展开 / 收起 |
| 语音键 | `mic` | `waveform` | 开始 / 停止录音 |
| 记忆薄片 | `chevron-right` | `chevron-down` | 展开 / 收起 |
| 朗读 | `play` | `pause` | 开始 / 暂停朗读 |
| 桌宠 | `circle` | `moon` | 在场 / 休息 |

形变的语义是"同一个东西换了个状态"，因此必须发生在同一位置、同一尺寸。跨位置的状态变化（例如从输入区跳到标题栏）不使用 morph，直接切换。

**无障碍**：每个图标必须传 `label`（中文，如「展开设置」）。仅作装饰的图标显式传 `label={undefined}`，此时 morphicons 会输出 `aria-hidden`。

**合规**：morphicons（MIT）、Iconoir（MIT）、Lucide（ISC）三项均须在 `NOTICE` 中登记，包含版本、版权方、许可证与项目地址。

### 4.5 品牌标志唯一真源

**唯一真源**：仓库根 `/icon.svg`。它是 24 × 24 的应用图标（圆角底板 + 鲸鱼图形），也是托盘、安装器、应用图标（`.icns` / `.ico` / `.png`）的唯一来源。

**派生链**（全部由脚本生成，不手工维护第二份）：

```
/icon.svg
  ├─ pnpm tauri icon icon.svg      → src-tauri/icons/*.png / .icns / .ico
  ├─ node tools/gen-brand.mjs      → src/brand/mark.ts（纯图形 path，供内联使用）
  └─ node tools/gen-brand.mjs      → assets/favicon-*.png、安装器品牌区 32×32
```

`src/brand/mark.ts` 首行必须带 `/* AUTO-GENERATED from /icon.svg — do not edit */`，并纳入 CI 校验：真源变更而未重新生成时构建失败。

**必须删除的两处第二真源**（当前状态）：

| 文件 | 问题 |
| --- | --- |
| `src/components/WhaleMark.tsx` | 手写鲸鱼路径，viewBox 为 23.16 × 17.04，与 `icon.svg` 的坐标系不同。`Sidebar.tsx:263` 正在使用它，导致侧栏与首页出现两种 logo 形态 |
| `icon-1024.svg` | 与 `icon.svg` 几何不一致的独立 1024 版（squircle 与 `rx=5.5` 两种圆角），会与 `tauri icon` 的产物漂移 |

删除后，`Sidebar.tsx` 改用 `src/brand/mark.ts`，与首页共用同一份图形数据。

**品牌标志不走 morphicons**：它是图形不是图标，viewBox 与线宽体系都不同，塞进图标引擎会让"换图标库"变成不可能。这一条与 `WhaleMark.tsx` 文件头注释的判断一致，只是结论从"另存一个组件"改为"从真源派生"。

### 4.6 材质与阴影

全界面**只有一种阴影**：`--shadow-lv3`，仅用于浮层菜单（z-index 40 及以上）。其余层级一律用 0.5px 描边表达。

不使用：毛玻璃（`backdrop-filter`）、渐变、内阴影、发光。原因：毛玻璃在 820×580 的小窗口上会显著拖低滚动帧率，且与宣纸底色冲突。

## 5. 组件规范

### 5.0 通用状态与反馈

所有可交互元素必须先满足这一节，再看各自的小节。**组件小节只描述"与通用规则不同"的部分**，重复描述本身就是缺陷——它会随时间长出两个版本。

#### 5.0.1 八态矩阵

每个可交互元素都在这八态之内。没有的状态写"不适用"，不允许留空。

| 状态 | 判据 | 视觉 | 是否必须 |
| --- | --- | --- | --- |
| 常态 | 默认 | 见各组件 | 必须 |
| 悬停 | 指针进入 | `--alias-interactive-bg-hover`，`--motion-fast` fluid | 必须（触摸设备无此态） |
| 按下 | `:active` | 底色加深一档 + `scale(.98)` | 必须 |
| 焦点 | `:focus-visible` | 2px `--static-teal-600` 环，offset 2px | 必须 |
| 选中 | 逻辑上被选中 | 图标/文字转 `--static-teal-600`，Rail 另有 2px 竖条 | 按需 |
| 禁用 | 不可操作 | 文字 `--alias-label-dimmed`，不透明度 1（见 5.0.3） | 按需 |
| 加载 | 操作进行中 | 见 5.0.4 | 按需 |
| 错误 | 操作失败 | 见 5.0.5 | 按需 |

**`:focus-visible` 而非 `:focus`**：鼠标点击按钮后不该出现焦点环，只有键盘导航才该出现。用 `:focus` 会让每次点击都闪一个环，这是最常见的粗糙感来源。

#### 5.0.2 反馈必须在 100ms 内出现

任何会失败或耗时的动作，**结果可以后到，状态必须立刻变**。三类动作的具体落点：

| 动作 | 0ms | ≤100ms | 结果到达 |
| --- | --- | --- | --- |
| 发送消息 | 输入框清空、消息以 60% 不透明度插入 | 显示"她在想"（三个点的呼吸，非打字机） | 流式替换占位 |
| 切换模型 | 菜单项打勾、菜单关闭 | 模型名转 `ink-3` | 成功：转回 `ink-2`；失败：Toast + 名字回滚 |
| 保存设置 | 滑杆值已变（本地即时） | 底部条出现「保存中」 | 成功：条消失；失败：条变红 + 「重试」 |
| 删除记忆 | 薄片淡出并向左 8px | — | 成功：从列表移除；失败：薄片复位 + Toast |
| 连接通道 | 开关进入 pending（轨道变半透明） | — | 成功：开关落位；失败：开关弹回 |

**禁止**：本地已完成的操作（如滑杆取值）等待服务端确认才更新界面。用户拖了滑杆，界面必须立刻跟手；服务端只是持久化。

#### 5.0.3 禁用必须说明原因

禁用而不解释，用户只会认为坏了。规则：

| 规则 | 说明 |
| --- | --- |
| 禁用项保留在位置上 | 不隐藏、不移除，只降低对比。隐藏会让布局跳动 |
| 必须有 `title` 或可聚焦的原因 | 例：「先选一个模型」 |
| 优先用"引导态"而非"禁用态" | 若禁用原因是"还没配置"，直接显示「去配置」按钮，比灰掉的控件有用得多 |
| 不透明保持 1 | 靠颜色降低而非透明度，避免与背景混成一团、失去可读性 |

#### 5.0.4 加载：三种，不许多

| 形态 | 用在哪 | 规格 |
| --- | --- | --- |
| 行内三点 | 她正在想（回复生成中） | 三个 3px 圆点，`ink-3`，依次 `opacity .3 → 1`，间隔 160ms，循环 |
| 控件 pending | 按钮、开关、滑杆提交中 | 内容不透明度降至 40%，不换图标、不加转圈 |
| 骨架块 | 列表类区域首次加载（记忆、设置模块层） | `--static-paper-2` 纯色矩形，**不做闪光** |

**禁止转圈（spinner）**：本地操作通常 < 300ms，转圈只会闪一下，比不动更难看。只有超过 1 秒的操作才允许 16px 细环旋转，且必须延迟 300ms 才出现——先出现再消失等于制造噪声。

#### 5.0.5 错误必须三段式

`发生了什么 · 为什么 · 下一步`，三段缺一不可。

| 位置 | 形态 | 停留 |
| --- | --- | --- |
| 输入框内校验 | 输入框下方 12px 红字，不弹窗 | 到改正为止 |
| 消息流内 | 消息下方 12px 红字 + 「重试」文字按钮 | 常驻直到重试成功 |
| 用户主动操作失败 | Toast 错误态 | 4s，可悬停暂停计时 |
| 需用户决策 | Dialog | 到用户选择为止 |

错误文案禁用词：「出错了」「操作失败」「系统异常」。这三个词等于什么都没说。

#### 5.0.6 指针与光标

| 元素 | 光标 |
| --- | --- |
| 可点击 | `pointer` |
| 可拖拽（滑杆、曲线控制点、窗口） | `grab` → 拖动中 `grabbing` |
| 可选中文本 | `text` |
| 禁用 | `not-allowed`（仅禁用项，普通不可点区域用 `default`） |
| 正在等待 | 保持原光标，**不用 `wait`**（会让人以为整个应用卡住） |

#### 5.0.7 点击热区

视觉尺寸与可点击尺寸分离。**视觉 16px 的图标，热区必须 32×32**（macOS 指针环境的下限是 24，舒适值是 32）。

热区分两套值。**这不是两套设计，是同一设计的两种输入方式**——指针精确，手指不精确。

| 元素 | 视觉 | 指针热区 | 触屏热区 | 触屏是否放大视觉 |
| --- | --- | --- | --- | --- |
| Rail 图标 | 16 | 32 × 32 | — （手机端无 Rail） | — |
| 发送键 | 28 | 32 × 32 | 44 × 44 | 是，图标 16 → 20 |
| 消息操作按钮 | 16 | 24 × 24 | 40 × 40 | 是，16 → 18 |
| 关闭叉 | 12 | 24 × 24 | 44 × 44 | 是，12 → 18 |
| Windows 三键 | 10 | 46 × 32 | — （无窗口控制） | — |
| 记忆薄片删除点 | 12 | 20 × 20 | 40 × 40 | 是，12 → 16 |
| `TopBar` 汉堡 | — | — | 44 × 44 | — （仅移动端） |
| `TopBar` 状态点 | 8 | — | 44 × 44 | 否，点仍 8px |

**触屏热区下限 44 × 44**（Apple HIG 与 Material 的共同值），不管视觉多小。指针热区下限 24，舒适值 32。

**Android 与鸿蒙的 48 不是另一套值，是同一档的下限加余量**。§10.12 登记这两端为 48，原因是 Material Design 3 规定触控目标 48dp，且 Android 的 `dp` 与 CSS `px` 在 `devicePixelRatio` 非整数时不严格一一对应，按 48 写能保证任何 DPR 下都不低于 44。**iPad 与 iOS 仍按 44 执行**——iOS 的 `pt` 是严格映射，44 就是 HIG 原值。落地时用一个变量收口，不要在两处写死：

```css
:root { --hit-touch: 44px; }
@media (hover: none) and (pointer: coarse) {
  :root { --hit-touch: 44px; }
  [data-platform="android"], [data-platform="harmony"] { --hit-touch: 48px; }
}
```

**为什么触屏连视觉尺寸也要放大**：手机观看距离比桌面远约 40%，16px 图标在 44px 热区里会显得孤零零一个小点，用户看不出那是按钮。热区放大、视觉也放大，两者比例才正常。

热区用 `::before` 绝对定位扩展，不用 padding 撑（padding 会把视觉尺寸也撑大）。触屏放大视觉尺寸时**不用 `transform: scale()`**——那会让 1.5px 线变得粗细不均，改为直接换 size 属性（`Icon` 支持 16/20 两档，见 §4.4）。

#### 5.0.8 组件跨端适用性总表

§5 的 15 个组件小节默认描述的是**指针 + 窗口**环境。移动端不是"把同一套规格缩小"，而是有组件消失、有组件换形态、有组件改热区。落地前必须查这张表，否则会把桌面数值直接搬到手机上。

| 组件 | 电脑三端 | iPad | 手机 / 鸿蒙 | 变化要点 |
| --- | --- | --- | --- | --- |
| TitleBar | ✓ 44px | ✗ | ✗ | 移动端换 `TopBar`（48 + 安全区，§10.3） |
| Rail | ✓ 48px 常驻 | ✓ 常驻 | ✗ | 收进 `TopBar` 汉堡 + 全屏抽屉 |
| Timeline | ✓ | ✓ | ✓ | 仅字号 14→16、行距放大 |
| Message | ✓ 悬停出按钮 | ✓ 接键悬停 / 触屏常驻 | ✓ 常驻按钮 | 按钮从"悬停出现"改"常驻 40% 不透明" |
| MemoryChip | ✓ | ✓ | ✓ | 触屏下右箭头常显（无悬停可依附） |
| Composer | ✓ | ✓ | ✓ | 字号必须 16px；语音键更重要 |
| Spine | ✓ 纵向 6×150 | ✓ 同 | ✗ | 改为 `TopBar` 下沿 2px 横线 + 圆点 |
| Inspector | ✓ 侧栏/抽屉 | ✓ 可常驻 | ✗ | 改全屏 Sheet 从底部推入 |
| Drawer | ✓ 300px 覆盖 | ✓ 300px | ✗ | 全屏 Sheet 从左侧推入 |
| Toast | ✓ 底部居中 | ✓ 同 | ✓ 顶部 | 手机上移到顶部，避开键盘区 |
| Menu | ✓ 浮层，不超窗口 | ✓ | ✓ | 触屏下改为底部 Sheet 式动作表（长按触发） |
| Sheet | ✓ 居中 480 | ✓ | ✓ | 从底部推入，最大高 90vh |
| Dialog | ✓ 400 居中 | ✓ | ✓ | 同，宽度改 `calc(100vw - 48px)` |
| Settings | ✓ 独立窗口 560 | ✓ 全屏 | ✓ 全屏 | 手机上为全屏页面，非弹窗 |
| Onboarding | ✓ 480×360 | ✓ | ✗ | **手机上卡片宽度改 `calc(100vw - 40px)`**，高度自适应 |
| 桌宠 | ✓ | ✗ | ✗ | 不存在 |

**三条从这张表读出来的通用规律**：

1. **悬停依附的控件必须给触屏替代**。Message 的操作按钮、MemoryChip 的箭头、Rail 的悬停标签，三处在 `hover: none` 下全部改为常驻或长按。
2. **侧向展开的容器在窄屏上改为从对应边推入的全屏**。Drawer 从左、Inspector 从下，方向对齐用户的心理预期。
3. **固定像素尺寸的卡片必须给窄屏兜底**。480 宽的卡片在 375 屏上会溢出，一律写 `min(480px, calc(100vw - 40px))`。

### 5.1 TitleBar（仅电脑三端）

移动端的对应部件是 `TopBar`：高度 48 + 安全区，语义与 TitleBar 相同（左抽屉入口 / 中标题 / 右状态点），但**不是窗口标题栏**，没有拖拽与窗口控制。见 §10.3。

| 属性 | 值 |
| --- | --- |
| 高度 | 44px |
| 背景 | 透明（透出 `--static-paper-1`） |
| 下边框 | 无（由主列与双脊的底色差表达分界） |
| 标题 | 见 2.4 |
| 交互 | 拖拽、双击缩放（系统） |

### 5.2 Rail（左侧脊）

| 属性 | 值 |
| --- | --- |
| 宽度 | 48px |
| 背景 | `--static-paper-1` |
| 右边框 | 0.5px `--static-line`（画在 Rail 右侧，不画在 Column 左侧） |
| 图标尺寸 | 32 × 32 点击区，16 × 16 图形 |
| 图标间距 | 8px |
| 首图标起点 | y = 64（标题栏 44 + 20） |
| 底图标 | 设置，固定在 y = 532（580 − 16 − 32） |
| 选中态 | 图形颜色 `--static-teal-600`，左侧 2px 竖条（x=0，高 16，居中） |
| 悬停态 | 背景 `--static-paper-2`，圆角 8 |

**图标顺序**（自上而下）：今天 / 周 / 记忆 / 剧场 / （留空）/ 设置。

点击任一图标 → 展开对应抽屉（宽 300px，覆盖主列左半），再次点击收起。抽屉展开时该图标保持选中态。

**补充交互**：

| 场景 | 行为 |
| --- | --- |
| 悬停 | 图标从 `ink-2` 转 `ink-1`，底色浮现（`--motion-fast`）；800ms 后右侧出现 12px 文字标签（延迟出现，避免扫过时闪一片） |
| 点击已展开的图标 | 收起抽屉，图标回到未选中 |
| 点击另一个图标 | 当前抽屉内容**原地替换**，不先收起再展开（否则两次 180ms，共 360ms） |
| 键盘 | 进入 Rail 后 `↑/↓` 移动，`Enter` 展开，`Cmd/Ctrl + 1..5` 直达 |
| 齿轮 | 不展开抽屉，直接打开偏好设置窗口 |
| 抽屉展开状态 | Rail 不被遮挡，图标始终可点 |
| 缩放动画 | 无。图标不做 `scale` 反馈，只用底色（图标形变已被 A9 占用，避免同元素两种动画） |

### 5.3 Timeline（主列）

| 属性 | 值 |
| --- | --- |
| 背景 | `--static-paper-0` |
| 左右内边距 | 64（正文 588 居中于 716） |
| 滚动 | 自绘 overlay，宽 8px / 悬停 12px，不占布局（见 §12.1） |
| 消息间距 | 同一条消息内 4px，不同条之间 20px |
| 跨天分隔 | 上下各 32px 留白 |

**日期分隔行**：左右各一条 0.5px 线，中间 11px 文字，格式「今天 · 周四」。首屏在文字右侧 8px 处附「第 12 天」标注（`--static-ink-4`）。

**滚动到底**：新消息到达时，若用户已在底部 80px 内，自动滚动；否则显示"↓ 有新消息"浮标，不抢滚动位置。

### 5.4 Message

| 类型 | 对齐 | 排版 | 标记 |
| --- | --- | --- | --- |
| 用户消息 | 右对齐，右边界 x=700 | 14px / 500 / `--static-ink-1` | 右侧 2px × 36 竖线，`--static-teal-600`，距文字 6px |
| 助手消息 | 左对齐，左边界 x=112 | 14px / 400 / `--static-ink-1` | 无 |
| 系统提示 | 居中 | 12px / `--static-ink-3` | 无 |

**没有**：气泡、头像、消息状态勾、时间戳（时间只在日期分隔行出现）、已读回执。

**用户消息的竖线**：高度固定 36px（约两行），不随消息长度增长。它是"我说的"标记，不是装饰。

**流式输出**：按标点与语义边界切块，块内 2–4 字，单块 12ms，标点后 +60ms；带积压追赶与熔断，规则见 §8.4。流式期间不显示光标。

**停止按钮**：生成中，输入卡片右侧的发送键变为「先别说」（12px 文字按钮，宽 64），点击后消息尾部追加 12px 灰字「已停下」。

**消息的五种异常态**（正常态只有两种，异常态反而更多，必须逐个定义）：

| 态 | 视觉 | 可执行 |
| --- | --- | --- |
| 生成中 | 已生成部分正常显示，尾部三个点 | 「先别说」 |
| 已停止 | 正文 + 尾部 12px `ink-4`「已停下」 | 「继续」 |
| 发送失败 | 用户消息转 60% 不透明度 + 下方 12px 红字「没发出去 · 网络断了 · 重试」 | 「重试」「删除」 |
| 回复失败 | 助手位置显示一行红字，不占满整块 | 「重试」 |
| 被撤回（她主动） | 整条淡出 180ms 并移除，不留痕迹 | — |

**悬停操作**（出现于消息右上角，`--motion-fast` 淡入）：

| 操作 | 位置 | 说明 |
| --- | --- | --- |
| 复制 | 所有消息 | 复制纯文本，不含 Markdown 记号 |
| 引用 | 所有消息 | 插入 Composer，见 §12.7 |
| 朗读 | 助手消息，且 `tts` 开启 | 播放/暂停（图标形变 A9） |
| 重答 | 助手消息 | 从这条重新生成，下方消息标灰并可「保留」或「丢弃」 |
| 删除 | 所有消息 | 需确认（Dialog），因为不可逆 |

**消息不可编辑**。这是刻意的：编辑历史消息会让"她记得什么"变得不可推断，而记忆可追溯是本项目的核心承诺。想改口就直接说，她会按新的说法修正记忆。

**选中与复制**：消息正文可选中；跨消息可连续选中（容器 `user-select: text`，但按钮与薄片 `user-select: none`）。选中后浮出一个 32px 高的小工具条（复制 / 引用），位置在选区上方 8px，超出窗口时翻到下方。

**输入区的十条细则**：

| 场景 | 行为 |
| --- | --- |
| 空输入 + 发送键 | 发送键保持可见但为禁用态（`teal` 降为 40% 不透明度），**不移除**。移除会让右侧突然空一块 |

| 首次聚焦 | 边框从 `0.5px line` 过渡到 `0.5px teal-600`（`--motion-fast`），不做外发光 |
| 高度增长 | 从 1 行到 3 行逐级增长，每级 20px，`--motion-base`；超过 3 行内部滚动 |
| 粘贴多行 | 不自动发送，不自动折叠，原样插入 |
| 输入中的 @ / # | 不触发任何自动补全。本项目无此概念，硬加会与"直接说话"的定位冲突 |
| 生成中 | 输入框保持可编辑（用户可先写下一条），发送键变为「先别说」 |
| 生成中点 Enter | 按设置「打断方式」执行：排队则入队并在气泡右侧显示「排队中」；打断则停止当前生成并立即发送 |
| 草稿 | 切换会话/抽屉不丢草稿；退出应用时写入本地，下次启动恢复（保留 7 天） |
| 超出长度 | 单条上限由模型上下文决定，接近上限时底部行出现 11px `ink-3` 计数，超出时发送键禁用并说明原因 |

| 附件细则 | 规则 |
| --- | --- |
| 类型 | 图片、文本、PDF、代码文件。其他类型给提示而非静默拒绝 |
| 大小 | 单文件 20MB，单条总计 50MB。超出时提示具体数值，不只说"太大" |
| 上传时机 | 选中即上传（不等发送），发送时只引用。这样发送是瞬时的 |
| 上传中 | 缩略图上覆盖 40% 遮罩 + 底部 2px 进度条 |
| 失败 | 缩略图右上角红色 `!`，点击可重试或移除 |
| 图片粘贴 | 自动命名 `粘贴的图片-{时间}`，不进系统相册 |
| 移除 | 悬停出现 12px 叉，点击立即移除（无确认，可撤销通过重新添加） |

| 呼吸暂停条件 | ①窗口失焦 ②生成中（她在想，呼吸应停） ③检查器展开中（正在看数字，不该晃）④`prefers-reduced-motion` |

**关于「让位」这条**（原表没有，是实测补的）：

窗口最小宽 820。提示条最大宽 420、居中 → 占 x 200–620；设置面板宽 360、右贴 Spine → 占 x 404–764。两个区间相交，**面板标题与三个层切换选项卡正好落在交叠区里**。

层级本身是对的（`--z-toast` 50 高于 `--z-drawer` 30），所以提示条不会被面板吞掉——但它会压住标题。三种解法里只有「左移落点」同时满足三条：

| 做法 | 为什么不选 |
| --- | --- |
| 降 Toast 层级 | 提示条被面板整块吞掉，用户看不到「已复制」 |
| 收窄 Toast 宽度 | 420 已是「一句话 + 关闭键」的下限，再窄就折行 |
| **左移落点** | 宽度不变、无浮层时行为零变化，只是换个落点 |

位移量 = 浮层宽 / 2（把中心从视口中心挪到剩余空间中心）。用 `--overlay-right-w` 表达，面板宽度改动时自动跟上，避免"提示条正好骑在面板边缘上"这类差十几像素的缺陷。

这条不写进文档就会出现一个问题：截图里标题被盖住，而 `textContent` 类断言照样全绿——文字在 DOM 里，只是看不见。

### 5.13 设置

设置分两层，对应 HIG 的 Settings 与 Inspector 两种模式：

| 层 | 入口 | 内容 | 形态 |
| --- | --- | --- | --- |
| 偏好设置 | `Cmd/Ctrl + ,`、Rail 底部齿轮 | 主题、语言、字号、发送方式、默认权限、更新、关于 | 独立窗口，560 × 480，左侧 160px 导航 |
| 检查器设置 | 检查器底部「全部设置」 | 1168 项插件参数（自动生成） | 抽屉，宽 300 可扩至 420 |

**检查器设置的三层深度**：

| 层 | 数量 | 控件语言 | 面向 |
| --- | --- | --- | --- |
| 场景 | 13 项 | 滑杆（带语义锚点）、分段、开关、24h 曲线 | 全部用户 |
| 模块 | 122 段 | 按插件分组，可搜索、按最近改动排序 | 愿意深调的用户 |
| 原始 | 1168 条 | 键值 + 类型 + 默认值 + 来源插件 + 影响范围 | 开发者 |

切换层用顶部分段控件，不换窗口。当前层记忆在会话内保持，重启后回到场景层。

**这三个数字的来源与口径**（可复算，不是估计）：

| 数字 | 口径 | 复算方式 |
| --- | --- | --- |
| 1168 | 123 个 `settings.ts` 中 `FIELD_SPECS` 的**顶层键总数** | 逐文件解析 `export const FIELD_SPECS ... { ... }` 的一级键后求和 |
| 122 | 声明了 `CONFIG_SECTION`（即真正注册配置段）的插件数 | `grep -rl 'export const CONFIG_SECTION' --include=settings.ts` |
| 1168 − 561 = 607 | 普通字段 / 高级字段 | 按 `advancedOnly: true` 拆分 |

`kind` 的真实分布（合计 1168）：`number` 576 · `boolean` 359 · `string` 126 · `json` 54 · `enum` 53。这五个数决定五种渲染器的**被使用频次**——`number` 与 `boolean` 合计 80%，所以这两种控件的观感决定设置页的整体观感。

**为什么模块数是 122 而不是 123**：`ondra-memory-intake` 有 `FIELD_SPECS`（5 项），但没有导出 `CONFIG_SECTION`，即它**不向配置真源注册自己的段**——它的字段走插件实例配置，不走四层合并。界面看得见字段，但归不到一个可 `resolve` 的段里。**这一类段必须在模块层单独标记**，见下文「无段字段」条目。

**13 项场景**（固定，可改取值；每项一行，全部是**已存在的真实键**）：

| # | 名称 | 控件 | 锚点文案 | 绑定段.字段（kebab，即配置文件名里的写法） | 范围 / 默认 |
| --- | --- | --- | --- | --- | --- |

**为什么第 1 项是「分段 4 档 + 展开滑杆」，而第 2、7、13 项是纯分段**：判据是**底层字段类型**，不是「看起来像几档」。

| 底层 `kind` | 控件形态 | 例子 | 为什么 |
| --- | --- | --- | --- |
| `enum`（`values` 有限枚举） | 纯分段，一档对应一个值 | `proactive-quota.profile` 的 `slow/standard/fast` | 值本身就是离散的，界面不能凭空多造一档，也不能把 `standard` 拆成 `standard-1.5` |
| `number`（连续，有 `min`/`max`） | 分段 4 档只是**快捷锚点**，必须能展开成滑杆改任意值 | `memory-core.archive-normal-days`（1–3650） | 用户想要「45 天」，而三档锚点只有 30/90/365/3650。若只给分段，等于把连续字段阉成枚举，「可自定义参数」这条要求就落不了地 |
| `boolean` | 开关 | `tts.enable` | — |

因此第 1 项的档位文案（一个月 / 三个月 / 一年 / 十年）**只是 30 / 90 / 365 / 3650 的显示名**，点开滑杆后显示的是真实天数，且滑杆步长必须为 1（字段没有 `step`，见 §12.16）。这条容易做错：把 `number` 字段做成纯分段，用户会以为参数只能选这四个值，而 `FIELD_SPECS` 里 `min: 1, max: 3650` 明明允许任意值。

**与旧表的差异**：旧表列的 13 个绑定目标里，**只有 3 个键真实存在**（`dialogue.maxTokens`、`tts.enable`、`pet.enable`，前者的语义还不适用），另外 10 个键在任何插件的 `FIELD_SPECS` 里都找不到。逐条处理如下：

| 旧表写的字段 | 真实情况 | 处理 |
| --- | --- | --- |
| `memory-decay.halfLifeDays` | `memory-decay` 无此键；衰减用的是艾宾浩斯八档 + SM-2 的 EF，且脚本注释明确「刻意不放进配置」 | 换 `memory-core.archive-normal-days`（才是「多久忘」的真实旋钮） |
| `proactive-quota.dailyBudget` | 本插件无此键；额度是 `profile` 三档 + `quotaOverride` | 换真实键，并把「每天几条」挪到 `proactive-gate.daily-quota`（真预算在闸门那侧） |
| `persona-core.toneIntensity` | 本插件无此键 | 换 `persona-vars.tone-level`（0–100，文档写的是「说话浓度」） |
| `emotion-hormone.volatility` | 本插件只有 4 个键，无 `volatility` | **删掉此项**：情绪起伏没有对应的可调标量，硬造一个等于承诺界面能改一件后端做不到的事 |

| `proactive-reason.expose` | 真实键是 `pool-enabled`（台词池兜底），语义不同 | 换真实键，并把文案改成它真正管的事 |

| `dialogue.maxTokens` | ✅ 存在，但默认 `0` = 交给上游 | 换成用户真会调的 `max-turns` |

**为什么场景层必须是「真实键的视图」而不是「新造一层配置」**：场景层的每一项改动都要能落到一份用户能看见的配置文件里。若它绑定的键不存在，用户调完之后要么没生效、要么生效在一个界面没显示的地方。**这一层不得新增任何字段**——只挑出现有的 13 个。

**⚠ 绑定时必须做一次键名映射，这是最容易踩空的地方**：

`FIELD_SPECS` 里的键是 **camelCase**（`archiveNormalDays`），而写进配置文件的键是 **kebab**（`archive-normal-days`）。两者由各插件自己的 `KEY_PAIRS` 表对应，**不是简单的大小写转换**——`maxCharsPerMessage` 对应 `max-chars-per-message`，但 `autoSeed` 在 `emotion-hormone` 里对应的是 `auto-seed`，而同一个词在别的插件里未必一样。界面的流程必须是：

```
段 id + kebab 键  →  查该插件的 KEY_PAIRS  →  得到 camel 键  →  在 FIELD_SPECS[camel] 取 min/max/default/doc
                                                              ↓
                                              读值/写值走配置文件的 kebab 键
```

只做字符串替换（`camel → kebab`）会在遇到连续大写或数字时出错（如 `gsvTextLang` → `gsv-text-lang`、`bm25K1` → `bm25-k1`），必须查表。上表 13 项已逐条验证过 `KEY_PAIRS` 里确有对应项。

**场景项的两条硬规矩**：

1. **一项只绑一个字段**（第 8 项「作息」绑两个键，是唯一的例外，因为它表达的是**一个区间**，拆成两个滑杆就不是「作息」了）。
2. **不得伪造取值范围**。滑杆的最大最小值必须等于 `FieldSpec.min/max`，不做"界面收窄"——那会让用户看到滑杆拉到底却没有真正到底。

**第 2 项为什么是 3 档而不是 4 档**：`profile` 的取值只有 `slow / standard / fast` 三个。「完全关闭」不单独占一档——它由 `enable` 表达。这是插件注释里专门解释过的决定：两个「关」（`enable=false` 与某个 `profile` 档位）并存的下场是用户关了一个、另一个还在工作，而面板只说「已关闭」。所以界面上这一项**只给 3 档**，要关她主动说话，去 `enable` 那一项。若某一版真需要 4 档，也不能靠"多加一个假档位"实现，必须让插件先在 `FIELD_SPECS` 里加值。

**第 7 项「上下文长度」为什么用 `max-turns` 而不是 `max-tokens`**：`dialogue.max-tokens` 默认 `0`，`0` 的含义是"不设上限、交给上游按模型默认处理"（插件注释原文）。把这样一个"0 表示没限制"的字段做成滑杆，滑杆最左端就等于"无限"——语义反了。`max-turns` 是"带几轮历史"，10 轮是个用户能理解的量，且它是普通字段（非 `advancedOnly`）。

**三种控件语言之外，场景层需要第四种：时间区间**。第 8 项是两个 `HH:MM` 输入，界面上画成一条 24 小时横轴 + 两个可拖动的点，点之间是暗色（休息时段）。但**存的是两个字符串**，不是时间戳——因为 `life-rhythm` 的 `pattern` 是 `^([01]\d|2[0-3]):[0-5]\d$`，界面必须产出符合这个正则的值。两个点相连时若起始晚于结束（跨零点，如 23:30–07:00），横轴上画成两段而不是一段。

**五种控件语言**（由 `FieldSpec.kind` 决定，不另立映射）：

| kind | 控件 | 规则 | 真实数量 |
| --- | --- | --- | --- |
| `number` | 滑杆 | 有 `min/max` 时用滑杆；范围 > 1000 或需要精确输入时用数字框 + 步进 | 576 |
| `boolean` | 开关 | 右侧必须显示生效范围（立即 / 重启后） | 359 |
| `enum` | 分段控件 | 候选 ≤ 4 用分段，> 4 用下拉 | 53 |
| `string` | 输入框 | 有 `pattern` 时实时校验并给出中文提示 | 126（其中 35 个带 `pattern`） |
| `json` | 等宽文本域 | 实时校验，错误定位到行 | 54 |

**`secret` 在本项目里是 0**：全仓 1168 个字段没有一个标 `secret: true`。`llm-gateway` 的注释写了原因——`credentialRef` 存的是**环境变量名**（引用），不是密钥值，所以连 `secret` 都不该出现。**界面不要为"密码框"预留位置**，那会诱导后来的插件把密钥塞进配置文件（违反手册 §6 禁令 6）。密钥只走环境变量与凭据域。

**`advancedOnly` 的真实比例是 48%**（561 / 1168），不是少数例外。这意味着模块层打开后**近一半字段默认不显示**，必须在段标题右侧给一个「高级」开关，且该开关的开启状态**按段记忆**，不全局。若做成一个全局开关，用户为看 A 段的两个高级项而打开它，B 段会一次涌出三十个字段。

**无段字段**（有 `FIELD_SPECS` 但没有 `CONFIG_SECTION`）：目前只有 `ondra-memory-intake` 一处，5 个字段。模块层把它渲染成一段，段标题用插件目录名，标题右侧加一个 12px `ink-3` 标记「未注册配置段」。**不隐藏它**——字段存在就能调，只是它的值不参与四层合并与来源追溯，界面必须让人知道这一点，否则用户会以为"改了没生效"是 bug。

**四档预设：机制已存在，但目前没有插件用它**。`ondra-config-schema` 的 `SectionDecl` 定义了可选的 `presets`（每档一组字段增补值），并有 `presetOf(id, preset)` 取某档的增补值；`PresetName` 的类型就是 `'off' | 'slow' | 'standard' | 'fast'`，注释说明「四档只影响一段配置的成组取值，由调用方放进 `bundle` 层」。

**实测：声明了 `presets` 的插件数为 0。** 因此：

- 界面**现在不能**做"一键切到简单模式"——那需要每段都声明 `presets`，而这段工作还没做。
- 已有一个真实可用的四档：`proactive-quota.profile`（`slow / standard / fast`，第四档「关闭」由 `enable` 表达，插件注释专门解释了为什么不给"关闭"单独一个档位值）。**场景层第 2 项直接用它**，不自己造四档。
- 落地顺序：先让插件声明 `presets`，界面再读。**不要反过来**——界面先做四档，插件没声明，用户点了没反应。

**每项统一的元数据行**（12px `--static-ink-3`）：
`当前值 · 默认值 · 来源插件 · 是否已改`

来源插件必须显示**段 id 对应到哪个插件目录**，而不是段名。因为 122 个段里有 12 个的段 id 与目录名不同（去掉了 `ondra-` 前缀且有 3 个做了改写：`ondra-adapter-dingtalk` → `dingtalk`、`ondra-beichen-api` → `beichen`、`ondra-dev-rebrand` → `rebrand`）。用户报问题时说的是目录名，配置里存的是段 id，两者要在界面上对得上。

**预演**：能预演的项在控件下方放一个「按当前参数预演」区块，显示一条示例消息。参数变化后 300ms 防抖重算，文字即时改写。这是"参数可感知"的唯一手段。**不要给每一项都加这个区块**——下面这张表列了哪 6 项能演、怎么演。

**预演只对 6 项成立**，必须逐项判断，不能一律给：

| 可预演 | 怎么演 |
| --- | --- |
| 4 说话的浓度 | 同一句话在 0 / 50 / 100 三个取值下的写法对照 |
| 5 一次说多少 | 把一条长回复按 `max-chars-per-message` 切成几条，直接显示条数 |
| 6 打字的节奏 | 一条 40 字的消息按 `chars-per-second` 算出的总时长（"这条会显示约 7 秒"） |
| 7 上下文长度 | 显示"她会记得最近 10 轮对话" |
| 1 她记得多深 | 显示"30 天没提到的记忆会沉底，仍可翻到" |
| 2 她多主动 | 显示"大约每天 3 条"（由 `profile` 映射，不显示英文枚举名） |

**其余 7 项不给预演**（3 / 8 / 9 / 10 / 11 / 12 / 13）：它们是开关、时间、审批策略，预演不出有意义的文本。硬给一个"预演"区块只会显示一句废话。

**预演区块的交互细则**（这四条不做就等于没做预演）：

| 场景 | 行为 |
| --- | --- |
| 首次显示 | 不自动展开。用户第一次**拖动**控件后才展开，高度从 0 到内容高度，`--motion-base` + fluid。用户没动之前不占空间 |
| 防抖中的状态 | 300ms 内不显示加载态。超过 300ms 才在区块右侧给一个 12px `ink-3`「重算中」，**不换骨架屏**——换个骨架再换回来，比等 300ms 更晃眼 |
| 算不出来 | 显示「按当前参数算不出示例」+ 一句原因，**不留空白**。例如 `chars-per-second` 被拉到 20 时，一条 40 字消息只要 2 秒，预演仍可显示；而 `max-turns` 为 1 时没有"多轮"可演，就明说 |
| 预演与真实不同 | 预演用的是**本地规则**（字数切分、字速乘法），不调模型。因此它只能演"形状"，不能演"她会说什么"。区块底部固定一行 12px `ink-3`「示例只演参数的影响，不是她会说的话」 |

**为什么这条免责声明是必须的**：预演区块里有一句文字，用户会默认它是"她会说的"。一旦真实回复不同，用户会认为预演在骗他。写清"只演参数的影响"，预演就从"承诺"变成"量尺"。

**改动记录**：底部固定条显示「本次改动 N 项 · 来自 {插件}」，右侧「撤销」按钮回退到本次打开前的状态。撤销粒度是"一次打开设置"，不是"每一步"。

**不属于场景层的三类配置**（说明为什么它们不进上面那张表）：

| 类别 | 例子 | 为什么不能做成场景项 | 应该在哪 |
| --- | --- | --- | --- |
| 列表编辑器 | `llm-gateway.sources`（`json`）、`gui-agent.appAllowList`、各 adapter 的 `allowSenderIds` | 值是数组，没有"滑杆拉到哪"这种表达 | 模块层的专用列表编辑器（增删行、拖动排序） |
| 凭据引用 | `asr.credentialRef`、`vision.credentialRef`、`llm-gateway` 的 `sources[].credentialRef` | 存的是环境变量名，改它等于改部署，不是改偏好 | 偏好设置·连接，且只允许从已有环境变量里选，不允许现场输入密钥 |
| 高危开关 | `adapter-wechat-personal.enable`（插件标题里就写着「高危」）、`gui-agent.enable` | 打开它会产生用户在别处无法撤回的后果 | 必须走 §7 的 Sheet 确认，并附一句"这会做什么" |

这三类合计覆盖了场景层之外最常被问"这个在哪改"的配置。**界面上要能搜到它们**——搜索直接跳到模块层对应段并高亮该字段，不停在场景层。

### 5.14 Onboarding（初始引导）

| 属性 | 值 |
| --- | --- |
| 形态 | 覆盖层，`z-index: 70`，遮罩 `rgba(28,31,29,0.18)` |
| 卡片 | 480 × 360，圆角 16，居中 |

**四步内容**：

1. **欢迎**：logo、项目名、「一个安静的对话伙伴」、双语 slogan。
2. **她是谁**：人格选择（出厂鲸鲸 / 导入人设包）。说明人格是虚构角色设定。
3. **模型**：三种来源（在线接口 / 本地大模型 / 免费模型）。此步可跳过，跳过时使用免费模型并提示。
4. **隐私**：按宿主位置分两种措辞——**不能说错**。

| 宿主位置 | 文案 | 附按钮 |
| --- | --- | --- |
| 本地（电脑三端） | 「对话只存在这台电脑上，没有账号、没有上传」 | 「查看数据目录」 |
| 远程（移动端、Web） | 「对话存在你连接的那台电脑上，没有经过我们的服务器」 | 「查看宿主地址」 |

**为什么必须分两种**：移动端连的是远程宿主（§10.0），此时说"只存在这台电脑上"是不成立的——对话存在另一台机器上。同一条文案搬到手机上就是假话。

引导只出现一次，状态存 `localStorage['ondra.onboarded']`。不允许在引导中强制填写密钥。

**引导的交互细则**：

| 场景 | 行为 |
| --- | --- |
| 能否中途关闭 | 能。`Esc` 或点遮罩等同"跳过"，且记住已完成的步骤——下次打开从第 3 步继续，不从头再来 |
| 跳过第 3 步（模型） | 使用免费模型，并在第 4 步顶部加一行 12px `ink-3`「已为你选好免费模型，随时可在设置里更换」 |

| 已登录/已有配置 | 不显示引导，直接进首页（判断依据是配置文件存在，不是 `localStorage`） |

### 5.15 桌宠联动

| --- | --- |

## 6. 功能联动矩阵

### 6.0 这一章的前提：界面不绑定插件

**插件不是界面的固定格子。** 134 个插件装进同一个 Cordis 宿主，宿主把每个插件对外提供的能力交给 dsh 内核，内核把它当作一个**工具**暴露给大模型。模型自己决定调谁、按什么顺序、传什么参数。

这带来一个必须先立住的契约：

| 谁 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 插件 | 声明自己的能力（工具名、参数、返回）；声明自己的配置项（`FIELD_SPECS`） | **不画界面**，不指定自己出现在哪 |
| 宿主 | 装载插件、四层配置合并、把能力清单交出去 | 不解释业务 |
| dsh 内核 | 把能力包装成工具交给模型；把 `event.*` 推给界面 | 不决定界面布局 |
| 界面 | 通用地渲染"有哪些工具、此刻在调哪个、结果是什么"；**按 `FIELD_SPECS` 自动生成设置** | **不写死任何插件名** |

**因此界面只有两件事与插件相关**：

1. **工具级**：一组与插件无关的通用组件——工具卡（正在调用 / 成功 / 失败）、能力清单（有哪些工具可用）、参数回显（模型传了什么）。加一个新插件，这些组件**一行都不用改**。
2. **配置级**：设置页不手写 1168 项，而是读每个插件 `FIELD_SPECS` 里的 `kind / default / min / max / values / pattern / advancedOnly / doc`，用 5 个控件渲染器（开关、数字、文本、枚举、JSON）自动生成。加一个新插件，设置页**自动多出它的那一段**。

**这条契约解决了什么**：原方案里"1168 项设置"是一个要手工对接的清单，插件一改字段界面就要跟着改。改成"插件声明、界面生成"之后，界面与插件的数量彻底解耦——插件从 134 涨到 200，设置在代码里不会多一行。**这不是设想，是已经成立的**：134 个插件里有 123 个带 `settings.ts`，合计 1168 个字段，这些数字全部由插件侧决定，界面侧一行都不用改。

**唯一需要人判断的地方**：某个插件的配置该不该出现在「场景层」（少数几个用户真的会调的），仍要人工挑。但这只是**挑出 13 项做常用入口**，不是把 1168 项都摆出来——其余的全在自动生成的模块层与原始层里。

### 6.1 一个必须避开的命名冲突

**「L0–L9」这个词在项目里已经有确定含义**，指插件的系统层级（§6.2）。早期本文件曾用 `L0/L1/L2/L3` 表示"露出层级"，与插件层级用了同一套编号却含义完全不同——**这是必须消灭的冲突**。

本文件自此统一：

| 术语 | 指什么 | 取值 |
| --- | --- | --- |
| **系统层级** | 插件在系统中的位置，来自 README 首行 | `L0`–`L9` |
| **露出形态** | 界面以什么形式承载它 | 下表四个中文名，**不用编号** |

| 露出形态 | 含义 | 典型数量 |
| --- | --- | --- |
| **常驻** | 主界面一直可见（时间轴、双脊、输入区） | 16 个插件贡献 |
| **常用** | 场景层挑出来做常用入口 | 5 项 |
| **可查** | 检查器读数，或设置里可调（自动生成） | 多数插件 |
| **不露出** | 无专属位置，功能照常可用 | 其余 |

"照顾到每个功能"不等于"每个插件都上界面"。一个插件若在界面上没有可信的信息可显示，强行露出只会制造噪声。

**「不露出」不等于不可用**：这类插件**功能完全可用**，模型随时能调；只是界面不给它专属的可见位置。它的配置项同样会被自动生成进设置页（§6.6）。

### 6.2 真实分类：L0–L9 十层，不是自定义的域

**这一节的数字全部来自插件自身，不是设计阶段的设想。** 每个插件的 `README.md` 首行都带一行元信息，格式固定：

```
> O-041 · L4 节奏与拟人（第 7 组第 4 项）· 档位〔研〕 · 服务键 `ondra-breath`
```

四个字段各有含义，界面必须按它们组织，不能另造一套：

| 字段 | 含义 | 界面用途 |
| --- | --- | --- |
| `O-041` | 手册编号，稳定不变，用于跨文档引用 | 诊断页与日志里显示，便于报问题 |
| `L4` | **层级 0–9**，表示该插件在系统中的位置 | 决定它出现在界面的哪一类位置 |
| `第 7 组第 4 项` | 所属功能组与组内序号 | 设置页分组、能力清单分组 |
| `〔研〕/〔复〕/〔薄〕` | 档位：自研 / 复用 / 薄封装 | 只用于诊断展示，不影响界面 |

**插件总数是 134，不是 137。** 目录下有 137 个文件夹，但 `ondra-core` 是清单本身、`desktop-bridge` 与 `dsh-client` 是壳与内核的桥接，三者不在 `members` 数组里。真正的可装载插件由 `cordis-host/plugins/ondra-core/src/index.ts` 的 `MIGRATED_PLUGIN_COUNT` 定义，值为 **134**。

**L 层级实测分布**（截至本文档修订时，逐条统计自各插件 README）：

| 层级 | 含义 | 实测数量 | 界面对应 |
| --- | --- | --- | --- |
| L0 | 基座（时钟、配置、端口、路径） | 5 | 诊断页 |
| L1 | 存储（SQLite / JSON / 迁移） | 4 | 诊断页 |
| L2 | 情绪域 | 24 | 检查器·此刻、Spine 水位 |
| L3 | 单例层 | 1 | 视具体插件 |
| L4 | 表达 / 节奏 / 人格（含生活感：`ondra-diary`、`ondra-live`） | 16 | 语气、呼吸、动态、人格工坊 |
| L5 | 通道 | 8 | 设置·通道 |
| L6 | 端侧（ADB / 浏览器 / 设备） | 8 | 设置·设备 |
| L7 | 系统与交付 | 9 | 设置·诊断 |
| L8 | — | 0（本版无） | — |
| L9 | 扩展池 / 运行时治理（23 个，是最大的一层） | 23 | 抽屉·扩展 |
| **未标注** | 元信息无 `Lx` 的 34 个 + 无 README 的 1 个 | **35** | **待补，见下方说明** |

**35 个未标注是真实缺口，不掩饰。** 其中 34 个有 README，但元信息行里没有 `Lx`（如 `> O-127 · 〔复〕复用 · 手册 1.5 · P1 · 批次 B9（多模态）`，其中的 1.5 指项目内部的插件手册，与本文件的第 1 章无关）；剩 1 个（`ondra-memory-intake`）**连 README 都没有**，只能从 `package.json` 的 `description` 认出它是什么。界面处理方式：

1. **不阻塞加载**。缺 L 层级只影响"归到哪一组显示"，不影响功能可用。
2. **归入「未分组」**。设置页与能力清单里单列一个「未分组」区，排在最后。
3. **补标注是插件侧的事**。文档不替它们猜层级——猜错会让诊断页显示错误的归类，比"未分组"更糟。

**这张表会随插件演进变化**，因此不写死在代码里，而是运行时从插件的包元信息读取。界面只提供 10 个层级容器 + 1 个未分组容器，来什么放什么。

### 6.3 界面如何承载这十层

层级决定「放在哪」，不决定「画成什么」。同一个层级里的 24 个 L2 插件，界面不为每个都做面板——它们通过工具调用与检查器读数体现存在。

| 层级 | 界面承载方式 | 是否需要专门组件 |
| --- | --- | --- |
| L0 / L1 | 只在诊断页出现，设置自动生成 | 否 |
| L2 | 情绪结算结果进检查器「此刻」，配置自动生成 | 否（复用检查器） |
| L3 | 视插件而定 | 视插件而定 |
| L4 | 语气与动态影响消息渲染，配置自动生成 | 否 |
| L5 | 设置·通道，每个适配器一行状态灯 | 否（一行通用表单） |
| L6 | 设置·设备，同样自动生成 | 否 |
| L7 | 设置·诊断与关于 | 否 |
| L9 · 扩展池子类（`absence` / `theater` / `cocreate` / `first-meet` / `ritual` / `sandbox` 等） | 抽屉·扩展，列出可用扩展与其开关 | 否 |
| L9 · 运行时治理子类（`crisis` / `redteam` / `memory-heal` / `trust-dashboard` 等） | **不进抽屉**，只在设置·诊断与安全区出现。它们是护栏，不是功能入口 | 否 |
| 未标注 | 设置·未分组，附一行提示「这些插件未声明层级」 | 否 |

**结论：十层不需要十个组件。** 界面提供的是 5 类容器——诊断清单、设置段落、通道行、能力清单、检查器读数——每类都能容纳任意层级的任意数量插件。这正是 §6.0 那条契约的具体形态。

**L9 内部必须再分一次类**，因为它是 23 个插件、最大的一层，而"扩展池"这个名字会误导人。两类的区别不是代码层面的，是**用户是否需要主动去碰它**：

| 子类 | 判断依据 | 界面位置 | 数量级 |
| --- | --- | --- | --- |
| 扩展池 | 用户主动开启、有独立玩法（剧场、共创、仪式、初遇、沙盒） | 抽屉·扩展，可开关 | 6 个 |
| 运行时治理 | 默认开启、无用户操作、只在出问题时起效（危机识别、红队自检、记忆修复、信任面板、遗忘权、时间胶囊） | 设置·诊断（只读状态）与设置·安全（可关） | 17 个 |

这条区分只能靠插件元信息里的描述判断，**不能靠名字猜**。落地时不要写死清单——治理类的判定依据是「默认开启 + 无用户操作入口」，插件新增时按这条规则自动归位。若判不出来，归「扩展池」并允许用户关闭，比藏起来安全。


### 6.4 关键联动细则

**A. 启动与故障**
`startup-check` 失败 → 全窗故障页（替换主列内容，保留双脊），显示「没能连接上后台服务」+ 原因 + 「重试」+「查看日志」。`install-doctor` 检出缺失组件 → Toast + 偏好设置「关于」页红点。

**B. 模型切换**
Composer 的模型名可点击 → 浮层菜单列出模型 → 选中后 300ms 内生效，模型名文字做一次 900ms 的 `ink-1 → ink-2 → ink-1` 呼吸，表示已切换。切换失败 → Toast（错误态）+ 名字回滚。

**C. 情绪**
`emotion-core` 每次结算后推送 `{mood, energy, tension}` → Spine 水位 240ms 过渡 → 若变化幅度 > 0.15，检查器「此刻」的分组标题旁出现 8px 沙色圆点，3 秒后消失。用户点击检查器后圆点清除。

**D. 记忆写入**
`memory-extract` 写入一条新记忆 → Spine 的「记忆 N」数字做一次 600ms 的计数递增 → 若当前对话与此条相关，下一条助手消息下挂 MemoryChip。

**E. 主动开口**
`proactive-gate` 允许 → `proactive-reason` 给出判据 → 消息渲染时在正文下 8px 处渲染 11px 一行：`她主动开口 · {判据摘要}`，行首 2px 沙色点。该行右侧 3 秒内显示「这次不用」，点击后：本条消息淡出（180ms）、`proactive-quota` 记录一次拒绝、当天剩余预算减一。

**F. 通道**
任一 `adapter-*` 断线 → 偏好设置「通道」页对应行状态灯转灰 + 主界面不提示（通道故障不属于当前对话，弹到主界面属于噪声）。连续断线 3 次 → Toast 一次。

**G. 语音**
点击 Composer 的语音键 → `asr` 开始 → 键变为录音态（teal 实心 + 呼吸）→ 实时转写进输入框 → 再次点击停止。`tts` 开启时，助手消息右侧出现 16px 播放图标，悬停出现「朗读」。

**H. 危机**
`crisis` 命中 → 在当前消息下插入一张 inline 卡片（宽 588，背景 `--static-paper-1`，圆角 8），内容为求助资源。此卡片不可关闭，不进入消息历史，不做任何统计。

### 6.5 改一个设置，界面必须回应

这是"可交互设置项"与"可视状态"的接合点。用户拖了一根滑杆，如果界面上什么也没变，他会怀疑有没有生效。

| 设置类型 | 生效时机 | 界面必须有的回应 | 延迟上限 |
| --- | --- | --- | --- |
| 外观（主题/字号/圆角） | **即时** | 立即重绘，无过渡（避免"渐变到新主题"的怪感） | 0 |
| 影响下一条回复（模型/温度/人设） | 下一次发送 | Composer 旁的模型名原地闪一次 `ink-1→ink-2→ink-1`（900ms） | 发送时 |
| 影响水位（情绪基线/节律） | 下一次结算 | Spine 水位 240ms 过渡到新位置 | 一次结算周期 |
| 影响打扰（主动说话/免打扰） | 立即 | 设置页该行右侧出现「已生效」灰字，5 秒后淡出 | 0 |
| 影响通道（微信/QQ 开关） | 连接需时间 | 该行状态灯转「连接中」（呼吸），成功后转实心 | 连接完成 |
| 需要重启（极少数） | 重启后 | 该行下方出现一行「下次启动生效」+「立即重启」 | 0 |

**「立即重启」不是按钮，是链接样式**：重启宿主会丢当前未保存的生成，做成主按钮会诱使用户误点。

**滑杆的预演**：§1.1 承诺「参数可即时预演」。温度、字数上限这类抽象参数无法预演，能预演的是**有可见结果**的参数：

| 参数 | 预演方式 |
| --- | --- |
| 字号 | 拖动的当下，下方示例句按新字号重排 |
| 圆角 | 示例卡片角部实时变化 |
| 行距 | 示例段落实时重排 |
| 打字速度（落字段） | 示例句按新速度重放一次 |
| 音量 | 播放一声 200ms 的提示音 |
| 其余抽象参数 | **不预演**，改为在滑杆下方显示一行「当前：0.7 · 偏高」的文字解释 |

**不给抽象参数编造预演**是 §1.2 第 3 条（不做假装）的直接应用。温度调到 0.7 无法"演"出来，硬演就是骗人。

### 6.6 完全通用：加一个插件，界面要改几行

这是本章最重要的一条验收：**新增一个插件，界面代码的改动量必须是零**。

先看现状。插件 `ondra-breath` 的 `settings.ts` 里已经有完整的字段声明：

```ts
export const FIELD_SPECS = Object.freeze({
  enable:      { kind: 'boolean', default: true,  doc: '总开关…' },
  dailyCap:    { kind: 'number',  default: 2, min: 0, max: 2, doc: '单日上限…' },
  extraActions:{ kind: 'json',    doc: '追加的动作，最多 11 条' },
  // …
})
```

`kind` 决定用哪个渲染器，`doc` 直接就是界面上的说明文字，`min/max` 直接约束滑杆。**插件作者写配置时，界面就已经写好了。**

**五个渲染器覆盖全部情况**：

| `kind` | 渲染 | 附带 |
| --- | --- | --- |
| `boolean` | 开关（§12.16） | — |
| `number` | 滑杆；有 `min/max` 时显示刻度两端 | 下方显示当前值 + `doc` |
| `string` | 单行输入框；超过 60 字改多行 | `doc` 作占位符或下方说明 |
| `enum` | 分段控件（≤ 4 项）或下拉（> 4 项） | 选中项变化即时生效 |
| `json` | 折叠的代码块 + 「编辑」按钮 | 校验失败时行内红字，不弹窗 |

**三个必须由界面自己补的字段**（`FIELD_SPECS` 里没有，也不该由插件承担）：

| 字段 | 谁补 | 为什么 |
| --- | --- | --- |
| 中文标签 | 界面按 `KEY_PAIRS` 派生的键名转写，缺失时显示原始键名 | 插件不该管界面语言 |
| 分组归属 | 界面按插件所在域归入 12 组之一 | §6.2 的表已经定好 |
| 是否需要重启 | 界面按 `kind === 'string'` 且键名含 `path`/`dir` 猜测，猜测失败一律按"即时生效" | 宁可立即生效后发现无效，也不要提示重启但其实不需要 |

**通用性验证的三步法**（每次加插件都跑一遍）：

1. 装上新插件，**不改任何界面代码**，重启。
2. 设置页是否自动出现该插件的一段？字段数、类型、默认值、`doc` 是否与 `FIELD_SPECS` 一致？
3. 让模型调一次它的工具，工具卡是否正常显示「调用 → 结果」？参数回显是否是模型真实传的值？

三步全过，说明界面确实是通用的。任何一步要改代码，就说明界面里某个地方写死了插件名——那是缺陷，不是"正常适配"。

**反例（必须避免的写法）**：

| 错误写法 | 后果 |
| --- | --- |
| `if (plugin === 'ondra-breath') { … }` | 每加一个插件都要改界面 |
| 手写一份 1168 行的设置清单 | 插件改字段时界面不同步，出现"设置项的键不存在" |
| 为某个插件单独做一个面板 | 该面板迟早与插件实现漂移 |
| 按插件名决定工具卡样式 | 新插件的工具卡没有样式 |

**唯一允许存在的插件专属组件**是 §5 里已登记的 15 个（Rail、Spine、Timeline 等）——它们属于**界面骨架**，不是插件面板。骨架之外的插件专属代码一律不允许。

### 6.7 没有专属露出的插件，用户怎么碰到

L0 只是"没有专属露出位置"，不是"不可见"。四条途径让用户随时能查到它确实在工作：

| 途径 | 位置 | 用户能做什么 |
| --- | --- | --- |
| 工具清单 | 检查器·能力 | 看到模型当前可调的全部工具（由握手 `methods` 与实际加载的插件共同决定），按域分组 |
| 诊断页清单 | 设置·诊断·全部插件 | 每行显示名称、域、状态、最近一次调用时间 |
| 模块层参数 | 设置·模块层（自动生成） | 按域筛选，直接改值 |
| 日志检索 | 设置·诊断·日志 | 按插件名筛选，看它实际做了什么 |
| 停用开关 | 诊断页每行的开关 | 停用后该插件不再被加载，界面对应能力灰显并注明 |

**为什么要有工具清单**：模型能调哪些工具是**动态的**（取决于装了哪些插件、握手返回了什么）。用户问"你为什么不能帮我查天气"，答案应该是"看一眼能力清单，天气插件没装"——而不是一句含糊的道歉。

**停用插件的界面义务**：停用某插件后，自动生成的那一段设置必须灰显并注明「插件已停用」。不允许让它看起来还能调——那是最容易让人失去信任的一类缺陷。

### 6.8 自检的五个问法

登记表写完不等于做对了。五个问法，每个都要有肯定答案：

| # | 问法 | 不合格的表现 |
| --- | --- | --- |
| 1 | **反查**：界面上任一可见元素，能否说出它由哪个插件或内核事件驱动？ | 有说不出来源的元素 → 要么删，要么补登记 |
| 2 | **正查**：附录 A 里任一标为「常驻」的插件，能否在界面指出落点？ | 指不出 → 露出形态标错了 |
| 3 | **断链**：把任一插件停用，界面是否仍能启动，且**明确告知**哪部分不可用？ | 启动失败或静默失效 → 耦合没断开 |
| 4 | **通用**：装一个新插件且不改界面代码，设置与工具卡是否自动出现？ | 需要改代码 → 界面里写死了插件名（§6.6） |
| 5 | **诚实**：附录 A 里的层级与数量，是否与各插件 README 首行逐条一致？ | 对不上 → 表格在臆造，比没有更糟 |

**第 5 问是这份文档特有的要求**。本章与附录 A 的数字全部来自代码与插件 README，一旦有人手工改动而不同步代码，文档就会变成"看起来专业但全错"的东西——这比留空危害更大。

## 7. 弹窗与提醒

这一章决定"她什么时候可以打断你"。陪伴类应用最容易做坏的地方就是打扰——每多一次无谓弹窗，用户就多一次想关掉通知的念头。

### 7.1 四级打扰

| 级别 | 形态 | 使用条件 | 每日上限 | 可关闭 |
| --- | --- | --- | --- | --- |
| 0 | 无 | 默认。一切后台状态变化 | — | — |
| 1 | 内联（消息流内的错误条 / 危机卡片） | 与当前对话直接相关 | 不限 | 随对话滚走 |
| 2 | Toast | 用户刚执行的操作失败了 | 不限（用户主动触发） | 4 秒自动消失 |
| 3 | Sheet | 需要用户确认后才继续 | 不限（用户主动触发） | `Esc` |
| 4 | Dialog | 不可逆操作 | 不限（用户主动触发） | `Esc`，但**不点确认不执行** |

**核心禁令**：由后台事件（通道断线、模型降级、插件自检、记忆写入失败）**不得**直接触发 2 级以上打扰。后台事件一律进偏好设置的状态页，最多在 Rail 齿轮上加一个 4px 圆点。

**为什么这条不许破例**：用户打开这个应用是为了和她说说话，不是为了知道你后台哪个插件崩了。后台的事后台解决，用户问起再答。

### 7.2 判断用哪一级：四个问题

按顺序问，第一个"是"就定级：

```
1. 会丢数据或不可撤销吗？        → 是：4 级 Dialog
2. 不确认就无法继续吗？          → 是：3 级 Sheet
3. 是用户刚做的动作失败了吗？    → 是：2 级 Toast
4. 与当前这条对话直接相关吗？    → 是：1 级内联
                                 → 否：0 级，不打扰
```

**反例**（常见误判）：

| 情况 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 通道（微信）断线 | 弹 Dialog「连接已断开」 | 0 级。设置·通道页标红，Rail 加圆点 |
| 模型降级到备用 | 弹 Toast「已切换备用模型」 | 0 级。检查器状态行显示 |
| 记忆写入失败 | 弹 Dialog 要求重试 | 1 级。在消息下方加一行灰字「这条没记住」 |
| 宿主重启完成 | 弹 Toast「已重新连接」 | 0 级。状态行颜色由灰变实即可 |
| 插件自检发现异常 | 弹 Sheet 列出问题 | 0 级。齿轮圆点，点开才看 |

### 7.3 各形态的规格

**Toast（2 级）**

**尺寸与外观以 §5.10 为准，本节不重复列数值**——两处各写一份，改一处必然漏另一处。本节只补 §5.10 没写的打扰维度：

| 项 | 值 | §5.10 是否有 |
| --- | --- | --- |
| 位置 | 顶部居中，`y = 56` | 有 |
| 最大宽 | 420 | 有 |
| 高 | 40（单行） | 有 |
| 圆角 | 8 | 有 |
| 出现 / 消失 | 180ms / 120ms | 有 |
| 同时最多 | 1 个，新的替换旧的 | 有 |
| 悬停暂停计时 | **悬停时不倒计时** | 本节新增 |
| 操作 | 最多一个文字按钮（「再试一次」），不带图标 | 本节新增 |

**为什么不堆叠**：堆叠的 Toast 会互相遮挡，用户读不完最上面那条就消失了。后到的替换先到的，符合"最新的更相关"。

**Sheet（3 级）**

**桌面尺寸以 §5.12 为准：宽 420、下方圆角 16、顶部贴边**（不是居中弹窗）。这一点最容易做错，因为"Sheet"这个名字在别处常指居中面板。本节只补打扰维度：

| 项 | 值 | §5.12 是否有 |
| --- | --- | --- |
| 桌面 | 宽 420，顶部贴边，下方圆角 16 | 有 |
| 手机 | 从底部推入，占满宽度，顶部圆角 16，最大高 90vh | 本节新增（§10 有，此处汇总） |
| 进场 / 退场 | 180ms fluid / 180ms fluid-reverse | 有 |
| 遮罩 | 点击遮罩 = 取消 | 有 |
| 关闭 | `Esc` / 遮罩 / 取消按钮 / 完成按钮 | 有 |
| 焦点 | 锁在 Sheet 内，默认落在第一个**非破坏性**按钮 | 本节新增 |
| 滚动 | Sheet 内部滚动，遮罩不动 | 本节新增 |
| 最大高 | 70vh（桌面）/ 90vh（手机） | 有 |

**Dialog（4 级）**

Dialog 与 Sheet 的唯一区别是**必须明确选择**：点遮罩不关闭，`Esc` 关闭等同取消，破坏性按钮需二次确认（手写或长按 800ms）。

只用于三件事：删除对话、删除全部记忆、清除本地数据。**每多一件，Dialog 的严肃性就少一分。**

| 项 | 值 |
| --- | --- |
| 宽 | 400 |
| 标题 | 动词短语，如「删除这段对话」 |
| 正文 | 一句话说明后果 + 一句"无法撤销" |
| 按钮 | 左「取消」（默认焦点）、右「删除」（红色，见 §4.1 的 `red-600`） |
| 二次确认 | 破坏性按钮按下后变为「再按一次确认」，3 秒内未再按则复原 |

**为什么用"再按一次"而不是输入文字**：输入「DELETE」是网页后台的做法，用在陪伴应用里像审问。连按两次已经足够防误触——误触者不会连按两次。

### 7.4 主动消息的打扰预算

她可以主动找你，但有预算。预算是硬的，不是"尽量"。

| 项 | 规则 |
| --- | --- |
| 每日上限 | 场景层「主动说话」决定（0 / 2 / 4 / 8 条） |
| 冷却 | 两条之间至少 90 分钟 |
| 免打扰 | 场景层「作息」的睡眠区间内不发 |
| 可撤回 | 每条主动消息下方 3 秒内可点「这次不用」 |
| 累计拒绝 | 连续拒绝 3 次 → 当日停止主动消息，Spine 显示「安静」 |
| 应用未开 | 走系统通知，不受 §7.1 约束（系统通知有自己的开关） |
| 应用已开但不在前台 | **不发系统通知**，只在 Rail 加圆点 |

**"已开但不在前台"这条容易被忽略**：用户在浏览器里查东西，应用在后台。这时弹系统通知是打扰——她已经在屏幕上了，用户回来就能看到。只有当应用完全关闭时才值得用系统通知。

### 7.5 打扰的自我约束清单

落地前逐条自查，任何一条不满足就不许上线：

- [ ] 除用户主动操作外，没有任何 2 级以上打扰
- [ ] 首次启动的引导是唯一一次"连续多步"打扰
- [ ] 所有 Toast 都能被忽略，忽略后功能仍可用
- [ ] 没有任何"每秒刷新"的状态提示（如常驻的"正在同步…"）
- [ ] 断网、断宿主、插件异常，全部静默降级到设置页
- [ ] 主动消息的拒绝是**一次点击**，不需要进设置
- [ ] 没有任何"升级到 Pro"一类营销弹窗（本应用没有此机制）
- [ ] 系统通知权限只在用户开启"主动消息"时才请求，不在首启请求

### 7.6 文案规则

- 按钮用动词，不用"确定/取消"以外的抽象词。危险操作的按钮必须写明后果（「删除这条记忆」而非「确定」）。
- 错误信息三段式：**发生了什么 · 为什么 · 下一步**。例：「没能切换模型 · 接口返回 401 · 检查 API Key 后重试」。
- 不使用感叹号。不使用"哦""啦"一类语气词（人设语气由模型生成，界面文案保持中性）。
- 标题不超过 12 字，正文不超过 40 字。超了就不是"提醒"，是"说明"，该进设置页。
- 不用"请"。中文里"请"在错误提示中显得生硬（「请检查网络」→「检查一下网络」）。

### 7.7 提醒的分级文案对照

同一个事件在不同级别下措辞不同，不能复用：

| 事件 | 1 级内联 | 2 级 Toast | 3 级 Sheet |
| --- | --- | --- | --- |
| 消息没发出去 | 「未送达 · 点击重发」 | 「没能发出 · 网络断了」 | — |
| 记忆没记住 | 「这条没记住」 | — | — |
| 模型不可用 | 「当前模型没响应」 | 「没能切换 · 接口 401」 | 「这个模型连不上 · 密钥可能失效 · 去设置里换一个」 |
| 附件太大 | 「文件太大，没传上去」 | 「超过 20 MB」 | — |

**规律**：级别越高，信息越完整；级别越低，越要短。1 级内联在消息流里，用户扫一眼就要懂，所以只给状态和恢复动作；3 级 Sheet 有整块空间，才展开原因。

## 8. 全局动效

### 8.0 三条元规则

动效最容易失控的地方不是"做得不好看"，而是"每个人各写一个 200ms"。因此在列举具体动效之前，先定三条不可协商的元规则：

1. **时长只有五档**。全部动效的时长必须取自下表，出现第六个数值即为缺陷。
2. **曲线只有三条 CSS 曲线加一个物理弹簧**（fluid / fluid-reverse / breathe / spring），多一条都不加。
3. **一切动效必须可中断**。中断时从**当前值**继续，不回到起点重播。这条最容易被跳过，也最影响手感——用户在抽屉展开到一半时再点一次，如果动画先弹回 0 再收起，那种顿挫就是廉价感的直接来源。

### 8.1 时长标尺

| 令牌 | 值 | 用途 | 为什么是这个值 |
| --- | --- | --- | --- |
| `--motion-0` | `0ms` | 降级态、跟随系统切换主题 | 不是"没有动效"，是"明确要求瞬时" |
| `--motion-fast` | `120ms` | 悬停、按下、菜单、焦点环、复制按钮 | 低于 100ms 像没动，高于 150ms 会"黏手" |
| `--motion-base` | `180ms` | 抽屉与检查器展开、Sheet 进场、消息入场 | 位移类动效的舒适中位 |
| `--motion-slow` | `240ms` | 水位变化、Toast 进场、收起（反向） | 有物理量感的属性需要稍长 |
| `--motion-emphasis` | `900ms` | 回声（上一句淡出） | 唯一的长动效，且只改文字色，不位移 |
| `--motion-loop` | `3000–7000ms` | 呼吸（完整一轮周期，不是单程） | 3s ≈ 20 次/分（急促），7s ≈ 8.6 次/分（安睡），与真实呼吸频率对齐 |

**五档是硬约束，但有两类数值不受它管**。混淆这两类，要么把标尺写死到不可用，要么让标尺形同虚设：

| 类别 | 是否受五档约束 | 文档里的例子 |
| --- | --- | --- |
| **过渡时长**（CSS `transition` / `animation-duration`） | **受约束**。出现第六个过渡时长即为缺陷 | 抽屉 180ms、Toast 退场 120ms、水位 240ms |
| **停留时长**（元素可见多久后自己消失） | 不受约束。它不是"动效快慢"，是"给人多久看" | Toast 成功停留 2.4s、错误停留 4.0s、滚动条停止滚动 800ms 后才淡出 |
| **节拍与阈值**（循环动画的每一步间隔、防抖、超时判定） | 不受约束。由内容与网络决定 | 三点加载间隔 160ms、呼吸周期 3–7s、落字单块 12ms、预览防抖 300ms |
| **位移量**（`translateX(16px)` 这类） | 不是时长，但受 §8.7 禁止清单约束 | 抽屉 ±16px、消息 4px、Toast −8px |

因此全文出现的 `160ms`、`200ms`、`300ms`、`800ms`、`2.4s`、`4s` 分属后三类，**不是标尺违规**。判定方法只有一句：**看它有没有写在 `transition` 或 `animation-duration` 里**。

**与现有代码的冲突（必须处理）**：`tokens.css:261-264` 现有 `--motion-duration: 0.18s`、`--motion-duration-fast: 0.12s`、`--motion-duration-slow: 0.26s`、`--motion-curve: cubic-bezier(0.4, 0, 0.2, 1)`。

- `0.26s`（260ms）不在五档内，归入 `240ms`。
- `--motion-curve` 现为 Material 的 standard 曲线，本规范要求 Apple 的 fluid 曲线，见 §8.2。**这是唯一必须替换的动效令牌。**
- 三个旧变量**不要删除**，改为直接赋新值（`--motion-duration: 180ms` 等），让 20 余处现有引用自动收敛，避免逐文件查找。

### 8.2 曲线

| 名称 | 值 | 用在哪 | 为什么 |
| --- | --- | --- | --- |
| fluid（进场） | `cubic-bezier(.32, .72, 0, 1)` | 所有"出现"：抽屉、Sheet、Toast、菜单、Dialog | 起步快、收尾慢，物体落位的自然感。这是 HIG 的 fluid 曲线 |
| fluid-reverse（出场） | `cubic-bezier(.4, 0, 1, 1)` | 所有"消失" | 出场应比进场快且干脆，不拖尾。**用进场曲线做出场是常见错误**，会让关闭动作显得犹疑 |
| spring | `{ stiffness: 320, damping: 34 }` | 仅图标形变 | 物理模型，无固定时长，≈140ms 到位，临界阻尼不回弹 |
| breathe | `ease-in-out` | 仅呼吸循环（C1） | 呼吸是往返循环，两端必须对称减速。`fluid` 的单向收尾特性会让每一轮出现"吸到底就卡住"的顿挫 |

**为什么进场与出场必须用不同曲线**：进场时用户注意力在"新东西"，慢收尾让视线跟上；出场时用户已经决定关掉它，慢收尾就是拖沓。两者用同一条曲线，界面会显得"开门慢、关门也慢"。

**为什么不能用 `ease` / `ease-in-out` 兜底**：`ease` 的实际曲线是 `cubic-bezier(.25,.1,.25,1)`，起步有轻微迟滞。大量元素同时用它，界面会显得"整体慢半拍"。这是现有代码里 20 余处 `transition: ... ease` 需要一并替换的原因。

### 8.3 动效全清单

分三类。**"全部动效"指这三张表的并集**，表外任何动效都算新增，需先改本节。

**A. 状态过渡（属性值变化，可中断）**

| # | 名称 | 触发 | 属性 | 时长 | 曲线 |
| --- | --- | --- | --- | --- | --- |
| A1 | 悬停 | 指针进入可交互元素 | `background-color` / `color` | fast | fluid |
| A2 | 按下 | `:active` | `background-color` / `transform: scale(.98)` | fast | fluid |
| A3 | 焦点环 | 键盘聚焦 | `box-shadow`（外扩 0 → 2px） | fast | fluid |
| A4 | 分段控件滑块 | 切换选项 | `transform: translateX()` | base | fluid |
| A5 | 开关 | 切换布尔值 | 滑块 `transform` + 轨道 `background-color` | base | fluid |
| A6 | 滑杆拖动 | 拖动 | 跟随指针，**无过渡** | 0 | — |
| A7 | 水位 | 精力值变化 | 内层 `transform: scaleY()` | slow | fluid |
| A8 | 数字递增 | 记忆计数变化 | 文本插值 | 600ms（见注） | 线性插值 |
| A9 | 图标形变 | 同一位置的状态切换 | path 插值 | spring | spring |
| A10 | 主题切换 | 用户手动切换 | `background-color` / `color` | fast | fluid |

> A7 的关键实现：**不要动画 `height`**。外层轨道设 `overflow: hidden` 与 `border-radius: 3px`，内层填充用 `transform: scaleY()` + `transform-origin: bottom`。这样圆角由外层裁出，内层缩放不会把圆角拉成椭圆。原方案动画 `height` 会触发 layout，且在 150px 范围外会拖帧。
>
> A8 的 600ms 是唯一不在五档内的时长，理由是它属于文本插值而非 CSS 过渡，由 JS 驱动，不受标尺约束。若坚持统一，可降到 240ms，但数字跳得太快会失去"在计数"的观感。

**B. 进场与退场（元素出现或消失）**

| # | 名称 | 场景 | 属性 | 进场 | 退场 |
| --- | --- | --- | --- | --- | --- |
| B1 | 抽屉浮现 | Rail / 检查器展开 | `translateX(±16px)` + `opacity` | 180ms fluid | 240ms fluid-reverse |
| B2 | 消息入场 | 新消息到达 | `opacity 0 → 1` + `translateY(4px)` | 180ms fluid | 无（不做出场） |
| B3 | Toast | 提示条 | `translateY(-8px)` + `opacity` | 180ms fluid | 120ms fluid-reverse |
| B4 | 菜单 | 浮层菜单 | `opacity` + `scale(.98 → 1)` | 120ms fluid | 120ms fluid-reverse |
| B5 | Dialog | 模态 | `scale(.98 → 1)` + `opacity` + 遮罩淡入 | 180ms fluid | 120ms fluid-reverse |
| B6 | Sheet | 确认面板 | `translateY(-100% → 0)` | 180ms fluid | 180ms fluid-reverse |
| B7 | 输入框高度 | 多行展开 | `height`（唯一允许的 layout 动画，见 §8.6） | 180ms fluid | 180ms fluid |
| B8 | 附件缩略图 | 添加附件 | `scale(.9 → 1)` + `opacity` | 180ms fluid | 120ms fluid-reverse |
| B9 | 双脊进入会话 | 首页 → 会话 | `translateX(∓8px)` + `opacity` | 180ms fluid | 无（返回首页时瞬时） |

**C. 常驻与特殊（无触发的循环，或一次性的长动效）**

| # | 名称 | 场景 | 属性 | 时长 | 降级 |
| --- | --- | --- | --- | --- | --- |
| C1 | 呼吸 | 有情绪数据时 | `opacity .85 ↔ 1` | loop（3–7s 完整一轮） | 停止，固定为 1 |
| C2 | 落字 | 流式输出 | 每词 `opacity 0 → 1` | 见 §8.4 | 整段直接出现 |
| C3 | 回声 | 她回复完成 | 上一条用户消息 `color` | 900ms | 立即变色 |
| C4 | 滚动条 | 滚动中 | `opacity` + `width 8 → 12px` | 进场 fast / 停止滚动 800ms 后，用 slow 淡出 | 常显不透明 |
| C5 | 拖拽反馈 | 文件拖入窗口 | 虚线框 `opacity` | fast | 直接显示 |
| C6 | 录音波形 | 录音中 | `scaleY` 逐条随机，60ms/帧 | 循环 | 静态三根等长竖线 |
| C7 | 光标闪烁 | 输入中 | `opacity` | 1.06s 循环 | 常亮 |
| C8 | 骨架 | 连接宿主 | 无动效，纯色块 | — | 同 |

**明确不做的**：窗口最小化/还原/全屏动画交由系统（两端各自的原生动画是合理的，模仿反而更差）；应用启动不做开屏动画（820×580 的窗口里做 400ms 开屏，等于让用户每天多看 400ms 空屏）。

### 8.4 落字：最容易做错的一条

"每词 12ms"听起来温和，实际有两个陷阱：

**陷阱一：中文没有空格分词。** 上游给的是 token 流，不是"词"。必须按**标点与语义边界**切块（逗号、句号、问号、换行），块内按 2–4 字追加。直接按 token 落字，中文会出现"我/们/今/天"这种断字感。

**陷阱二：积压。** 若一次到达 50 个字、每块 12ms，播放需要 600ms，而新数据在这 600ms 内继续到达，延迟会累积，最终变成"回复早已生成完，界面还在慢慢吐"。必须加延迟预算：

| 规则 | 值 |
| --- | --- |
| 目标总延迟 | ≤ 240ms（约 20 块） |
| 单块间隔 | 12ms，标点后 +60ms |
| 追赶 | 待播块数 > 20 时，间隔按 `12 × 20 / 待播数` 压缩，最低 4ms |
| 熔断 | 待播块数 > 60 时，直接整段渲染，放弃落字 |
| 生成结束 | 剩余块一次性渲染，**不补播** |

**绝不允许**：生成完成后还逐字播放一段"打字机"动画。这是最容易识破的假，也违反 §1.2 第 3 条。

### 8.5 中断与并发

| 场景 | 规则 |
| --- | --- |
| 抽屉展开中再点一次 | 从当前 `translateX` 值反向，不回到 0 |
| Toast 替换 | 新条从旧条位置淡入（120ms 交叉），不先退场再进场 |
| 连续切换主题 | 后一次直接覆盖，不做队列 |
| 连续切换模型 | 模型名的呼吸（900ms）重新计时，不叠加两次 |
| 消息流式期间切换检查器 | 落字继续，抽屉动画并行，互不阻塞 |
| 同屏并发上限 | 3 个。超过时，状态过渡类（A 组）优先，进场类（B 组）排队 120ms |

### 8.6 性能约束

- **只动画 `transform` 与 `opacity`**。两个例外：`background-color` / `color`（仅限 A1、A2、A5、A10，都是小面积）与 B7 的 `height`（单一元素，76–140px）。
- `will-change` 只在动画期间加，结束即移除。常驻 `will-change` 会让层数膨胀，反而更慢。
- 长列表（> 200 条）启用虚拟滚动；滚动期间**暂停**所有 C 组常驻动效。
- 60fps 是硬指标。任何在 M1 上掉到 50fps 以下的动效，删掉而不是优化。

### 8.7 降级：`prefers-reduced-motion`

不是"全部关掉"，而是**保留信息、去掉位移**。逐条映射：

| 原动效 | 降级后 |
| --- | --- |
| A1 / A2 / A3 / A10 | 保留颜色过渡（120ms），去掉 `scale` |
| A7 水位 | 瞬时跳变（`0ms`） |
| A9 图标形变 | 直接换图 |
| B1 / B3 / B4 / B5 / B6 / B8 / B9 | 直接出现 / 直接消失（`0ms`），**不做淡入** |
| B7 输入框高度 | 瞬时 |
| C1 呼吸 | 完全停止，`opacity` 固定 1 |
| C2 落字 | 按标点整句出现，无块内淡入 |
| C3 回声 | 瞬时变色 |
| C4 滚动条 | 常显 |
| C6 波形 | 静态三根竖线（仍表示"在录音"，信息不丢） |
| C7 光标 | 常亮 |

**实现方式只有一处**，写在 `base.css` 里，不要在每个组件里各写一遍 `@media`：

```css
@media (prefers-reduced-motion: reduce) {
  :root {
    --motion-0: 0ms;
    --motion-fast: 0ms;
    --motion-base: 0ms;
    --motion-slow: 0ms;
    --motion-emphasis: 0ms;
  }
  *, *::before, *::after {
    animation-duration: 1ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 1ms !important;
  }
}
```

用 `1ms` 而非 `0s`：部分浏览器在 `transition-duration: 0s` 时不触发 `transitionend`，依赖该事件的逻辑会挂住。改为 `1ms` 既瞬时又能触发事件。

呼吸是唯一例外：它靠 JS 驱动（周期由 `ondra-rhythm` 给），因此还需监听 `matchMedia('(prefers-reduced-motion: reduce)')` 并停掉定时器，CSS 兜不住。

### 8.8 禁止清单

弹跳（bounce）、回弹（spring overshoot）、旋转、缩放超过 1.02、位移超过 24px、粒子、发光、模糊过渡、视差、骨架屏闪光、逐字打字机（生成完毕后补播）、动画排队（用户连续操作时先播完上一个）。

**为什么禁止骨架屏闪光**：连接本地宿主通常不到 1 秒，闪光反而制造"在等待"的错觉。纯色块已经表达了"还没好"，再加流光就是强调一件用户不希望发生的事。

### 8.9 参考实现

```css
/* tokens.css —— 动效令牌在这里定义一次，别处只引用 */
:root {
  /* 时长五档，与 §8.1 逐字对应 */
  --motion-0:        0ms;
  --motion-fast:     120ms;
  --motion-base:     180ms;
  --motion-slow:     240ms;
  --motion-emphasis: 900ms;

  /* 曲线：两条 CSS 曲线 + 一条往返曲线，spring 走 JS（§8.2） */
  --ease-fluid:         cubic-bezier(.32, .72, 0, 1);
  --ease-fluid-reverse: cubic-bezier(.4, 0, 1, 1);
  --ease-breathe:       ease-in-out;

  /* 旧变量保留并赋新值，让现有 20 余处引用自动收敛（§8.1） */
  --motion-duration:      180ms;
  --motion-duration-fast: 120ms;
  --motion-duration-slow: 240ms;
  --motion-curve:         var(--ease-fluid);
}

/* 水位：外层裁圆角，内层缩放，避免 height 动画触发 layout */
.meter { overflow: hidden; border-radius: 3px; }
.meter__fill {
  height: 100%;
  transform-origin: bottom;
  transform: scaleY(var(--level, 0));
  transition: transform var(--motion-slow) var(--ease-fluid);
}

/* 呼吸：一轮 3–7s，由 JS 写入 --breath-period */
@keyframes ondra-breathe {
  0%, 100% { opacity: 1; }
  50%      { opacity: .85; }
}
.spine__water {
  /* 唯一允许 ease-in-out 的地方：往返循环需要对称减速，见 §8.2 */
  animation: ondra-breathe var(--breath-period, 5s) var(--ease-breathe) infinite;
}

/* 抽屉：进出场用不同曲线 */
.drawer {
  transition: transform var(--motion-slow) var(--ease-fluid-reverse),
              opacity   var(--motion-slow) var(--ease-fluid-reverse);
}
.drawer[data-open="true"] {
  transition-duration: var(--motion-base);
  transition-timing-function: var(--ease-fluid);
}
```

`--level` 与 `--breath-period` 由 JS 写入，**不是设计令牌**，因此不出现在 `tokens.css` 的令牌表里——它们分别是「水位高度 0–1」与「本轮呼吸周期」，属于运行期数据。这也是 §4.1 那张令牌存在性核对表里查不到它们的原因。同理，`.drawer` 的两条 `transition` 不能合并成 shorthand，否则 `[data-open="true"]` 覆写时会丢掉其中一条。

## 9. 键盘与可达性

这一章有两个目的：让熟练用户不离开键盘就能完成一切，让不能用鼠标的人也能完成一切。前者是效率，后者是底线。

### 9.1 快捷键总表

三端键位差异只有一处：修饰键。macOS 用 `Cmd`，Windows / Linux 用 `Ctrl`。除此之外**不支持任何平台特有键位**——不做 `Cmd` 与 `Ctrl` 混用映射，不做 `Alt` 替代方案，避免同一操作有两个说法。

| 操作 | macOS | Windows / Linux | 说明 |
| --- | --- | --- | --- |
| 发送 | `Enter` | `Enter` | 输入法组合中不触发（§12.3） |
| 换行 | `Shift + Enter` | `Shift + Enter` | — |
| 另一种发送 | `Cmd + Enter` | `Ctrl + Enter` | 为习惯 Slack 的用户保留 |
| 新建对话 | `Cmd + N` | `Ctrl + N` | 已在会话中时清空并回到首页形态 |
| 搜索记忆 | `Cmd + K` | `Ctrl + K` | 打开抽屉并聚焦搜索框 |
| 切换 Rail 项 | `Cmd + 1..4` | `Ctrl + 1..4` | 顺序固定为：今天 / 本周 / 记忆 / 剧场（见下方定稿说明） |
| 偏好设置 | `Cmd + ,` | `Ctrl + ,` | Windows 上逗号键无需 Shift |
| 关闭当前层 | `Esc` | `Esc` | 逐层退，见 §9.3 |
| 打开/关闭检查器 | `Cmd + Shift + I` | `Ctrl + Shift + I` | 与浏览器开发者工具同键，开发者熟悉 |
| 停止生成 | `Esc` | `Esc` | **仅当正在生成时**，优先于关闭层 |
| 上一条编辑 | `↑` | `↑` | 输入框为空时，把最后一条用户消息填回输入框 |
| 跳到最新 | `Cmd + ↓` | `Ctrl + ↓` | 时间轴滚到底部 |
| 显示快捷键表 | `Cmd + /` | `Ctrl + /` | 见 §9.4 |
| 切换主题 | `Cmd + Shift + L` | `Ctrl + Shift + L` | 亮/暗/跟随系统三态循环 |
| 复制最后一条回复 | `Cmd + Shift + C` | `Ctrl + Shift + C` | — |

**为什么不给"删除对话"配快捷键**：它是不可逆操作，快捷键会让误触代价过高。删除必须走 §7.1 的 4 级 Dialog 并手写确认。

> **定稿说明（Rail 的键位只到 4）**：本表先前写作 `Cmd/Ctrl + 1..5`，顺序是「对话 / 记忆 / 关系 / 通道 / 设置」，与 §5.2 的四个图标（今天 / 本周 / 记忆 / 剧场）对不上——条目不同、数量也不同。已按 **§5.2 为准**定稿为 `1..4`。
>
> 设置**不占数字键**，走 `Cmd/Ctrl + ,`（本表已有定义）。理由是设置不是抽屉：§5.2 明确「齿轮不展开抽屉，直接打开偏好设置窗口」，把它排进抽屉的序号里会让人以为第五个图标也是抽屉。给同一件事两个键位（数字 5 与逗号）也违背「不做同一操作的两个说法」这条原则。
>
> 关联约束：**输入框有内容时 `Cmd/Ctrl + 数字` 不切 Rail**（见 §9.2 第 1 条）。用户可能要输入序号。

### 9.2 快捷键的四条硬规则

1. **输入框内有文本时，`Cmd/Ctrl + 数字` 不切换 Rail。** 用户可能想输入序号。只有「输入框为空」或「焦点不在输入框」时才生效。
2. **`Esc` 有三重含义，按优先级判定**：正在生成 → 停止生成；有浮层 → 关浮层；其余 → 无操作（**不退出应用、不清空输入**）。
3. **不劫持系统键。** `Cmd + Tab`、`Cmd + Q`、`Alt + F4`、`Cmd + Space` 一律不拦截。唯一例外是 `Cmd + W` / `Alt + F4` 关闭窗口时确认宿主已优雅关闭（见 §12.9）。
4. **输入法组合中所有快捷键失效。** 监听 `compositionstart` / `compositionend`，组合期间直接 `return`。中文用户打「你」时按 `Enter` 是确认候选，不是发送。

### 9.3 `Esc` 的层级顺序

`Esc` 是用户唯一无需求助就能按的键，它的行为必须可预测。从最内层往外：

```
1. 正在生成 ────────→ 停止生成（Toast 提示"已停止"）
2. 菜单/浮层打开 ──→ 关闭浮层，焦点回到触发元素
3. 抽屉打开 ───────→ 关闭抽屉
4. 检查器打开 ─────→ 关闭检查器
5. 设置子页 ───────→ 回到设置首页
6. 设置页 ─────────→ 关闭设置
7. 全屏消息查看 ───→ 退出全屏
8. 其余 ───────────→ 无操作（不退出应用）
```

**第 8 条是刻意的**：桌面上 `Esc` 不承担"退出程序"语义。把它做成退出键，会让用户在想取消某个操作时误退应用。

### 9.4 可发现性：用户怎么知道有这些键

快捷键没人知道等于不存在。三个露出点，不做第四个：

| 露出点 | 内容 | 触发 |
| --- | --- | --- |
| 菜单项右侧 | 每项后跟键位提示，右对齐 | 常驻（菜单打开时可见） |
| 悬停提示 | 图标按钮的 `title`/`tooltip` 带键位，如「搜索记忆 ⌘K」 | 悬停 800ms（§5.2） |
| 快捷键总表 | 按 `Cmd/Ctrl + /` 或设置·键盘页 | 主动查看 |

**快捷键总表用 Sheet 不用 Dialog**：它是查阅，不是决策，不该阻断用户。

### 9.5 焦点管理

焦点是键盘用户唯一的"当前位置"。做错一处，整条路径就断。

| 场景 | 焦点去向 | 理由 |
| --- | --- | --- |
| 应用启动 | **不自动聚焦输入框** | 自动聚焦会让 `Tab` 从输入框开始，跳过整条 Rail |
| 打开抽屉 | 抽屉内第一个可聚焦项（搜索框） | 用户打开抽屉就是为了搜索 |
| 关闭抽屉 | **回到触发它的按钮** | 焦点丢失会让键盘用户从文档开头重新 Tab |
| 打开 Dialog | Dialog 内第一个**非破坏性**按钮 | 默认落在「取消」而非「删除」 |
| 关闭 Dialog | 回到触发元素 | 同上 |
| 发送消息 | 回到输入框 | 连续对话是主路径 |
| 删除条目 | 同列表的下一条；无下一条则上一条；列表空则列表容器 | **绝不回到页面顶部** |
| 切换 Rail 项 | 该项本身（不进入内容区） | 让用户能连续按方向键切换 |
| 消息加入 | **不抢焦点** | 生成中抢焦点会打断用户输入 |
| Toast 出现 | **不抢焦点** | 它是通知，不是请求 |

**现有代码的问题**：`Composer.tsx` 若在挂载时 `autoFocus`，上述第一条就不成立。落地时须移除，改用「用户点了输入框才聚焦」。

### 9.6 Tab 顺序

一条固定路径，不允许 `tabindex` 正数（`tabindex="1"` 会打乱整个文档顺序）：

```
标题栏（Windows 三键 → 菜单按钮 → 标题）
  ↓
Rail（5 项，↑↓ 或 Tab 逐个）
  ↓
主列：消息区（每条消息一次）
        ↓ 消息内操作（仅聚焦时进入）
      MemoryChip（有则插入）
      Composer（附件 → 输入框 → 发送）
  ↓
Spine（水位 → 读数 → 检查器入口）
  ↓
检查器（打开时）
```

**消息区内用 `Tab` 逐个走太慢**——40 条消息要按 40 次。补救：消息区获得焦点后，`PageUp` / `PageDown` 按屏跳，`←` / `→` 在消息间移动。这是唯一的例外，需在消息区 `role="log"` 上单独实现。

**抽屉打开时焦点锁在抽屉内**（focus trap）：`Tab` 到最后一个元素后回到第一个，`Shift+Tab` 反之。关闭后解除并归还焦点。

### 9.7 无障碍语义

| 元素 | 必须有的语义 | 常见错误 |
| --- | --- | --- |
| 图标按钮 | `aria-label`（如「新建对话」） | `aria-label="icon"` 一类无意义值 |
| 水位 | `role="meter"` + `aria-valuenow/min/max` + `aria-label="精力"` | 用 `role="progressbar"`（语义是任务进度，不是状态） |
| 指标条 | 同上，`aria-label` 写明指标名 | 只给数值不给名称 |
| 消息列表 | `role="log"` + `aria-live="polite"` | `aria-live="assertive"` 会打断朗读 |
| 生成中 | `aria-busy="true"` 挂在消息容器 | 挂在整页 |
| 错误条 | `role="alert"` | 用 `aria-live` + 视觉红代替 |
| 开关 | `role="switch"` + `aria-checked` | 用 `role="checkbox"`（语义不同） |
| 分段控件 | `role="radiogroup"` + `role="radio"` + `aria-checked` | 用 `button` + 手写选中样式 |
| 滑杆 | `role="slider"` + `aria-valuetext`（带单位） | 只给 `aria-valuenow`，读屏读出"78"不知何意 |
| 抽屉 | `role="dialog"` + `aria-modal="true"` + `aria-labelledby` | 缺 `aria-modal` 会让读屏读到背后内容 |
| 当前 Rail 项 | `aria-current="page"` | 只用视觉高亮 |
| 禁用项 | `aria-disabled="true"` + **可聚焦** | 用 `disabled` 属性（读屏跳过，用户不知道为什么不能点） |

**最后一条与 §5.0 呼应**：禁用使用 `aria-disabled` 而非 `disabled`，因为 `disabled` 的元素不可聚焦、读屏直接跳过，用户得不到「为什么不能点」的解释。`aria-disabled` 保留可聚焦，聚焦时朗读禁用原因。

### 9.8 对比度与视觉可达性

| 项 | 要求 | 现状核对 |
| --- | --- | --- |
| 正文与背景 | ≥ 4.5:1 | 浅色 `#1F2422` on `#FFFDF9` ≈ 14.8:1，通过 |
| 次要文字 `ink-3` | ≥ 4.5:1 | 需实测，临界 |
| 占位符文字 | ≥ 4.5:1 | **常被做到 3:1**，须核对 |

**不用颜色单独传信息**（HIG 硬性要求），三处必须复核：

| 信息 | 颜色 | 必须有第二通道 |
| --- | --- | --- |
| 心情 | 水位颜色 | 检查器内文字「平静 / 低落 / 明亮」 |
| 错误 | 红色 | 图标 + 三段式文案 |

## 10. 多端适配

本章覆盖九端：**macOS、Windows、Linux、Android、iOS、鸿蒙（HarmonyOS）、iPad、命令行与 Web、dsh 内核**。

前七端是"同一套界面跑在不同屏幕与系统上"，第八端是"没有图形屏幕时的降级形态"，第九端不是设备而是**内核进程**——它推送的事件必须落成界面状态，否则前面八端都是空壳。

**共同前提：移动端不能运行本地宿主。** 这不是取舍，是硬约束：

- 宿主是 **Node 进程**（`cordis-host`，运行时约 108 MB，见 `src-tauri/runtime/node`），由壳以子进程拉起，通过 **stdio + 本地 HTTP** 通信。
- iOS 沙盒**禁止应用创建子进程**（`fork` / `exec` 一律被拒），也禁止 JIT。Android 虽允许子进程，但 108 MB 运行时随包分发与"安装即用"的预期冲突。
- 因此桌面端是"**本地宿主**"，移动端必须是"**远程宿主**"——连你自己电脑上跑的那个，或一个托管实例。

好在这一点在代码里已经成立：`src/lib/host.ts` 的 `HostConnection { url, token, port }` **由壳注入**，前端不关心宿主在哪。移动端只需换掉注入来源，业务层零改动。

**但也有一处真实阻力，必须说清**：`src-tauri/Cargo.toml` 明确写了「不声明 `[lib]`：空谷只出桌面端（dmg / app / nsis）」，并用大段注释说明去掉 `lib + cdylib` 是为了让入口只留在 `main.rs`。而 Tauri 的移动端**必须**有 `lib.rs` + `cdylib`——iOS/Android 要把 Rust 编成被原生工程链接的动态库。所以移动端不是"加个配置"，是要**恢复 `lib` 结构并拆分入口**。这条已登记进 §11.1。

### 10.1 断点体系

断点用**内容宽度**而非设备宽度判断。窗口 820px 与 iPad 竖屏 820px 是一回事，无需关心它是手机还是电脑。

> **注意区分两个 820**：这里是**内容宽度阈值**（容器查询读的值），与 §3.6 的**电脑窗口尺寸** 820 × 580 是两个独立概念，数值相同纯属巧合。移动端不存在"窗口 820"，只有"内容区 820"——iPad 竖屏全屏渲染后内容区恰好 820，因此落入 `wide`，但它的窗口尺寸不由 §3.6 决定。

| 名称 | 宽度区间 | 对应 | 布局形态 |
| --- | --- | --- | --- |
| `compact` | < 600 | 手机竖屏、窄窗口 | 单列，双脊收进标题栏 |
| `regular` | 600–819 | 手机横屏、iPad 分屏、小窗口 | 单列 + 左抽屉，右脊收起 |
| `wide` | 820–1199 | 电脑端基准窗口、iPad 竖屏全屏 | 双脊常驻（本文件的主设计） |
| `wide+` | ≥ 1200 | 大窗、iPad 横屏 | 双脊 + 检查器可常驻 |

```css
/* 全部断点只写一处，用容器查询而非媒体查询 */
.shell { container-type: inline-size; container-name: shell; }

@container shell (max-width: 599px)  { /* compact */ }
@container shell (max-width: 819px)  { /* regular 及以下 */ }
@container shell (min-width: 820px)  { /* wide */ }
@container shell (min-width: 1200px) { /* wide+ */ }
```

**为什么用容器查询**：iPad 分屏、Windows 贴边、macOS 窗口缩放、台前调度都会让"视口"与"内容区"不一致。媒体查询看视口，容器查询看内容区，后者才是布局应该依据的。

**形态切换是布局，不是路由**。同一个组件树，只换 CSS 与少量条件渲染，不做页面跳转——否则拖动窗口大小时会丢滚动位置。

### 10.3 compact：手机上怎么放双脊

手机宽度 ≤ 599 时，48 + 56 = 104px 的脊会吃掉 17% 宽度，正文只剩 400 出头，不可接受。做法是**把脊的内容移进顶栏，脊本身消失**。

**顶栏（`TopBar`）与电脑端 TitleBar 的关系**：两者语义相同——左入口 / 中标题 / 右状态，但实现不同。`TopBar` 是应用内自绘的一行，**不含窗口控制、不可拖拽**（移动端没有窗口）；高度为 48 + 安全区，比 TitleBar 的 44 高，因为触屏需要更大热区。

| 原位置 | compact 后（进 `TopBar`） |
| --- | --- |
| Rail（5 个图标） | 顶栏左侧一个 24px 汉堡，点开全屏抽屉 |
| Spine（水位） | 顶栏右侧一个 8px 圆点（颜色=心情）+ 点开检查器 |
| 标题 | 居中，最大宽 180px |
| 检查器 | 全屏 Sheet，从底部推入 |
| 抽屉 | 全屏 Sheet，从左侧推入 |

| `TopBar` 属性 | 值 |
| --- | --- |
| 高度 | 48 + `env(safe-area-inset-top)` |
| 背景 | 与主列同色（`--alias-surface-primary`），下沿 2px 水位线覆盖其上 |
| 左 | 汉堡按钮 24px 图标，热区 44 × 44 |
| 中 | 标题，14px，最大宽 180，超出省略 |
| 右 | 状态点 8px，热区 44 × 44 |
| 拖拽 | **无**（移动端窗口不可拖） |
| 双击缩放 | **无** |

**水位在手机上只留一个圆点，会不会丢信息？** 不会，因为手机端有更合适的载体：**把水位改成一条 2px 横线，贴在标题栏下沿**。高度=精力，颜色=心情，长度满宽。它不占布局高度（绝对定位覆盖在分隔线上），却能一直可见。

### 10.4 触屏与指针的差异

这是适配里**最容易做坏**的一层。触屏没有悬停，`hover` 样式会"粘住"——手指点过后那个悬停态会一直停留到下次点击别处。

| 项 | 指针（桌面） | 触屏（iPad / 手机 / 鸿蒙） | 实现 |
| --- | --- | --- | --- |
| 悬停 | 有 | **无** | `@media (hover: hover)` 包裹，现有代码已如此 |
| 点击热区下限 | 24（舒适 32） | **44 × 44** | 触屏断点内单独放大 |
| 图标视觉尺寸 | 16 | **20** | 触屏观看距离更远，16 太小 |
| 正文字号 | 14 | **16**（输入框必须） | iOS 输入框 < 16px 会触发页面自动放大 |
| 消息操作按钮 | 悬停出现 | **常驻**（每条右下角，40% 不透明） | 无悬停可依附，只能常驻 |
| 长按 | 无 | **长按选中并出工具条** | 500ms，到达时轻触觉反馈 |
| 右键菜单 | 有 | 长按替代 | — |
| 滚动 | 8px 滚动条 | **无滚动条**，惯性回弹 | `overscroll-behavior` |
| 双击标题栏 | 缩放 | 无标题栏 | — |
| 文件入站 | 拖拽 | 选择器 | 见 §12.14 |

**`hover: none` 时按钮常驻**的代价是视觉噪声。缓解办法：常驻按钮用 40% 不透明度，滚动时隐藏，停止滚动 600ms 后重新出现。

**正文字号按「输入方式」分档，不按「设备」分档**。这条与热区同理，但结果不同，容易搞混：

| 条件 | 正文 | 输入框 | 理由 |
| --- | --- | --- | --- |
| `pointer: fine`（指针，含接键盘的 iPad） | 14 | 16 | 观看距离约 50cm，14px 是桌面正文的舒适值 |
| `pointer: coarse` 且屏宽 ≥ 768（iPad 手持、折叠屏展开） | **15** | 16 | 手持距离约 40cm，比桌面近一点，14 偏小但 16 会让 820 宽度下每行字数过少 |
| `pointer: coarse` 且屏宽 < 768（手机） | **16** | **16** | 手持距离约 30cm，16px 是下限 |

**输入框在所有触屏条件下都必须是 16px**，包括 iPad 接键盘时。原因不是观感，是 iOS 的自动放大：Safari 检测到聚焦的输入框 `font-size < 16px` 就会缩放整个视口，且缩放后不会自动恢复，用户得手动捏回去。这台 iPad 接了键盘也仍然可能在触屏上点输入框，所以不能因为 `pointer: fine` 就降到 14。

因此 §10.12 里 iPad 与桌面同记「正文字号 14」，指**接键盘时的 `pointer: fine` 状态**；手持时是 15。这一格不要理解成"iPad 上永远 14px"。

### 10.5 桌面三端：macOS / Windows / Linux

三端执行本文件全部规则，界面与操作**完全相同**。差异只在本文件 §2.2 登记的两处（窗口控制、安装器），加上 Linux 的六项环境补偿：

| 项 | 问题 | 处理 |
| --- | --- | --- |
| 字体 | MiSans 随包内嵌，但系统缺中文回退时缺字会掉到默认无衬线 | 字体栈补 `"Noto Sans CJK SC", "Source Han Sans SC"` |
| 字体渲染 | FreeType 比 CoreText 细，与 Windows 类似 | `[data-platform="linux"] body { font-variation-settings: "wght" 450; }`，与 Windows 同一补偿值 |
| 无边框窗口 | 需 `decorations: false`，但部分 WM（i3、sway）不识别自绘拖拽区 | 改为**设置项**：「使用系统标题栏」（默认开）。开启后隐藏自绘三键，窗口高 +32 |
| 高 DPI | `GDK_SCALE` 与 `GDK_DPI_SCALE` 组合下 `devicePixelRatio` 可能是 1.5 | 与 Windows 同一套 0.5px 降级逻辑 |
| 托盘 | GNOME 默认不显示托盘图标（需扩展） | 检测不到托盘时，关闭行为**改为最小化**，首次提示原因 |
| 文件选择器 | 走 xdg-desktop-portal，部分发行版未装 | 失败时退回 Tauri 原生对话框 |

**「使用系统标题栏」是 Linux 端唯一的额外开关，默认开启。** 理由：Linux 的窗口管理器生态太分散，自绘标题栏在 i3 / sway / Hyprland 这类平铺 WM 下会出现"窗口拖不动"，而这类用户占比不低。宁可少一点视觉一致性，也不能让窗口拖不动。

### 10.6 iPad：介于两者之间

iPad 是最需要单独考虑的一端，因为它**同时是触屏和宽屏**。

| 场景 | 宽度 | 形态 | 特殊处理 |
| --- | --- | --- | --- |
| 竖屏 | 820 | wide | 双脊常驻，但热区与字号按触屏放大 |
| 横屏 | 1180 | wide+ | 检查器可常驻展开在右侧 |
| 分屏 1/2 | 507 | compact | 双脊收起 |
| 分屏 1/3 | 320 | compact | 同上，且标题最大宽降到 120 |
| 台前调度（自由尺寸） | 任意 | 按当前宽度 | 容器查询自动处理，无需额外代码 |

**iPad 的键盘与指针**：接上妙控键盘后 `hover: hover` 与 `pointer: fine` 会同时成立。因此触屏适配**不能按设备判断**，必须按 `@media (hover: hover) and (pointer: fine)` 判断——同一台 iPad 在两种状态下要有两种行为，这是唯一正确的做法。

**Apple Pencil**：不做压感、不做手写识别。这是聊天界面，手写不是输入主路径，做了只会变成演示功能。

### 10.7 手机三端：iOS / Android / 鸿蒙

三端共用 compact 形态与触屏规则，差异集中在系统层：

#### 10.7.1 iOS 与 Android

| 项 | iOS | Android |
| --- | --- | --- |
| 状态栏 | 由 `prefers-color-scheme` 与 `data-theme` 决定图标明暗 | 需 `WindowInsets`，主题色由 `themes.xml` 定 |
| 返回手势 | 侧滑返回；**不与抽屉手势冲突**：抽屉只响应屏幕左缘 20px | 系统返回键：抽屉开着时先关抽屉，再退会话，最后退出 |
| 键盘 | `visualViewport` 唯一可靠 | `adjustResize`；华为/小米输入法高度差异大，同用 `visualViewport` |
| 震动 | 不支持 `navigator.vibrate` | 支持；长按到达时 10ms |
| 分享 | 系统分享面板 | 系统分享面板 |
| 通知 | 需引导用户到设置开权限 | 通知渠道（channel）分「她主动说话」与「系统」两条 |

**返回键是 Android 特有的先手**：iOS 靠手势，Android 有实体/虚拟返回键，不接管就会出现"按返回直接退出应用"。必须在 `popstate` 上拦一次，按 §10.7.1 的顺序逐层退。

#### 10.7.2 鸿蒙（HarmonyOS NEXT）

必须诚实说明：**Tauri 官方不支持鸿蒙，也没有社区成熟的 WebView 壳方案。** 鸿蒙 NEXT 已移除 AOSP 兼容层，不能直接装 Android 包。

| 路径 | 可行性 | 代价 |
| --- | --- | --- |
| ArkTS 原生重写 | 可行 | 界面要重写一遍，违背"界面相同" |
| ArkWeb 承载现有 Web 产物 | **推荐** | 写一个薄壳：ArkWeb 组件加载 `dist/`，注入 `HostConnection`，补窗口与键盘适配 |
| 打包 Android 包 | **不可行** | NEXT 不兼容 AOSP |
| 暂不支持 | 可行 | 明确不在本版范围内 |

**推荐 ArkWeb 薄壳**，因为前端产物是纯 Web，`src/lib/shell.ts` 已经把 Tauri 依赖收在一个 `tauri()` 取用点里，只要提供等价的 `invoke` / `listen` 两个方法，前端零改动。这条路的工作量集中在 ArkTS 侧，不在界面侧。

**若决定做**，必须补齐四项：安全区（鸿蒙有独立的安全区 API）、键盘高度（ArkWeb 有 `onAreaChange`）、返回手势、以及 `hover: none` 恒成立（鸿蒙无指针设备，折叠屏亦然）。

#### 10.7.3 手机端共同的三条硬要求

1. **输入框字号不得小于 16px**。iOS Safari 与部分鸿蒙 WebView 在小于 16px 时会自动放大页面，用户点一次输入框整个界面就"跳大"，且无法缩回。
2. **禁止下拉刷新**。`overscroll-behavior-y: contain`。聊天页面下拉会误触刷新，导致生成中断。
3. **生成中保持屏幕常亮**。`navigator.wakeLock`，生成结束即释放。手机端一次长回答可能 40 秒，熄屏会让用户以为卡死。

### 10.8 安全区与移动端系统

| 项 | 值 |
| --- | --- |
| 顶部 | iOS 刘海/灵动岛：`padding-top: env(safe-area-inset-top)`，标题栏高度 = 48 + 安全区 |
| 底部 | 输入区下方 `padding-bottom: max(12px, env(safe-area-inset-bottom))` |
| 左右 | 横屏时 `env(safe-area-inset-left/right)` |
| 键盘弹出 | 用 `visualViewport` 而非 `window.innerHeight` |
| 键盘弹出时 | 时间轴滚到底部，输入区上移，**不重排整页**（避免跳动） |
| 状态栏样式 | 跟随 `data-theme`；浅色主题深色文字，深色主题浅色文字 |
| 下拉刷新 | **禁用**。`overscroll-behavior-y: contain` |
| 屏幕常亮 | 生成中保持常亮（`navigator.wakeLock`），生成完释放 |

**`visualViewport` 这条不是细节，是必须**：iOS Safari 在键盘弹出时只有 `visualViewport.height` 变小，`window.innerHeight` 不变。按后者布局，键盘会盖住输入框，用户只能盲打。

### 10.9 命令行与 Web 端

这不是"次要端"，而是**排障与自建的唯一入口**：宿主崩了、界面白屏时，用户仍要能读到状态；也有人想在自己搭的服务器上跑一个网页版。

| 形态 | 是什么 | 界面 | 要求 |
| --- | --- | --- | --- |
| `vite dev` 浏览器页 | 开发时改样式用 | 完整界面 | 已支持：`shell.ts` 对 `__TAURI__` 缺失时全部降级 |
| 托管 Web | 远程宿主的网页入口 | 完整界面（无窗口控制） | `capabilities.tray / multiWindow / localHost` 全为 `false` |
| CLI 状态输出 | `ondra status` 一类纯文本 | **无图形界面** | 见下表 |

**Web 端与桌面端的唯一区别是"壳能力全缺"**，因此不需要单独设计，只需要能力探测（§10.11）返回全否。窗口控制区不渲染，标题栏退化为纯文字行，高度仍为 44。

**CLI 输出的规则**（与界面同一套文案）：

| 项 | 规则 |
| --- | --- |
| 语言 | 与界面一致，简体中文 |
| 状态行 | `宿主：就绪 · 端口 43117 · 已连 3 个插件` —— 与 §5.9 检查器同源同措辞 |
| 错误 | 三段式（§5.0）：发生了什么 / 为什么 / 下一步怎么办 |
| 颜色 | 仅在 TTY 且 `NO_COLOR` 未设时上色；重定向到文件时自动关闭 |
| 退出码 | `0` 正常 / `1` 一般错误 / `2` 宿主未就绪 / `3` 协议不兼容 |

**为什么退出码要分开**：脚本化部署时，"宿主还没起来"应当重试，"协议不兼容"重试一万次也没用。只给一个非零码，调用方只能盲目重试。

### 10.10 dsh 内核端

第九端不是屏幕，是进程。它是**全部界面的数据来源**，所以它的契约必须落到界面状态上，否则前八端只是空壳。

依据 `dsh-sidecar/src/protocol.ts`（协议唯一真源，JSON-RPC 2.0，`PROTOCOL_VERSION = '1.0'`，单条消息上限 16 MiB）：

#### 10.10.1 握手决定界面裁剪

`kernel.handshake` 的返回里带 `methods: readonly string[]`，源码注释写明用途是"调用方据此裁剪 UI，而不是逐个试探"。

| 握手字段 | 界面用途 |
| --- | --- |
| `kernel: 'dsh'` | 确认连对进程；不符时不进主界面，直接报「连到了别的服务」 |
| `version` | 显示在设置·关于；与客户端版本不同时提示 |
| `protocolVersion` | 主版本不匹配 → **拒绝进入**，不能"尽力兼容" |
| `methods[]` | **能力裁剪的唯一依据**：缺 `tool.invoke` 就不渲染工具卡；缺 `model.configure` 就隐藏模型配置页 |
| `ready: false` | 进入"正在启动"态，`kernel.ping` 轮询，其余按钮禁用并说明原因 |

**禁止写"假定某方法一定存在"**。内核版本会独立于界面版本演进，`methods` 就是为此存在的。

#### 10.10.2 事件到界面的映射

七个 `event.*` 各自有唯一落点，**不允许两个事件驱动同一个视觉状态**：

| 事件 | 界面落点 | 动效 |
| --- | --- | --- |
| `event.ready` | 去掉「正在启动」覆盖层 | 覆盖层用 `--motion-slow`（240ms）淡出。比进场慢一档是刻意的：数据已经在了，让开得柔和些 |
| `event.inference.delta` | 正文逐字落字 | 见 §8.4（唯一 JS 驱动的动画） |
| `event.inference.reasoning` | 折叠区「思考中」 | **不落字**，只更新行数与呼吸点 |
| `event.inference.done` | 结束态：光标停、操作按钮解禁 | 光标 120ms 淡出 |
| `event.tool.started` | 工具卡转为运行中 | 卡片 180ms 展开 |
| `event.tool.finished` | 工具卡转结果 | 同卡内替换，不重排 |
| `event.shutting-down` | 顶部 Toast「正在退出…」+ 输入禁用 | 不阻塞 |

**思考过程不落字，是协议层的决定，不是样式偷懒**：`protocol.ts` 把正文与思考拆成两个事件，理由是"正文要落盘、思考不该落盘；正文按段渲染、思考要折叠"。界面必须尊重这个拆分——把思考也做成逐字动画，等于把不该落盘的内容做成了用户会想复制的东西。

#### 10.10.3 错误码到提示

`KernelErrorCode` 五个应用级错误码，界面必须给出**不同**的下一步，否则用户只知道"出错了"：

| 码 | 含义 | 界面提示 | 是否可重试 |
| --- | --- | --- | --- |
| `-32000` | 协议主版本不兼容 | 「内核版本不匹配，需要升级」+ 一个「检查更新」按钮 | **否** |
| `-32001` | 内核尚未就绪 | 「正在启动…」+ 自动重试，不弹窗 | 是（自动） |
| `-32002` | 内核正在关闭 | 「正在退出」+ 输入禁用 | 否 |
| `-32003` | 请求超时 | 「这一步太慢了」+「再试一次」 | 是（手动） |
| `-32004` | 能力未实现 | 「这个版本还没有这个功能」+ 说明 | 否 |
| `-32601` | 方法不存在 | 与 `-32004` 同措辞（对用户是一回事） | 否 |

**超时不是错误，是状态**。`-32003` 不弹红色，用中性 Toast 加一个可点的「再试一次」——本地推理在慢机器上确实会超时，把它做成红色错误会让用户以为坏了。

#### 10.10.4 内核作为"插件端"的界面归属

dsh 内核在界面上**不单独出现**，它没有自己的页面。它的存在方式是两个：

1. **状态行**：设置·诊断页显示 `内核 dsh 2.0.1 · 协议 1.0 · 已连` —— 与 §12.13 的错误分级同源。
2. **能力差异**：`methods` 缺项时，对应设置项**灰显并注明原因**（§5.0 的"禁用须解释"），而不是整块消失。整块消失会让用户以为功能丢了。

> 内核与宿主是两回事：宿主（`cordis-host`）管 134 个插件，内核（`dsh-sidecar`）管推理、工具、会话、模型。界面只与宿主通信，宿主转发到内核。因此 §10.0 说的"远程宿主"在移动端意味着**宿主与内核都跑在远端**。

### 10.11 用能力探测，不用平台判断

不要写 `if (platform === 'ios')`。写能力探测：

| 需要的能力 | 探测方式 | 不可用时 |
| --- | --- | --- |
| 悬停 | `@media (hover: hover)` | 按钮常驻 |
| 精确指针 | `@media (pointer: fine)` | 热区放大到 44 |
| 托盘 | 壳注入 `capabilities.tray` | 关闭=最小化 |
| 多窗口 | `capabilities.multiWindow` | 检查器改全屏 Sheet |
| 语音 | `mediaDevices.getUserMedia` 存在性 | 隐藏语音键 |
| 常亮 | `'wakeLock' in navigator` | 不启用 |
| 剪贴板图片 | `navigator.clipboard.read` | 隐藏"粘贴图片" |
| 本地宿主 | `capabilities.localHost` | 连接远程地址 |
| 震动 | `'vibrate' in navigator` | 长按无反馈 |
| 安全区 | `CSS.supports('padding-top: env(safe-area-inset-top)')` | 不加上内边距 |
| 内核方法 | 握手返回的 `methods[]` | 灰显对应设置项 |

**为什么不用平台判断**：iPad 接键盘后与 Mac 无区别；Android 平板可以外接鼠标；Linux 有触摸屏笔记本；鸿蒙折叠屏展开后是 8 寸平板。平台名不承载行为，能力才承载。

### 11.3 施工顺序

20 多个文件不能一起改。按下表五批走，**每一批结束后应用都能跑起来**，出问题只回滚一批。

| 批 | 内容 | 验收方式 | 可回滚性 |
| --- | --- | --- | --- |
| 1 | `tokens.css` 换色板与尺寸变量；`layout.css` 改 `48px 1fr 56px` | 启动后看到新配色与新骨架，功能全部可用 | 单文件 `git checkout` |
| 2 | 新增 `TitleBar` / `Icon` / `Platform`；`tauri.conf.json` 与 `capabilities` | 两端标题位置一致，图标线宽统一 | 新文件为主，删掉即复原 |
| 3 | `Rail` / `Spine` / `Inspector` / `Drawer` / `Timeline` | 首页与会话态切换正常，水位有数 | 组件级替换，旧组件保留到本批结束 |
| 4 | 设置三层（场景 / 模块 / 原始）+ 现有 `FieldSpec` 九个字段 | 13 项场景可调、6 项有预演（§5.13） | 独立组件，互不影响 |
| 5 | 细节补齐（§12 十四项）+ 托盘 + 安装器 | 逐条对 §13 验收清单 | 逐项独立 |

**第 1 批是唯一会同时影响全部界面的改动**，也是风险最高的一步。建议单独提交，提交信息写明"仅样式层，无逻辑改动"，便于日后定位视觉回归。

**不要在第 1 批里顺手改组件**。一旦配色与布局同时变，出问题时无法判断是色板错了还是布局错了。

**第 3 批的新旧共存策略**：`Thread.tsx` 改造成 `Timeline.tsx` 时，先把 `Thread.tsx` 原样保留并从 `App.tsx` 切走引用，等第 3 批验收通过再删除。这样改造失败可以直接切回。

**第 4 批的前置条件是零**：`FieldSpec` 不需要新增任何字段，所以第 4 批可以直接开工，不必先改 schema。这一点值得写清楚，因为早期方案曾打算先给 `FieldSpec` 加五个字段再写界面，而那是**自找的一轮返工**。

**为什么五个字段一个都不加**：

| 想加的 | 本来想解决什么 | 已经有解，不必加 |
| --- | --- | --- |
| `label` | 中文名 | `doc` 就是给设置页直接显示的一句中文（类型注释原文）。字段名做标题、`doc` 做说明，比再加一个 `label` 少一处可漂移的真源 |
| `unit` | 数字单位 | 单位应当写进 `doc`。单独一个 `unit` 会让 `min/max` 与"用户看到的数"分离，滑杆读数的换算就有两处真源 |
| `group` | 段内分组 | `advancedOnly` 已经实现了唯一有意义的分组（普通 / 高级），561 个高级字段靠它分流。再加 `group` 等于承认段内还有别的层次，而 122 个段里没有一个需要 |
| `tier` | 露出层级 | 露出层级由**界面**挑（§5.13 的 13 项），不由插件声明。插件声明 tier 会让"哪些设置该露出来"这个产品判断散落进 122 个插件 |
| `effect` | 生效时机（立即 / 重启） | 生效时机由插件在实际读取时决定，声明一份静态的 `effect` 必然有插件写错。界面用「改完立刻生效」为前提，需要重启的少数几项在 `doc` 里写一句 |

**唯一真实存在的越界情况**：`ondra-memory-intake` 与 `ondra-crisis` 各自在 `settings.ts` 里定义了带 `label` 的**局部** `FieldSpec` 类型（共 7 处 `label`），没有派发到全局类型。它们渲染时会缺标题，界面用「字段键名」兜底显示即可。**不为此改全局类型**——为了两个插件的局部写法去动 1168 个字段共用的类型定义，是把局部妥协放大成全局约束。

## 12. 细节规范

以下每一条都会在实际使用中被感知到，但容易被"先做主体、细节以后补"跳过。细节不补，界面就会在第三天才显出廉价感。

### 12.1 滚动条

| 项 | 值 |
| --- | --- |
| 形态 | overlay，不占布局（Windows 常驻滚动条会吃掉 17px） |
| 宽度 | 常态 8px，悬停 12px |
| 轨道 | 透明 |
| 滑块 | `--alias-scrollbar-bg-l2`，圆角 4px，两端各留 8px 内缩 |
| 内容让位 | 滚动容器右侧内边距 8–12px（见下方定稿说明） |
| 出现 | 滚动时用 fast 淡入；停止滚动 800ms 后，用 slow 淡出 |
| 惯性 | 不做回弹（rubber-band）。macOS 原生回弹与 Windows 不一致，统一去掉 |
| 滚动单位 | 鼠标滚轮 1 格 = 3 行（约 60px）；触控板按物理距离 |

> **定稿说明一：滑块不能是 `--static-line`。** 本表先前写的是 `--static-line`（`#E4DFD3`），实测它压在 `paper-0` 上只有 **1.31:1**、`paper-1` 上 1.21:1——那不是「浅」，是看不见。滑块是「还要不要继续读」的位置指示，属于必须可见的控件。定稿改为 `--alias-scrollbar-bg-l2`（浅色 `#B4AD9E`，2.20:1；深色 `#5A635F`，2.91:1）。深底需要略高的对比才显得和浅底一样清楚，所以两端不是同一个数值，而是同一档视觉重量。悬停态压深到 `ink-4`，给出「我正在拖它」的确认。
>
> **定稿说明二：内容必须让出 8–12px。** 本表只说了「滑块不占布局」，没说内容该让多少。结果是 overlay 滑块会**压在文字上**——快捷键总表里实测把右侧键帽的「Enter」吃成了「Ent」。规则补一条：滚动容器右侧留 8–12px 内边距。这个量不是拍出来的，它等于「滑块悬停时最宽 12px + 右缘 2px 偏移」——留够了，滑块加宽时也不会碰到字。

### 12.2 文本选择与光标

| 项 | 值 |
| --- | --- |
| 选中底色 | `--static-teal-600` 20% 叠加 |
| 选中文字色 | 不变（不反白） |
| 光标 | 2px 宽，`--static-teal-600`，闪烁周期 1.06s（HIG 默认） |
| 可选区域 | 消息正文、代码块、输入框、检查器读数 |
| 不可选 | 标题栏、双脊图标、日期分隔行、按钮文字 |

读数数字不可选是刻意的：它们会被频繁扫视，误选会打断阅读。

### 12.3 输入法

| 场景 | 规则 |
| --- | --- |
| 组合中按 Enter | 不发送，交给输入法上屏。判据是 `event.isComposing` |
| 组合态样式 | 下划线由系统绘制，不自绘、不加背景 |
| 高度变化 | 组合态出现时输入框不跳动，单行态预留一行高度（76px 已含） |
| 候选框位置 | 由系统跟随光标，不干预 |
| 中文标点 | 不做自动替换（用户输入什么就是什么） |

### 12.4 内容排版

| 类型 | 规则 |
| --- | --- |
| 代码块 | 13px Menlo，底色 `--static-paper-2`，圆角 8，内边距 12，右上角复制按钮悬停出现 |
| 行内代码 | 12px 等宽，底色 `--static-paper-2`，圆角 4，左右内边距 4 |
| 表格 | 最大宽 588，超出横向滚动；表头 12px 500，正文 13px |
| 图片 | 最大宽 588，圆角 8，点击打开浮层放大；不自动裁剪 |
| 链接 | `--static-teal-600`，常态无下划线，悬停出现下划线，点击交系统浏览器 |
| 引用 | 左侧 2px `--static-line` 竖条，文字 `--static-ink-2`，左内边距 12 |
| 列表 | 缩进 20，项目符号用 `·`，不用圆点图片 |

正文 588px 下，代码块与表格是唯一允许横向滚动的元素。**不允许整条消息横向滚动**。

### 12.5 空状态

| 位置 | 文案 |
| --- | --- |
| 首页 | 不出现空状态，首页本身就是空状态 |
| 有会话但无消息 | 居中一行 12px `--static-ink-3`「从哪儿说起都行」 |
| 检查器·记得的事 | 「聊两句就有了」 |
| 检查器·此刻 | 不显示 0，显示「还没测到」 |
| 偏好设置·通道 | 「还没有连接任何通道」+ 「查看如何连接」链接 |
| Composer·模型 | 显示「未选择」，点击直接进偏好设置·模型 |

空状态一律用引导句，不用"暂无数据"。

### 12.6 时间与日期

| 场景 | 格式 |
| --- | --- |
| 日期分隔 | 今天 / 昨天 / 11 月 6 日 周四 / 2025 年 11 月 6 日 |
| 相对时间 | 刚刚 / 3 分钟前 / 昨天 / 上周 / 上个月 |
| 绝对时间 | 24 小时制，`14:30`。不跟随系统 12 小时制，避免「下午 2:30」在中文界面里过长 |
| 消息时间戳 | 不显示。只在日期分隔行与记忆薄片中出现 |
| 相处天数 | 时间轴首屏日期行右侧，`第 12 天` |

### 12.7 复制、引用与链接

| 操作 | 规则 |
| --- | --- |
| 复制整条消息 | 消息悬停右上出现 20px 复制按钮，120ms 淡入 |
| 复制代码 | 代码块独立按钮，复制纯代码不含围栏 |
| 复制反馈 | Toast「已复制」，时长走 §5.10 的成功档（2.4s），不为复制单开例外 |
| 引用 | 选中文字后浮出「引用」按钮，点击后插入 Composer：`> 摘录` + 空行 + 光标 |
| 外部链接 | 交系统浏览器，不在应用内打开（应用内无浏览器，`browser-pane` 仅用于插件自身场景） |

### 12.8 窗口尺寸与断点（仅电脑三端）

移动端无窗口尺寸概念，按 §10.1 的容器查询走。本表只描述 macOS / Windows / Linux 拖拽窗口时的行为。

| 宽度 | 行为 |
| --- | --- |
| 820（电脑端基准 = 最小） | 双脊常驻，检查器与抽屉覆盖式展开 |
| 960 | 正文仍 588，两侧留白由 64 增至 134 |
| 1100 及以上 | 检查器可常驻展开（不覆盖），主列仍 588 不拉宽 |
| 高度 < 560 | 输入区上间距 12 → 8，消息区优先保留 |

正文宽度永不随窗口变宽而增长。这是可读性约束，不是响应式缺陷。

### 12.9 焦点、失焦与休眠

| 场景 | 行为 |
| --- | --- |
| 窗口失焦 | 呼吸暂停；Spine 水位降到 60% 不透明度 |
| 重获焦点 | 用 `--motion-base` 恢复，不重播历史消息 |
| 离开超过 10 分钟 | 回到窗口时，在时间轴当前底部插入一行 11px 灰字「你离开了 23 分钟」 |
| 系统休眠唤醒 | 不补发错过的主动消息，只按当前时间重新排期 |

### 12.10 托盘与系统通知

| 项 | 规则 |
| --- | --- |
| 托盘图标 | 16 / 32 / 64 三档，由 `/icon.svg` 生成 |
| 托盘菜单 | 打开空谷 / 今天 / —— / 静音 1 小时 / 退出 |
| 单击托盘 | 显示并聚焦主窗口 |
| 未读数 | 不显示。陪伴产品不做未读压力 |
| 系统通知 | 默认关闭。开启后仅用于「她主动开口」，且同一天不超过打扰预算 |

### 12.11 系统偏好响应

| 系统设置 | 响应 |
| --- | --- |
| 减少动态效果 | 呼吸停止；浮现与收起瞬时；落字整段出现；图标形变直接换图 |
| 增强对比度 | 线宽 0.5 → 1px；`ink-4` 提升为 `ink-3` |

| 降低透明度 | 不使用毛玻璃，无需响应 |

### 12.12 声音

| 项 | 规则 |
| --- | --- |
| 默认 | 关闭 |
| 开启后 | 只有三种音：发送、她开口、错误。不做打字音、不做环境音 |
| 音量 | 独立于系统音量，设置内可调 |
| 静音 1 小时 | 托盘菜单入口，Spine 显示「静音」 |

### 12.13 加载与错误分级

| 级别 | 场景 | 形态 |
| --- | --- | --- |
| 骨架 | 连接宿主（通常 < 1s） | 三块纯色矩形，不做闪光 |
| 内联 | 发送失败、模型报错 | 消息流内 12px 红字条 + 「重试」 |
| 提示条 | 用户主动操作失败（切模型、保存设置） | Toast 错误态，4s |
| 故障页 | 宿主连不上、内核崩溃 | 替换主列内容，保留双脊，含「重试」「查看日志」 |

连接超时阈值 8 秒。超时前不显示任何"正在连接"文字，避免本地启动场景下的无谓焦虑。

### 12.14 拖拽与粘贴

| 操作 | 规则 |
| --- | --- |
| 拖文件进窗口 | 全窗出现 2px teal 虚线框 + 居中提示「松手添加附件」 |
| 拖出窗口 | 不支持 |
| 粘贴图片 | 自动转附件，48 × 48 缩略图 |
| 粘贴超长文本 | 超过 8000 字时提示「内容较长，确认发送？」 |
| 粘贴富文本 | 只取纯文本，保留换行，丢弃样式 |

### 12.15 首次与空白的差别

"空状态"和"第一次"是两件事。空状态是"这里暂时没有内容"，第一次是"你还不知道这里能做什么"。前者给一句引导语就够，后者必须给一条可执行的路径。

| 场景 | 第一次 | 之后为空 |
| --- | --- | --- |
| 记忆抽屉 | 三张示例薄片（灰色、不可点）+ 一句「聊两句，这里就会自己长出东西」 | 「聊两句就有了」 |
| 剧场抽屉 | 「这里会存下你们聊过的片段」+「看看示例」 | 列表为空 + 日期分组标题 |
| 记忆图谱 | 直接展示当前已有的少量节点，不做"暂无数据"——有节点就画，哪怕只有 3 个 | 同 |
| 周报 | 「满 7 天后生成第一份」+ 进度「已 3 天」 | 同上 |
| 通道设置 | 三张卡片：微信 / QQ / 飞书，各带一句"用来做什么" | 已连接列表 |
| 模型设置 | 三个来源并列，免费模型已选中并标注「现在就能用」 | 当前模型 + 切换 |
| 诊断页 | 默认折叠，只有「导出诊断包」一个按钮 | 同上 |

**判断依据**：`localStorage` 记录"是否首次进入该功能"，每个功能一个键（`ondra.seen.{feature}`）。**不用全局的单一标记**——用户可能很早就开过记忆抽屉，但一年后才第一次开剧场。

### 12.16 设置的控件规格

§5.13 定了五种控件对应的 `kind`，但没说每个控件画成什么样。这一节补齐，因为控件的外观不一致，比配色不对更显廉价。

**滑杆**

| 项 | 值 |
| --- | --- |
| 轨道 | 高 2px，`--static-line`，圆角 1 |
| 已填充 | 高 2px，`--static-teal-600`，左起至滑块 |
| 滑块 | 直径 14，白色，0.5px `--static-line` 描边，`--shadow-lv3` 极淡 |
| 热区 | 高 32（上下各扩 15） |
| 锚点标签 | 轨道下方均分，11px `ink-3`，如「安静 / 正常 / 黏人」 |
| 拖动 | 无过渡（A6），松手后 120ms 回弹到最近档（若为分档滑杆） |
| 连续态 | 用于 `kind: number` 且 `min`/`max` 跨度大的字段（如 1–3650 天）。此时**没有分档**，滑块可停在任意整数，右侧显示真实数值而非档位名。分档态（有锚点标签）与连续态的判据见 §5.13 的控件判据表 |
| 键盘 | `←/→` 步进，`Shift` 加速 10 倍，`Home/End` 到两端 |
| 无障碍 | `role="slider"`，`aria-valuemin/max/now/valuetext`（valuetext 是语义锚点，不是数字） |

**分段控件**

| 项 | 值 |
| --- | --- |
| 外框 | 高 28，`--static-paper-2` 底，圆角 8，内边距 2 |
| 滑块 | `--static-paper-0` 底 + 0.5px 描边，圆角 6，`transform` 移动（A4） |
| 文字 | 12px，未选中 `ink-2`，选中 `ink-1` |
| 等分 | 是。候选项文字长度差异大时仍等分（不等分会让人误判点击区） |
| 数量 | ≤ 4。超过 4 换下拉，不换更小的字 |

**开关**

| 项 | 值 |
| --- | --- |
| 尺寸 | 36 × 20，圆角 10 |
| 关 | 轨道 `--static-paper-3`，滑块白色 16，左 |
| 开 | 轨道 `--static-teal-600`，滑块右移 16，`transform`（A5） |
| 生效范围 | 右侧永远显示 11px `ink-3`「立即」或「重启后」，**不留空** |
| 拖动 | 不可拖，只可点击（开关能拖是移动端习惯，指针环境反而易误触） |

**曲线（24h 节律）**

| 项 | 值 |
| --- | --- |
| 画布 | 宽 268（抽屉内满宽减内边距），高 80 |
| 横轴 | 0–24 时，每 6 时一条 0.5px 竖线 |
| 纵轴 | 0–1（清醒度），不画刻度 |
| 曲线 | 2px `--static-teal-600`，下方 12% 填充渐隐至透明 |
| 控制点 | 两个：`rest-start`（休息起点）与 `rest-end`（休息终点）。12px 实心圆，拖动时 16px 并加环。**两点之间是暗色（她在休息），两点之外是亮色（她醒着）** |
| 吸附 | 15 分钟为步长（因为存的是 `HH:MM` 字符串，见 §5.13 第 8 项） |
| 跨零点 | 起点晚于终点时（默认 23:30–07:00 就是这种情况）画成**两段暗色**：从起点到 24:00、从 00:00 到终点。不要画成一段跨越整个画布，那会让人以为整夜都醒着 |
| 键盘 | `Tab` 在两个点间切换，`←/→` 各调 15 分钟 |
| 提示 | 拖动时上方浮出「23:30 休息」/「07:00 醒」，松手 1.5s 后消失 |
| 输出格式 | **必须产出 `HH:MM` 两位补零字符串**，因为 `life-rhythm` 的 `pattern` 是 `^([01]\d\|2[0-3]):[0-5]\d$`。`7:00` 会被插件拒掉 |

**原始层键值行**

| 项 | 值 |
| --- | --- |
| 行高 | 32 |
| 键名 | 13px 等宽（`Menlo`），`ink-1` |
| 类型与默认值 | 11px `ink-4`，同行右侧 |
| 来源插件 | 11px `ink-3`，可点击跳转到模块层对应段 |
| 值编辑 | 点击值进入编辑，`Enter` 提交，`Esc` 取消 |
| 校验失败 | 值下方红字一行，`Enter` 不提交 |
| 已改标记 | 键名左侧 2px teal 竖条 |

**五种控件共用的元数据行**（12px `ink-3`，位于控件下方 6px）：

```
当前值 · 默认值 · 来源插件 · 已改/未改
```

四项都用文字，不用图标——图标需要学习，文字不需要。

## 附录 A：134 个插件的分类与露出

本附录的数据**全部来自插件自身**：每个 `cordis-host/plugins/*/README.md` 的首行元信息。它不是设计阶段编的分类，是运行时的真实清单。

**读表前先记住三个数，别混**：

| 数 | 含义 | 怎么算出来的 |
| --- | --- | --- |
| **134** | 可装载插件数 | `MIGRATED_PLUGIN_COUNT`；等于 `ondra-core` 里 `members` 数组的条目数 |
| **134** | 本附录逐行登记的条目数 | A.0–A.10 合计。**等于上一条**，`members` 里每一个都有对应行 |

**这三个数容易算错的地方**（都是实测踩过的）：

- 目录有 **137** 个，其中 `ondra-core` 是清单本身、`desktop-bridge` 与 `dsh-client` 是桥接，三者都不在 `members` 里。137 − 3 = 134。
