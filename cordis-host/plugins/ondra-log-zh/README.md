# ondra-log-zh

> O-004 · L0 基座 · 〔研〕自研 · 服务键 **`ondra-log-zh`**（连字符，非 `ondra:log-zh`）

中文日志的**双层写入者**：给人看的句子一层，给排障的代码日志一层，
按大小 4MB×3 轮转，同一错误高频重复时自动折叠（手册 §8.3「单进程写放大保护」）。

## 职责

- 提供 `ondra-log-zh` 服务：`human()` / `info()` / `warn()` / `error()` / `debug()` 写中文层，
  `stats()` 读统计，`tailHuman()` 取最近若干行供界面日志视图。
- 桥接全仓 `ctx.logger` 的结构化消息进**代码层**（`ctx.logger.exporter()`，自带 effect 生命周期）。
- 两层分别轮转：`ondra.log` → `.1` → `.2` → `.3`，超出保留数丢最旧；连同当前文件共 4 份，
  总量上界 `4MB × 4 = 16MB`。
- 写盘连续失败 3 次 → 转「仅内存」模式，保留最近 500 行供界面查看，**不再重试写盘**。

## 明确不负责

- **不做日志查看界面**：日志视图在应用外壳里（原 O-096 已随 L8 下线），本插件只提供 `tailHuman()` 数据。
- **不做探针与健康判定**：那是 O-057 `ondra-channel-health`（且它必须不依赖被观测进程存活）。
- **不改 Cordis 的日志格式器**：只注册一个 exporter 旁路接收，不动 `Logger.format()`。
- **不写业务日志内容**：谁产生事件谁调 `human()`，本插件不替人编句子。
- **不做加密**：手册 §17-3 明确不给记忆库加密，日志同理；落盘权限由 O-002 保证 0700/0600。

## 配置（全部有默认值）

| 字段 | 默认 | 说明 |
|---|---|---|
| `logDir` | `''`（自动） | 日志目录绝对路径；留空则问 `path-layout` 的 `ensure('logs')` |
| `humanFileName` | `ondra.log` | 中文层文件名 |
| `codeFileName` | `ondra-code.log` | 代码层文件名（**不得与中文层同名**，校验器会拒） |
| `maxFileBytes` | `4194304`（4MB） | 单文件上限，下限 64KB |
| `maxRotated` | `3` | 保留历史份数；总量上界 = 4MB×(3+1) = 16MB |
| `codeLevel` | `info` | 代码层最低级别（`error` 最严、`debug` 最松） |
| `bridgeLogger` | `true` | 是否把全仓 `ctx.logger` 接进代码层 |
| `dedupe` | `true` | 是否开启写放大保护 |

## 关键取舍（每条都有代价）

1. **两层分文件，不混写。**
   混在一个文件里，用户翻日志第一屏永远是 `[verbose] payload chunk 3/17` 这种噪声。
   中文层只收显式 `human()` 的句子，代码层收全仓结构化消息。

2. **按大小轮转，不按日期切分。**
   日期切分在「一天写 200MB」时没有上界；按大小切给出确定上界 16MB，
   磁盘不会被日志吃干，这是可预测性的下限。

3. **写放大保护按「级别 + 来源 + 消息模板」去重，不按整条消息。**
   整条消息带时间戳，永不重复，保护就失效了。窗口 1 秒，**由独立定时器每秒扫一次**，
   到期就把「另有 N 条相同内容已折叠」补写出去。
   早先版本只在「同一个键下次出现」时才补——错误爆发完就停时，那条补充永远写不出来，
   用户只会看到「只错了一次」。这是本轮修掉的第一个真问题。

4. **同步写，不用异步。**
   `appendFile` 是异步的，进程崩溃时会丢尾部日志，而崩溃前最后几行恰恰最有价值。
   代价是短暂阻塞事件循环，所以「写放大保护 + 文件大小缓存」必须同时到位——
   早先版本每写一行都 `statSync` 一次，1000 条/秒就是 1000 次系统调用，
   把保护省下的开销原样吃回去。这是本轮修掉的第二个真问题。

5. **连续 3 次写盘失败转仅内存，不再重试。**
   磁盘满了还死磕，只会让每次日志调用都卡一次 IO，最终把主对话拖死。
   降级后 `stats().memoryOnly` 为 true，并立刻用宿主 logger 打一条 `error`。

6. **跳过自己的命名空间。**
   日志插件写日志 → exporter 收到 → 再写日志 → 无限递归。这一条不写就是进程卡死。
   另外 exporter 整体包 `try/catch`：它被宿主的 `logger.info()` **同步调用**，
   抛一个 `JSON.stringify` 的循环引用错会直接冒泡进业务代码。这是本轮修掉的第三个真问题。

7. **`start === end` 类窗口判定不在本插件**：`withinWindow` 归 O-003，本插件只消费它的
   `format()`，不自己算日期。

8. **级别过滤全部收回本插件，`Exporter.levels` 固定放行到底。**
   Cordis 的 `LoggerLevel` 是 `ERROR 0 / INFO 1 / WARN 2 / DEBUG 3`——**info 比 warn 还轻**，
   与所有人的直觉相反。若把本插件的 `LEVEL_RANK`（`error 0 / warn 1 / info 2 / debug 3`）
   直接塞进 `Exporter.levels.default`，`codeLevel='info'` 时会把 info 全部挡掉、只留 warn 以上。
   所以 `levels.default` 固定给 `3`（放行最多的一档），再用显式映射表在本插件内部过滤。
   这是本轮修掉的第四个真问题。

## 边界

- 属于 L0，崩溃后果是「谁也不知道出了什么问题」，因此不引入任何第三方依赖，
  只用 `node:fs` / `node:path`。
- 与 `path-layout` / `clock` / `identity` 的依赖方向单一：只读它们的服务，反向禁止。
- 不缓存统计：`stats()` 每次现算，避免「统计与实际写入不一致」这类最难查的偏差。

## 已知限制

1. **`tailHuman()` 每次整文件读入再切尾部**。4MB 文件可接受；若把 `maxFileBytes`
   调到几十 MB，界面日志视图会明显卡顿。真要做流式倒读，需要自己实现「从尾部按块读」，
   本轮不做，**已登记**。
2. **`stats().suppressedLines` 只统计已结算的窗口**。当前 1 秒窗口内的计数要等
   `sweep()` 才落账；也就是说刚爆发的那一秒里，数字会暂时偏小。刻意取舍：
   为了读一个统计数字而在每次写入时遍历全部桶，会把写放大保护本身变成新的开销。
3. **写放大保护有键上限 2000**。超限按「开始时间最早」淘汰，被淘汰桶的计数仍计入总数，
   但**不再补写汇总**——那正是上限要防的洪泛。极端情况下（每秒上千种不同的错）
   会看到总数涨、却没有逐条补充行。
4. **仅内存模式下代码层只留 500 行、且没有对外读取接口**。`tailHuman()` 只服务中文层；
   代码层的内存副本只为「不让缓冲无限涨」，不给界面读。要看代码层，必须先修好磁盘。
5. **轮转期间的写入可能丢一行**。`rotate()` 用 `rename`，单进程同步写下不存在并发窗口；
   但若同一数据目录被两个进程同时写，最坏情况各丢一行。**多开进程不在支持范围**。
6. **`logDir` 走配置时只 `mkdirSync`，不收权限**。权限归 O-002；若用户在数据根之外
   指定日志目录，该目录权限由用户自己负责。
7. **不做压缩归档**。`.3` 满了直接删，不 gzip：压缩要额外的 CPU 与临时空间，
   而日志的价值窗口只有最近几小时。

**档位判定（§1.8）**：〔研〕自研。生态里的日志库（`pino` / `winston`）解决的是
「多传输 + 结构化 + 采样」，**没有**「中文用户层与代码层分离」「写放大保护后主动补计数」
「失败转仅内存且不重试」这三条产品级约束；引入它们反而要多写一层适配。
Cordis 自带的 `LoggerService` 是不可替换的宿主服务，本插件只做旁路消费，不重写。

## 多方案分支说明（§12）

**不涉及分支。** 日志只有一种正确的写入姿势（同步追加 + 大小轮转 + 失败降级），
不存在两套口径并存的合法场景。

时间戳时区也不做分支：优先 `ondra-clock`，缺席退回进程本地时区。
这是**降级链**而不是两套实现——`ondra-clock` 是唯一真源，本插件只做兜底。
若将来要支持「日志单独指定时区」，正确做法是加一个 `timeZone` 配置并复用
`Intl`，**不得**新增第二个日志服务键。

## 隔离五问（§16.4）

1. **关掉我，谁受影响？** 只有我自己。其他插件仍可正常 `ctx.logger(...)`（那是宿主能力），
   只是没有中文层、没有文件落盘、没有轮转。界面日志视图会拿到 `undefined`
   并应显示「日志服务未启用」。
2. **我的状态存在哪？** 磁盘：`<数据根>/logs/ondra.log` 与 `ondra-code.log`（含 `.1`–`.3`）；
   内存：统计计数、写放大窗口表（上限 2000 键）、仅内存模式下的两份 500 行环形缓冲。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.log-zh`。
   **注意**：我自己崩了就无法用自己记日志，所以 `apply` 里的关键失败都先走
   `ctx.logger(...)`（宿主控制台），再决定是否降级——这条路径不依赖本插件已就绪。
   进一步的可观测性由 O-077 `ondra-startup-check` 兜。
4. **我依赖谁？缺席时怎么降级？** 依赖 `ondra-path-layout`（软，缺席→仅内存）、
   `ondra-clock`（软，缺席→本地时区）、`ondra-identity`（软，缺席→内置命名空间）。
   三者都不影响服务本身可用。
5. **我和同域的谁共享可变状态？** 没有。与 `path-layout` 只共享目录路径这一个只读字符串，
   与 `clock` 只共享格式化函数。
