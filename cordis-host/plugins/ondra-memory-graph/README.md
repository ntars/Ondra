# ondra-memory-graph

> O-015 ｜ L2 记忆域 ｜ 档位 **〔研〕自研** ｜ 批次 B2（记忆纵深 P0 第四项）

记忆之间「谁和谁有关」。一句话职责：**让「想起一件事，顺手想起另一件」有依据——但只依据她真的见过它们一起出现。**

---

## 职责

1. **建边 / 加固**：同一对记忆的同一关系只存一行（确定性主键 `from~to~relation`），重复建边即加固。
2. **1 跳邻居**（双向）：`neighbors(id, { minWeight, includeSurreal, limit })`。
3. **批量关联度**：`relatedness(ids, seeds)` —— **O-014 的图谱因子直接吃这个**。
4. **扩散**：`diffuse(seeds, { maxRings })`，圈权重 `[1, 0.55, 0.3, 0.16]`，默认 1 圈。
5. **边衰减**：每满 90 天 ×0.5，**按 `decayed_at` 游标结算**。
6. **软剪枝**：权重 <0.05 压到 0.01，`surreal` 与 `approved` 豁免。
7. **清孤儿边**：`forgetOf(id)` —— 记忆被 `forget()` 之后把它的边一起删。

## 明确不负责

- **不写 `memory_fact` 的任何一列**。裁决⑪：条目衰减归 O-013，边权归本插件，两不混。本插件对记忆表是**纯读**（只在验端点时 `getFact`）。
- **不算召回排序**。图谱因子怎么进排序是 **O-014** 的事；本插件只回答「这两个有多相关」。
- **不做荒诞联想的生成**。`surreal` 边的**建边时机与内容**归 **O-019** 做梦；本插件只提供容器与「永不进检索」这条硬规则。
- **不装定时器**。衰减 / 剪枝是写操作，时机由 **O-019 夜巡**显式调用。理由与 O-013 的 `autoScan` 默认关相同。
- **不做实体抽取 / NER**。「哪两条记忆该建边」由 O-011 提炼与 O-012 判重决定，本插件只落库。
- **不建会话、不写 `app_session_log`**（master-plan §6 禁令 5）。

## 服务键

| 项 | 值 |
|---|---|
| 服务键 | **`ondra-memory-graph`**（连字符，符合 `^[a-z][a-z0-9_-]{1,63}$`） |
| 提供 | `ctx.provide('ondra-memory-graph', service)` |
| 消费 | `ondra-store-sqlite` / `ondra-store-memory`（**硬依赖**：都没有则 `available=false`）；`ondra-memory-core`（软，只验端点）；`ondra-config-schema`（软）；`ondra-identity`（软，日志命名空间） |

依赖缺席一律不抛、不阻断：服务照常注册，`available=false` + 原因码
（`disabled` / `no-store` / `schema-failed`）。这样 O-014 能区分「没装图谱」与
「装了但存储不可用」——两种情况都该让图谱因子退出归一化，但排查方向完全不同。

## 表结构

`memory_link`（一张表，四个索引）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | `from~to~relation`（规范方向 + 关系）。确定性主键，让建边可以直接 `upsert` |
| `from_id` / `to_id` | TEXT | 两端记忆 id。**只存一行**，规范方向 = 字典序小的当 `from` |
| `relation` | TEXT | 关系名（开放字符串，见下） |
| `weight` | REAL | 0–1 |
| `hits` | INTEGER | 被加固次数 |
| `last_fired_at` | INTEGER | 最近一次加固 / 被扩散用到 |
| `decayed_at` | INTEGER | **衰减游标**（见「两条相反的衰减」） |
| `created_at` | INTEGER | 建边时间 |
| `approved` | INTEGER | 人工批准 → 软剪枝豁免 |
| `surreal` | INTEGER | 荒诞联想边 → 永不进检索 |

**不建外键**：两端指向 `memory_fact.id`，但记忆会被真删；外键级联会把
「她忘了一件事」变成「她忘了那件事的所有关联」，而后者该由 `forgetOf()` 显式做。
孤儿边由 `forgetOf()` 清，清不掉也只是多一条查不到端点的边，不会让写入失败。

## 三个关系预设（手册只给了这三个）

| 关系 | 初值 | 每次加固 | 进检索 | 剪枝豁免 |
|---|---|---|---|---|
| `same_topic` 同主题 | **0.72**（手册区间 0.72–0.85 的下沿） | **+0.05** | 是 | 否 |
| `cooccur` 共现 | **0.15** | **+0.10** | 是 | 否 |
| `surreal` 荒诞联想 | **0.03** | 不加固 | **永不** | 是 |

**共现边要加固 3 次才越过扩散门槛 0.4**（0.15 → 0.25 → 0.35 → 0.45）。
这是刻意的：「见过一次」不足以成为「想起来」的依据。手册另有一句
「用 0.05 需 8 晚才越线」——那是把步长取 0.05 时的账，本插件用 0.10，故 3 次。

### 第四边没有名字（待裁决）

台账 O-015 写「图谱四边」，但手册与语料里能逐字查到的关系名**只有三个**。
本插件**不编第四个名字**：`relation` 是开放字符串，未知关系走
`defaultInit 0.5 / defaultStep 0.05` 这组中性默认。第四个名字一旦裁决下来，
加一条 `RELATION_PRESETS` 即可，不用改代码结构。
→ 已在台账备注里登记为「待裁决：第四边命名」。

## 两条相反的衰减（这是本插件最容易被抄错的地方）

| | O-013 记忆条目 | O-015 图谱边 |
|---|---|---|
| 形状 | **闭式**：`0.5^(Δt/S)` | **步进**：每满 90 天 ×0.5 |
| 游标 | **不需要**（扫一次 = 扫一百次） | **必须有** `decayed_at` |
| 没有游标的后果 | 无（闭式函数自洽） | 重复乘算成 `0.5^N`，一次夜跑把图跑塌 |

手册 §9.7 那句「必须带 `decayed_at` 游标」是针对**步进式**说的。
本插件是步进，所以必须有；O-013 是闭式，所以不该有。**两个插件对同一件事采取相反做法，
是因为衰减形状不同，照抄会错。**

游标还有一条细节：**只推进整间隔**（`advancedCursor`），不推到 `now`。
推到 `now` 会把「剩 89 天」的零头抹掉，于是每条边每年多衰减一次——
一年看不出，三年后整张图都塌了。

## 多方案分支说明（master-plan §14）

本插件**不设运行期分支**——它落在 §14 的第一档「能融会贯通 → 融」：

| 表面上的多方案 | 怎么融的 | 没有做成分支的理由 |
|---|---|---|
| 「1 跳」与「1–3 圈扩散」 | 圈数是 `maxRings` 参数（默认 1），圈权重表 `[1, 0.55, 0.3, 0.16]` 固定 | 两者是同一个 BFS 的两种深度，不是两套算法。做成两套会出现「1 跳版本不认 `surreal` 排除」这类实现漂移 |
| 「三种关系」与「将来的第四边」 | `relation` 开放字符串 + 关系预设表；数值差异全部来自 `profileOf()` | 关系之间只差三个数（初值 / 步长 / 是否荒诞），没有行为差异。按关系写三份代码是最典型的「为一个字段抄三遍」 |
| 「步进衰减」与「闭式衰减」 | **不融**：本插件是步进（手册 §9.7 的边权），必须带 `decayed_at`；闭式归 O-013 的条目强度 | 这两者不是同一功能的两套实现，而是**两个不同对象**的衰减。融在一起就会让一边用错另一边的形状——见「两条相反的衰减」一节 |
| 「SQLite」与「内存后端」 | 只走表级 CRUD（`raw` 面刻意不用），两个后端同一份代码 | 一旦用上自定义 SQL 或 FTS，内存后端立刻失效，而它存在的理由正是「SQLite 打不开」 |

分区判定依据：§14.1 要求「能融就融，能兼容就做兼容层，都不能才做分支」。
本插件的差异全部是**参数**与**数据**，没有一处需要「同一接口两套实现」，
故不登记分支；`stats()` 里也没有「当前分支」这种字段——因为不存在分支。

## 隔离五问（master-plan §16.4）

1. **关掉我，谁受影响？** 只有 O-014 的图谱因子：它退出归一化，分母从 1.00 降到 0.89，其余四项照跑。召回本身不受影响。
2. **我的状态存在哪？** `memory_link` 一张表（走端口，落 `~/.ondra` 下的库）。计数器只在内存。
3. **我崩了，界面怎么知道？** 日志命名空间 `ondra.memory-graph`；`stats()` 给出 `available` / `reason` / `edges` / `byRelation` / `issues`。
4. **我依赖谁？缺席时怎么降级？** 存储端口缺席 → `no-store`，服务不可用；内核缺席 → 只少一道端点校验，建边照做。
5. **我和同域的谁共享可变状态？** 没有。边表是本插件独占的；`memory_fact` 只读。

## 已知限制

1. **第四边的名字未知**。手册与语料只逐字给出三个关系名，台账写「四边」。
   本插件不编名字，用开放字符串 + 中性默认兜住；裁决后加一条预设即可。
2. **扩散不沿路径连乘**。`score = 圈权重 × 边权`，三圈连乘（`0.16×0.4×0.4 = 0.026`）会让扩散形同虚设。
   代价是「第三圈的分」不代表真实路径强度，只代表「第几圈的折扣 × 最后一跳有多强」。
3. **`stats().avgWeight` 要全表遍历**。边多时（2 万条）会有一次几十毫秒的开销；
   它只给自检与界面读，不在对话路径上。
4. **`unlink(from, to)` 不带 `relation` 时只删三个已知关系**。未知关系的边要靠
   `forgetOf()` 或显式 `relation` 删——这是「不猜第四边叫什么」的直接代价。
5. **`maxEdges` 到上限是拒绝新建，不是淘汰**。删一条边比写不进去更难查；
   到上限时日志会告警，需要人工看是「库该扩」还是「建边逻辑在刷」。
6. **`surreal` 边永不进检索且没有开关**。若将来要让「荒诞联想」参与召回，
   必须新开一个显式的调用面（例如 `neighbors(..., { includeSurreal: true })`），
   而不是把这条硬规则改掉——后者会让 O-014 的图谱因子突然吃进 0.03 的噪声边。
