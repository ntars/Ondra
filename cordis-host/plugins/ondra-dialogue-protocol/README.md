# ondra-dialogue-protocol

> O-034 · 对话链 · 档位〔研〕 · 服务键 `ondra-dialogue-protocol`

一整轮回复不是一句话，而是**五帧**。这个插件只干一件事：把帧的形状、跨帧纪律与编解码定死在一处。

---

## 一、职责

1. 定义五种帧：`text-delta` / `text-replace` / `crisis` / `usage` / `done`（手册 §9.5，master-plan §9.5）。
2. 定义结束原因四值闭集：`stop` / `aborted` / `error` / `length`，并提供上游 `finish.reason.kind` 的**唯一一份**映射。
3. **跨帧纪律**：一个回合一个 writer，自带序号；`done` 是唯一终帧；`usage` 与 `crisis` 各最多一次。
4. 编解码：一行一帧（NDJSON），给通道转发与界面调试用。

## 二、明确不负责

- **不做业务判断**：不判断「这句该不该说」、不判断危机等级是否成立。协议层只回答「这帧合不合法、还能不能继续写」。
- **不改写正文**：`text-replace` 是**告知**替换，不是由协议层算替换成什么。改写归 `ondra-filter-chain`（O-037）。
- **不落盘**：帧是流的一部分。会话不落盘，见 O-033 的边界。
- **不建 Session、不写 `app_session_log`**（master-plan §6 禁令 5）。
- **不注册 `ctx.llm` 事件**：帧是给界面与通道的**对外**协议，与上游 agent 事件流是两层东西。把两者接在一起，换个通道就要改对话链。

## 三、服务键与方法

```
ondra-dialogue-protocol        ← 连字符，不是 ondra:dialogue-protocol
```

| 方法 | 说明 |
|---|---|
| `frames` / `stopReasons` / `crisisLabels` | 三个闭集，只读，供界面与自检枚举 |
| `create(options?)` | 为一个回合创建 writer；总开关关闭时返回一个**立刻关闭**的 writer |
| `stopReasonOf(kind)` | 上游 `finish.reason.kind` → 四值闭集的**唯一一份**映射（O-033 消费它） |
| `validate(value)` | 单帧结构校验，纯函数，无副作用 |
| `encode(frame)` | 帧 → 一行 NDJSON；非法帧抛 `TypeError` |
| `decode(line)` | 一行 NDJSON → 帧；非法返回 `undefined`，**不抛** |
| `stats()` | `writers / frames / rejected / lastReject / codecCalls`，只在内存 |

`FrameWriter` 的五个方法**全部返回 `DialogueFrame | undefined`**：`undefined` 表示这一帧被拒（已终态 / 重复 usage / 重复 crisis / 空增量）。调用方拿到 `undefined` 就跳过，**不需要 try/catch**。

> 为什么是「拒绝」不是「抛错」：抛错发生在流式路径上，用户会看到半句话然后插件崩掉，而真正的错误信息在日志里——两边都没得到好结果。

## 四、配置

| 键（camelCase） | 段字段（kebab） | 默认 | 说明 |
|---|---|---|---|
| `enable` | `enable` | `true` | 总开关。关掉后服务照常注册，但 `create()` 返回立刻关闭的 writer |
| `allowEmptyDelta` | `allow-empty-delta` | `false` | 是否放行空文本增量。只有通道保活需要打开 |
| `verbose` | `verbose` | `true` | 写入被拒时打一行日志 |

`Config` 是 camelCase，而手册 §8.4 的配置键正则不认大写，所以段声明 / 用户层归一化 / 结果回填**三处全部由 `KEY_PAIRS` 派生**（见 `src/settings.ts`）。这是 O-035 起定下的模式，照抄是对的——它防的正是「改一处漏两处」。

## 五、关键裁决（每条都对应一个真实失败）

1. **`seq` 是全仓唯一的本地扩展**。手册只给了五帧的名字与业务字段，没给序号。加它是因为没有序号就无法区分「同一句话被重发」与「她真的说了两遍」——流式重连时最难查的一类重复。**已登记待裁决**：若主人判定不加，删掉 `seq` 即可，其余逻辑不动。
2. **序号从 1 起，不从 0 起**。`0` 在布尔判断里是假值，任何一处 `if (frame.seq)` 都会把第一帧吞掉，而这种 bug 只在「只有一帧」的极短回复里出现，最难复现。
3. **`seq` 跨类型共用一个计数器**。每类型独立会让「第 3 帧」有五种含义，乱序检测直接失效。
4. **`crisis` 不是终帧**。危机提示之后仍可有 `done`（一次完整回合总要收尾），也允许后面有正文（提示之后补一句安抚）。协议层刻意不替业务决定「危机时必须停」——那是 O-037 与通道层的事。
5. **`usage` 与 `crisis` 各最多一次**。重复上报会让下游重复累加（账单翻倍）／让用户以为出了两件事。
6. **未知 `finish.kind` 一律落到 `stop`，不新增第五个值**。界面对未知值只能是「静默按 stop 处理」，多一个值等于多一处分支，而分支永远没人写。
7. **`encode` 先校验再序列化**。直接把未知对象 `JSON.stringify` 出去，对端 `decode` 会失败并且不知道为什么——错误跑到了另一端。
8. **`decode` 不抛**。通道收到的脏数据不应该打断转发循环。

## 六、多方案说明

本插件不涉及 §12 的多方案能力（没有分支实现）。唯一一处「两种做法」是**编解码格式**：对象直传 vs NDJSON。选择**两者都提供**（`validate` 给进程内，`encode`/`decode` 给跨进程），因为它们的消费者不同（界面要对象，通道要一行一帧），不存在二选一。

## 八、隔离五问

1. **关掉我，谁受影响？** 只有我自己。O-033 会退回到自己内部的兜底 writer（同形状、不校验），对话照常进行。
2. **我的状态存在哪？** 只在内存（writer 的序号与终态、`stats` 的计数）。不落盘、不建表。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.dialogue-protocol`（有 O-001 时走 `identity.loggerName('dialogue-protocol')`）。`stats().lastReject` 给出最近一次拒绝原因。
4. **我依赖谁？缺席时我怎么降级？** 不依赖任何服务键。唯一软依赖是 O-005（配置四层）与 O-001（日志命名空间），缺席时分别退回插件实例配置与固定命名空间。
5. **我和同域的谁共享了可变状态？** 没有。writer 是每回合新建的，`live` 集合只为本插件的统计服务。

## 九、已知限制

1. **`seq` 是本地扩展**，不是手册原文。理由见裁决 1，登记待裁决。
2. **单帧校验看不到跨帧纪律**。`validate()` 只能答「这一帧结构对不对」；「写了两帧 done」要靠 `FrameWriter`，因为那需要状态。两者刻意分开，混在一个函数里就会有人拿它做流式校验。
3. **不校验文本长度**。一帧十万字也是「合法帧」——上限该由通道按平台限额切（`ondra-channel-kit` 的 `chunkText`），在协议层设一个魔数会让所有通道共用一个错误的上限。
4. **不提供重放/断线续传**。`seq` 让这件事**可能**，但续传需要服务端缓冲，而本产品不落盘会话（隐私优先）。通道侧要续传请自己缓冲未确认帧。
5. **`text-replace` 的可见文本由消费方维护**。协议层不记「当前可见文本是什么」，所以它无法校验「替换后的长度是否合理」。
