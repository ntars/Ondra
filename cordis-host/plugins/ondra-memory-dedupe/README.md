# ondra-memory-dedupe

> O-012 ｜ L2 记忆域 ｜ 档位 **〔研〕自研** ｜ 批次 B2（记忆纵深 P0 第三项）

在**写入之前**回答一个问题：这句话该新建一条、并进旧的、只记一次「又提了一遍」、报冲突，还是干脆不写。

一句话职责：**让「重复」与「补充」分开——重复不该占两条，补充不该被当重复丢掉。**

---

## 职责

1. **五分类判重**（手册 §2.2）：`add / merge / append / conflict / drop`。
2. **确定性前置**：候选为空直接 `add`，**不调模型**（省 4 倍成本）。
3. **候选截断到 5 条**（手册「候选 ≤5 条才交模型」）——本插件只做闸门，不发请求。
4. **合并走 `revise()`**：旧正文进 `oldText`，可回溯，**绝不 `forget()`**。
5. **决策日志**：每条裁决落一行，回答「我明明说过，怎么没记住」。
6. **存量疑似重复清单**（`scan()`）：只报告、不改内容（手册 §2.7「无损自动 + 有损人审」）。

## 明确不负责

- **不算寿命、不算显著度**。那是 **O-010**。传了 `salience` 就用传的，没传就让 O-010 按打分表算——
  **本插件不持有第二份打分公式**。
- **不做衰减、不排复习、不改 `archived`**。那是 **O-013**。本插件连 `sealed` 都只在
  `conflictPolicy='seal-old'` 时碰一次。
- **不调模型**。提示词与解析已在 O-011 有一份，再造一份就是第二真源。灰区只标 `needsModel`。
- **不做向量检索 / 语义相似度**。倒排与向量是 O-014 / O-122 的事；本插件只做字面包含度。
- **不建会话、不写 `app_session_log`**（master-plan §6 禁令 5）。
- **不自动合并存量重复**。合并要选主条、要改写正文，属「有损」，必须人审或 O-019 夜巡出单后处理。

## 关键取舍（每条都有代价，写在这里防后人踩回去）

### 1. 只用「包含度」一把尺子，不混余弦与 Jaccard

手册 §12.3 裁决⑥ 的原话是「口径不同不可互搬」。手册别处确实出现过
「余弦 0.85」「Jaccard 0.75」，但那是别的场景的标定值。两套阈值并存，
同一对记忆就会时而合并、时而建边——而这种「同一个问题两个答案」的错，
日志里全正常，只有用户觉得「她怎么一会儿记得一会儿不记得」。

包含度 = `|A∩B| / min(|A|,|B|)`，A/B 为**字符二元组**集合。选二元组不选分词：
分词器是一个会漂移的依赖，而「新词」会让它悄悄改变切分结果。

### 2. 「复述」与「补充」用**新颖度**分，不用包含度分

包含度只能回答「像不像」，回答不了「有没有新东西」。
「用户喜欢猫」与「用户喜欢猫和狗」的包含度是 1.0——只看包含度，两句必然同类。

- 都判成复述 → 永久丢掉「狗」；
- 都判成合并 → 每句重复都改写一次正文，`oldText` 被无意义地冲刷。

故再加一个「新颖度」= 新正文里旧条没有的二元组占比。≤0.25 算复述（只加固），
>0.25 算补充（并入主条）。

**但只看占比不够。** 占比会随句子变长而变小：

| 旧 → 新 | 新增二元组 | 占比 | 只看占比会判成 | 实际是 |
|---|---|---|---|---|
| `明天要考试` → `明天要考试了` | 1（「试了」） | 0.20 | 复述 | 复述 ✓ |
| `…橘猫` → `…橘猫，三岁了` | 3（「猫三」「三岁」「岁了」） | 0.20 | 复述 ✗ | **补充** |
| `明天要考试` → `明天要考试数学` | 2（「试数」「数学」） | 0.33 | 补充 ✓ | 补充 ✓ |

所以判「复述」要求**两个条件同时满足**：占比 ≤ `appendNovelty` **且** 新增个数
≤ `appendNoveltyGrams`（默认 2）。只用占比会漏掉长句里的真补充，
只用绝对量会放过短句里的真补充。

### 2.1 「太短不判重」的线是 4 字，不是 6 字

最初定 6 字，理由是不想合并「好的」与「好的呀」。但 6 字会把**中文里最常见的
5 字短句**（「用户喜欢猫」）整类挡在判重之外——它们永远每条新建一条。

4 字 = 3 个二元组，是包含度还能区分「相同 / 不同」的最小粒度；再短
（「嗯」「她怕狗」）包含度恒为 1.0，判了只会误合并，直接新建。

### 3. 合并**绝不**用 `forget()`

`forget()` 会写墓碑，而墓碑的语义是**「用户要求忘记」**。用它做合并的后果是：
同样的正文以后**永远写不进来**——她再听你说一遍这件事，也记不住了。

合并只改主条：`revise()` 把旧正文存进 `oldText`，`revisions+1`，S×1.3。
信息没丢，也没造出第二条。

### 4. 冲突靠「槽位替换」识别，不靠否定词

最初只用否定词与数字差异判冲突，漏掉了最典型的一类：
「用户住在上海」vs「用户住在北京」——两句都没有否定词、也没有数字。

改为**公共前后缀 + 中间差异段**，五道闸按顺序判：

| # | 闸 | 例子 | 结论 |
|---|---|---|---|
| 1 | 公共前后缀覆盖较长那条 ≥ `slotCoverage`(0.45) | `她说她怕狗` → `用户怕狗` 只覆盖 0.4 | 不是同一句式，不报冲突 |
| 2 | 两侧中间段全空 | 完全相同 | 交给「全等线」那条规则 |
| 3 | 只有一边有中间段 | `喜欢猫` → `喜欢猫和狗` | 纯追加，不报冲突 |
| 3b | 同上，但插进来的**是否定词** | `怕狗` → `不怕狗` | **极性翻转 → 报冲突** |
| 4 | 两段互相包含 | `上海` → `上海的浦东` | 补了一句，不报冲突 |
| 5 | 差异段合计 ≤ `maxSlotChars`(8) | `上海`/`北京`、`28`/`30`、`喜欢`/`讨厌` | **报冲突** |

第 3b 与第 4 条都是真跑用例逼出来的：

- `怕` 与 `不怕` 在字面上就是「一边为空」（`不` 是插进去的），
  靠「两边都非空」永远判不出来——而那是最典型的一类冲突。
- `上海` 与 `上海的浦东` 两边都非空，靠「两边都非空」会误报冲突，
  而它其实是补充。

**代价**：冲突检测只看字面，`她挺喜欢猫` → `她不喜欢猫` 这种**句式不同**的
极性翻转仍然漏检（覆盖不够）。漏检的后果是多写一条（可回收），
不是错合并（不可回收）。

### 5. 冲突默认**照常写入**，不是「不写」

`conflictPolicy='report-only'` 的语义是「写新条 + 旧条一个字不动 + 把冲突报出来」。
不是「判成冲突就不写」——判重是启发式，「今天吃了面条」与「今天吃了米饭」
在字面上就是同一句式换了一个值。一次误判就丢一条真事实，而这个代价不可逆。

`seal-old` 是可选分支：封存旧条再写新条，等于手册 §2.3「双时态事实」在
**没有 `valid_time` 字段时**的等价动作。默认不开——**错封一条查不出，少写一条能补**。

### 6. 候选排序**槽位命中优先**，不纯按分数

槽位命中比「包含度 0.42」具体得多（同一句式换一个值几乎不可能是巧合）。
截断到 5 条时，先保住强信号那一条，比按分数排更不容易漏掉真冲突。

### 7. 只比活跃记忆，不碰沉底与封存

`listFacts({ state: 'active' })`。把新写入并进一条已沉底的记忆，等于**给一条
已经退出主动位的记忆续命**——而这个续命动作没有任何人批准过。

### 8. 正文过短不判重

「好的」与「好的呀」的包含度是 1.0。合并它们等于丢语气，而语气是产品的一半。
故 `minCompareChars`（默认 6 字）以下直接新建。

## 已知限制

1. **没有语义相似度**。「她很高兴」与「她心情不错」包含度接近 0，会被当两件事。
   语义判断属 O-014 的向量分支（O-122）与 O-011 的模型裁决，不在本插件。
2. **`kind` / `category` 的兜底值（`fact` / `misc`）与 O-010 的缺省重复了一份**。
   传 `undefined` 会让 O-010 记一条 `bad-kind` issue（它把「没写」也当「给错」），
   而 issue 会进 `stats()` 让健康面板报警。**改 O-010 的缺省时，这里要同步改。**
3. **`scan()` 是 O(n²)**。300 条约 4.5 万次比对，同步执行会阻塞调用方几十毫秒。
   调大 `maxScanRows` 前先想清楚它跑在哪个线程上。
4. **冲突检测只看字面**。同义改写（「她很高兴」↔「她心情不错」）、语序调换、
   以及**句式不同**的极性翻转（`她挺喜欢猫` → `她不喜欢猫`）都检不出来。
   反方向也有误报：`今天吃了面条` → `今天吃了米饭` 会被判成「同一槽位换了值」。
   误报的代价可控——`report-only` 下新条照写、旧条不动，只多一行日志。
   漏检的后果是多写一条，可被 `scan()` 与 O-017 审计收拢。
5. **主条选「更早创建」的那条**，正文取较长的。若较早那条本身是错的，
   合并后仍以它为主条 id——订正要靠 `revise()`，不靠合并。
6. **决策日志只留残文**（默认 200 字）。要还原全文得回 O-010 的 `old_text` 或原文层。
7. **`revise()` 的 S×1.3 会随合并次数复利**。同一件事被反复补充，寿命会被抬高。
   这是「被反复提起衰减更慢」的应有表现，但极端情况下（每天补充一次）会明显偏长。

## 多方案分支说明（§12）

本插件涉及一处：**冲突处置**。

| 方案 | 处理 |
|---|---|
| `report-only`（默认） | 写新条 + 旧条不动 + 报冲突。**可逆**：最坏是两条并存，能被 `scan()` 与 O-017 收拢 |
| `seal-old` | 封存旧条 + 写新条。等于「双时态事实」的等价动作，**不可逆**（旧条退出活跃位） |

同一接口（`settle()` 返回同一个 `DedupeOutcome`），差异只是一个配置项，
**不拆文件**：两段逻辑各 3 行，拆成两个文件反而让「默认是哪条」更难看清。
默认选 `report-only`（§12.2「默认最稳」）。

判重阈值**不设分支**：包含度 0.4 是裁决⑥ 定死的口径，多一个开关就多一个
「到底哪个在生效」的问题。

## 隔离五问（§16.4）

1. **关掉我，谁受影响？** 只有我自己。写入会退化成「每条都新建」，记忆变多但不丢；
   旧记忆读写完全不受影响（归 O-010）。
2. **我的状态存在哪？** 计数器**只在内存**；决策日志落 `memory_dedupe_log` 表
   （走 O-006 / O-007 的端口，路径由 O-002 决定）。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.memory-dedupe`；
   `stats()` 给 `available` / `reason` / `logging` / `logRows` / `counters` / `lastError`。
4. **我依赖谁？缺席时我怎么降级？** 见「边界」表：硬依赖只降 `available`，不抛不阻断；
   存储缺席只降日志，判重照常。
5. **我和同域的谁共享了可变状态？** 没有。O-010 只经服务键调用、每次现取（晚装载能自愈）；
   日志表是本插件私有的，O-010 不认识它。
