# ondra-cocreate · 共创流程

> O-117 · L9 扩展池 ·〔研〕自研 · 服务键 `ondra-cocreate` · 档位〔薄〕
>
> 两个人一起做出点什么时的分工与轮次：谁提、谁改、什么时候收束成稿。
> **只给流程约束，不生成任何内容。**

## 1. 一句话定位

回答一个问题：**「两个人一起做点什么时，谁提、谁改、什么时候停？」**

四拍固定序，一个字的内容都不给：

| # | 拍 | 该谁开口 | 要解决什么 |
|---|---|---|---|
| 1 | `brief` 立题 | 提出方 `author` | 说清做出什么、给谁用、什么样算成 |
| 2 | `make` 出稿 | 动手方 `maker` | 交第 1 版（最小可用），之后每版只在上一版上改 |
| 3 | `review` 意见 | 提出方 `author` | 只指一处最该改的，说清改成什么样算改到 |
| 4 | `close` 收束 | 提出方 `author` | 原话问「这版算定稿吗」，问完就停 |

三条落地规则，写进实现而不是写进提示词：

- **角色由状态机轮换。** `handoff()` 收不到「这轮谁来改」，所以「同一个人既提又改」
  在结构上不可能发生，不需要靠提醒。同一个人既提又改，共创就退化成独白。
- **版数是硬的。** 上限按版数算而不按发言次数算：发言谁都能刷（问一句答一句就翻一轮），
  版数只在**真的交出一版**时才加一。撞上限后阶段落到 `closing`——只许 `close()`。
- **定稿不归流程。** `final` 在类型上就是字面量 `false`。收束拍只逼调用方问出那句话，
  答案不记录、不推断、不默认。

## 2. 服务键与契约方法表

服务键 **`ondra-cocreate`**（连字符，全仓唯一归属；`ondra:cocreate` 会被模型侧直接拒绝）。

| 方法 | 语义 | 是否推进水位 | 失败时抛 |
|---|---|---|---|
| `open(goal)` | 立题。重复调用等于换题，版数与账目清零 | 是（新会话） | `disabled` / `bad-request` |
| `next()` | 当前这一拍。**可随便轮询** | 否 | — |
| `handoff(note, expectedEdition)` | 兑现当前这一拍 | 是 | `disabled` / `bad-request` / `no-session` / `already-done` / `stale-version` / `round-cap` |
| `close()` | 收束，返回 `askFinal: true` 的一拍。**幂等** | 是（进入 `closed`） | `disabled` / `no-session` |
| `snapshot()` | 进度快照 | 否 | — |
| `stats()` | 累计统计（只在内存） | 否 | — |

```ts
interface CocreateService {
  readonly available: boolean
  readonly reason?: CocreateErrorCode
  open(goal: string): CocreateRound
  next(): CocreateRound
  handoff(note: string, expectedEdition: number): CocreateRound
  close(): CocreateRound
  snapshot(): CocreateSnapshot
  stats(): CocreateStats
}
```

**版号语义**：`expectedEdition` 是「我这一版基于第几版」。
初稿基于第 0 版，改稿基于第 1 版……对不上直接抛 `stale-version`，
错误详情里带「调用方以为的 / 实际」两个数字。两个人同时改的时候，后到的那个当场报错，
而不是把别人的改动悄悄盖掉——这与 O-107 的 `advance(expected)` 是同一条道理。

**阶段（`snapshot().phase`）**：`idle` → `brief` → `make` ⇄ `review` → `closing` → `closed`。
`closing` 不是一拍，是「版数用尽、只许收束」这个状态；`closed` 之后 `next()` 返回空拍，
`handoff()` 抛 `already-done`，`close()` 幂等返回同一拍。

**水位与账目分开记**：`edition` 是水位（已交出几版，决定何时必须收束），
`rounds` 是账目（真交接了几次）。一轮意见交接后 `rounds` 加一而 `edition` 不动——
合成一个数字就会得出「意见也算一版」，那等于允许两个人靠互相点评把版数耗完。

**只校验、不留存**：`goal` 与 `note` 校验非空与字数上限后即丢，只把字符数记进快照
（`goalChars`）。本插件是**闸**，不是账本。

## 3. 明确不负责

| 不负责 | 归谁 |
|---|---|
| 生成任何内容：初稿、示例段落、措辞 | 对话链 O-033（本插件只给约束） |
| 说话的口吻、人称、句长 | 人格 O-020 / 表达 O-047 |
| 保存作品正文、版本历史、改动差异 | 调用方 + O-010 `ondra-memory-core` |
| 记住「上次聊到哪一版」 | 调用方（本插件不落盘，见 §6.1） |
| 要不要开口、什么时候说、发到哪个通道 | O-042 `ondra-proactive-gate` 与通道适配器 |
| 人设边界的具体条文 | O-021 `ondra-persona-core`（本插件只数条数，不读原文） |
| 渲染、面板、Toast、任何界面 | 应用外壳 `desktop/`（L8 界面插件已整批下线） |
| 多人协作（三方以上、并行分支） | 不做（见 §6.3） |

## 4. 技术来源

**档位〔薄〕**：本插件不引入任何外部算法，四拍约束表与轮次状态机为自研；
「薄」的依据是——全部代码只有一张约束表（`briefs.ts`，纯数据）与一个六状态转移
（`rounds.ts`，纯函数），没有 IO、没有定时器、没有第三方依赖，通读一遍即可复核。

| 能力 | 参考项目 | 仓库地址 | 许可证 | 借鉴了什么 | 本项目如何实现 | 是否引入代码 |
|---|---|---|---|---|---|---|
| 轮次推进与「到点收束」 | 无（生态审计：GitHub 上没有「双人共创轮次」的可移植实现，相关材料全是写作方法散文与协作规范，无可复用状态机） | — | — | 只有一条设计原则：**上限要按产物算，不按发言算** | `rounds.ts` 六状态转移 + `maxEditions` 硬上限 + `closing` 阶段 | 否 |
| 版本号校验（并发改稿） | 本项目 O-107 `ondra-first-meet` 的 `advance(expected)` | 仓库内 | AGPL-3.0（同仓） | **水位校验的手法**：调用方报出自己以为的位置，不一致就当场拒绝 | `handoff(note, expectedEdition)` 同手法实现，独立代码 | 否 |
| 只给约束不给内容 | 本项目 O-108 `ondra-absence` 的「课表」口径 | 仓库内 | AGPL-3.0（同仓） | 「每拍给目的 + 禁令 + 上限，不给一句台词」的表达纪律 | `briefs.ts` 四拍表独立实现，零共享 | 否 |
| 闸与账本分离 | 本项目 O-105 `ondra-digital-health` 的 `pulse()` / `advise()` 分权 | 仓库内 | AGPL-3.0（同仓） | **写口只有一个**：读接口永不推进 | `next()` / `snapshot()` 只读，只有 `handoff()` / `close()` 写 | 否 |

## 5. 配置项

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `enable` | boolean | `true` | 总开关。关掉后服务仍注册，`open()` / `handoff()` / `close()` 抛 `disabled`，`next()` / `snapshot()` 照常可读 |
| `max-editions` | number（1–6） | `3` | 版数硬上限。默认 3 版＝初稿 + 两次修改；到点只能收束，之后 `handoff()` 抛 `round-cap` |
| `note-max-chars` | number（1–500） | `120` | 交接备注字数上限。备注只校验不留存；上限的意义是逼一句话说清，而不是写一段总结 |

常量（**不是配置**）：立题上限 `GOAL_MAX_CHARS = 200`。做成配置，第一个动作就是把上限调到 2000，
于是「立题」变成一份需求文档——而需求文档没有验收标准也一样能写很长。

刻意没有的：角色指派（角色由状态机轮换）、关闭收束询问（关掉就等于自动定稿）、
作品字数上限（字数不是硬的，版数才是）。

## 多方案分支（master-plan §12）

轮次模型只有一套，不做「自由共创 / 严格分工」双轨：

- 「改必须基于上一版」是本插件的骨架，不是可选项。做成两种模式等于承认「另起一稿」也算共创，而那正是共创退化成各写一半的起点。
- 收束条件（轮次上限 + 定稿确认）只有一套数值来源：`src/settings.ts`。不提供「按项目类型切换阈值」的分支表。
- 与 O-033 的分工是硬边界而非分支：内容生成归对话链，本插件只出流程约束。两者不是「两种模式」，是两件事。

## 6. 已知限制

1. **状态不落盘。** 进程重启后轮次清零，硬上限只在单次会话内有效。
   这是**刻意**的：落盘会得到一种更坏的局面——下一个进程读到「第 3 版」，
   却不知道前 3 版做过什么，然后对着一个自己没见过的稿子收束。
   代价写在明处：跨进程续做要由调用方自己重新 `open()`。
2. **只支持两方。** `author` / `maker` 是两个角色，不是两个可扩展的席位。
   三方以上（谁都能提、谁都能改）会让「改基于上一版」失去唯一指向——本插件拒绝猜测。
3. **不记「谁是谁」。** 角色是枚举，不含人名或 `personId`。按人分档会复制 O-028 的按人维度，
   本轮不做；调用方要区分人，请在 `open()` 之前自己路由。
4. **`close()` 之后不能再开新的一版。** 「定稿了但想再改一版」要重新 `open()`，
   于是版号从 1 重来。这是有意的：定稿之后再改，本来就不是同一件作品。
5. **备注内容不留存，所以没有审计日志。** 想知道「第 2 版改了什么」，只能问调用方。
   本条与 O-103 的遗忘权是同一条取舍的另一面。
6. **`close()` 只保证「必须问」，不保证「问到了」。** 答案是否真的被问出口、对方怎么答，
   都在对话链里，本插件看不见——它只在 `askFinal` 上把这件事标成必做。

## 7. 隔离五问（master-plan §16.4）

1. **关掉我，谁受影响？** 只有我自己。没人被拦着不许共创，只是没有轮次约束；
   对话照常，人格照常，记忆照常。
2. **我的状态存在哪？** **不落盘。** 全部状态在内存（几个计数与时刻），
   进程结束即消失。本插件不写任何文件，也不读任何文件。
3. **我崩了怎么知道是我崩了？** 日志命名空间 `ondra.cocreate`（经 O-001 拼，
   缺席时退回同一串字面量），`stats().lastIssue` 留一行中文原因，
   `stats().rejected` / `capHits` 告诉我「硬上限到底拦过人没有」。
4. **我依赖谁？缺席怎么降级？** 四项全软依赖：

   | 缺什么 | 退回什么 | 怎么看出来 |
   |---|---|---|
   | `ondra-persona-core` | 边界条数记 `null`（**不拿 0 顶替**：0 会被读成「人设没有边界」），出稿 / 收束拍的禁令换成「先核对边界」那一句 | 一行 `warn` + `mustNot` 措辞不同 |
   | `ondra-clock` | 系统时间（时刻只用于展示与排序） | 无感 |
   | `ondra-config-schema` | 插件实例配置 + 本地 `completeConfig` | 一行 `warn` |
   | `ondra-identity` | 日志命名空间退回 `ondra.cocreate` | 无感 |

   每个 `ctx.get(...)` 之后都判 `undefined`，绝不直接调用；`persona.boundaries()` 抛错也当取不到。
5. **我和同域的谁共享可变状态？** 没有。O-107（初见）、O-108（空窗期）与本包结构同形但**零共享**：
   不 import、不共用文件、不共用键、不共用存档。与 O-021 只**读**边界条数，从不写。
