# ondra-recall-eval

> 手册 §12.4 原话：「20–40 条真实问法评估集（含换说法）先行：recall@1 / recall@3 / MRR /
> 端到端成功率；改一次跑一次；报告落盘。**没有评估集，所有参数调整都是玄学。**」
>
> 本插件就是那台秤。它**只测量，不调参**——调参是人看了报告之后做的决定。

## 职责

1. **跑题集算指标**：读 `user/eval/<题集名>.set.json`，逐题调 `ondra-memory-recall` 的
   `search()`，输出 `recall@k` / `hit@k` / `MRR` / `avoidRate`（编造题分心率）。
2. **真值按正文指纹落地**：题集写 `expect: ["她说的那句原文片段"]`，换库重建也不会全失效。
3. **报告落盘**：`user/eval/<题集名>-<13 位时间戳>.json` + `.md`，保留最近 `keepReports` 份。
4. **可比性判断**：`compare()` 先比**参数快照**与**库容**，再说指标 Δ。
5. **生成待填模板**：`seed()` 从库里抽若干条记忆，产出**只有真值、没有问法**的模板。

## 明确不负责

| 不做的事 | 为什么 |
|---|---|
| **改任何排序参数** | 它是秤不是手。自动调参会把「玄学」包装成「科学」，而且没人能复核它为什么把 `bm25Half` 从 3.0 改成 2.4 |
| **替你写问法** | 见「关键取舍 5」：自动问法 = 把正文当查询，`recall@1` 接近 100%，那是自欺 |
| **算端到端成功率** | 手册把它和 recall/MRR 并列，但它要跑完整对话链路（O-033 / O-039），测的不是召回。留给链路联调 |
| **建索引 / 存记忆 / 改记忆** | 全部归 O-010 / O-014。本插件对库只有一次 `listFacts` 的只读扫描 |
| **装定时器** | 「改一次跑一次」是人的动作。装定时器会每小时白烧一遍全库扫描，且没人会看那些报告 |

## 关键取舍（每条都有代价，写在这里防后人踩回去）

### 1. 真值按**正文指纹**落地，不按 id（本轮最重要的一条）

题集写 `expectIds: ["mem-001"]` 很快很准，但库一重建、一搬迁、一导入导出，**全部题目一起失效**，
报告显示 `recall` 从 0.72 掉到 0.00，而代码一个字都没改。这是本项目最怕的那种「看起来是性能退化」。

所以默认按正文指纹解析：先精确相等，再退到包含，且要求 ≥ `minFingerprintChars`（4 字）。

**代价**：指纹要手写、要够长；4 字以下的短记忆（「猫粮」）做不出可用指纹。

### 1.1 子串匹配会误命中，所以「怎么匹配上的」必须进报告

`includes` 匹配有两个经典陷阱：`28` 会命中 `1280`，`喜欢猫` 会命中 `不喜欢猫`。
误命中**不报错**，只会让 `recall` 悄悄变高——而「评估数字虚高」比「数字难看」糟得多。

所以匹配方式单独成一个字段（`MatchKind`：`id` / `exact` / `partial` / `none`），
报告逐题明细里有一列「匹配」，`partial` 标成 `片段 ⚠`，提示里还会统计有多少道走了片段匹配。

**代价**：多一列、多一个字段、多一段提示。收益是「数字偏高时能看出偏高在哪」。
真正消掉它要靠把指纹写长（≥ 8 字），本插件不替用户决定 `minFingerprintChars` 调到多少。

### 2. 不可判的题**剔除**，不记 0 分

`missing`（库里找不到）与 `ambiguous`（指纹命中多条）都从分母剔除，并在 `skipped` 里逐条列原因。

**代价**：报告会出现「30 题，计分 24 题」。看起来不整齐，但比把一次库重建记成「召回暴跌 60%」诚实。
一条反直觉的推论：**被剔除的题不是召回失败**。报告里这一节的标题就是这句话。

### 3. MRR 用「无命中计 0 且进分母」的 trec_eval 口径

剔除失败题的 MRR 只统计「答对的题答得多靠前」，天然偏高。`reciprocalRank` 的类型是 `number`
（不是 `number | null`），就是为了让「没命中」必须落成 0、不能落成「跳过」。

**代价**：MRR 会比「业内一些博客里报的数」低。这是对的。

### 4. `rrf` 模式下编造题**不能**设分数阈值

`rrf` 的 `score` 是 `1/(k+rank)`，只表达「排第几」，不表达「有多像」。
给它设 0.05 的置信阈值就是给一个没有量纲的数编了一个意义。
故 `fabricatedJudge` 在 `rrf` 下被强制成 `no-hit`，报告里明写「fabricatedScoreFloor 不生效」。

**代价**：`rrf` 模式下测不出「命中了一条、但证据极弱」这种情形。要测就得切 `weighted`。

### 5. `seed()` **不生成问法**，只生成待填模板

自动问法最省事的做法是把记忆正文原样当 `query`——那样查询与答案是同一串字，`recall@1` 会接近 100%。
**那不是评估，是自欺**，而且比没有评估集更糟：它会让人以为「召回很好，不用调」。

所以 `seed()` 产出的是「真值已填、问法待写」的模板，问法带 `【待改写】` 前缀。
只要还有一条带着这个前缀，报告基线就是 `template-unfilled`，**数字不能用来调参**。

**代价**：`seed()` 之后必须人工写 30 条问法。这半小时省不掉。

### 6. 同一轮所有题共用一个时间戳

新鲜度因子是 `0.5^(Δt/S)`。逐题取 `Date.now()` 会让第 1 题与第 30 题差几十毫秒——
单看无所谓，但两次跑若题序相同，差会累积，于是「同一份代码跑两遍得到两个数」。

**代价**：报告里的 `at` 是全轮快照时间，不是每题真实调用时间。这对指标是正确的，对性能剖析不够。

### 7. 报告带**参数快照**，`compare()` 先说「是不是同一把尺子」

`EngineSnapshot` 只从召回结果里取真有的东西（`fuse` / `weights` / `normalizedBy` / `channels`），
`rrfK`、`bm25K1`、`bm25B` 拿不到就写 `null` 显示 `—`——**不 import O-014 源码去读人家的配置**（§18.5）。

`compare()` 先比参数快照与库容，再出 Δ。参数不同就明说「差异可以归因到参数」；
库容不同就补一句「差异也可能只是库里多了几条记忆」。

**代价**：`rrfK` 一栏永远是 `—`（召回结果里没有这个字段）。宁可空着，不猜。

### 8. 只测量，不调参

本插件没有 `tune()`、没有 `autoAdjust()`、没有「建议把 X 改成 Y」。
它给数字，判断归人（手册 §12.4 的「改一次跑一次」本身就是一个人工回路）。

### 9. 不注册定时器

见「明确不负责」最后一行。

### 10. 报告脱敏：只写 id，不写正文

报告会落到用户目录、可能被用户发给别人看。所以：

- **记忆正文一个字都不进报告**，只有 id；
- 问法按 `queryMaxChars` 截断（`redactQueries=false` 可整体关掉）。

**代价**：报告里看到 `mem-0042` 排第 12 位，要回库里查才知道是哪条。这是刻意的。

### 11. 修剪只删自己命名规则内的文件，且只在新报告写成功之后

正则完整匹配 `<题集名>-<13 位时间戳>.json|.md`，逐条再 `isInside()` 复核。
题集文件（`<题集名>.set.json`，少时间戳）、别的题集的报告、用户自己的笔记，一条都不匹配。

**代价**：`keepReports` 设小了会丢历史。它默认 20，够用。

## 边界

- **对 O-014**：只调 `search()`，只读返回值。不建索引、不改权重、不写 `lastHitAt`。
  已核对 O-014 的 `search()` 是只读实现（没有 `reinforce` / 没有 `update`），**跑评估不会污染真实记忆**。
- **对 O-010**：只调 `listFacts({limit, offset})`，一次分页扫描，只读 `id` 与 `text`。
- **对 O-002**：只调 `ensure('user','eval')` / `fileIn(...)` / `exists` / `isInside`。
  本插件任何地方都不出现绝对路径拼装。
- **对 O-005**：只 `register` 一个段、只 `resolve` 一次。
- **对文件系统**：只写 `<题集名>.set.json` 与报告两份（0600）；只删自己命名规则内的旧报告。

## 已知限制

1. **`rrfK` / `bm25K1` / `bm25B` 在报告里恒为 `—`**。召回结果没有回传这三个字段，
   而本插件不 import 它的源码、也不读它的配置文件。要显示它们，得给 `RecallResult`
   补三个字段（那是 O-014 的改动，走 §15.7 登记，不偷改）。
2. **`fabricatedScoreFloor` 在 `rrf` 模式下不生效**。见「关键取舍 4」。
3. **20 题的 `recall@5` 置信区间极宽**。20 题跑出 0.85，二项分布下 95% 区间约 [0.62, 0.97]——
   手册 §2.3 的糯糯标准是「`recall@5>0.80`、100–200 条」，样本量差一个量级。
   **拿 20 题去对标 0.80 是不严谨的**，见「待裁决 3」。
4. **`seed()` 之后必须人工写问法**。这是设计，不是缺陷（见「关键取舍 5」）。
5. **不做端到端成功率**。见「明确不负责」。
6. **中文指纹按「剥标点 + 小写」归一化，不做同义词归并**。「猫」与「猫猫」是两条不同指纹。
   这是刻意的：归并会让 `ambiguous` 变多，而 `ambiguous` 是剔除。
7. **评估集不支持嵌套分组 / 权重**。每题等权。加权 MRR 这类需求等真出现再说。
8. **一次 `run()` 会全量拉一遍记忆正文**（只为按指纹找 id）。库里 1 万条时约 1000 万字符，
   一次性、不进缓存。若这点开销都受不了，说明该给 O-010 加 `findByText()`——那属于契约缺口，
   已登记，本插件不硬做。
9. **片段匹配（`partial`）仍可能认错**。只做了「标出来」，没做「自动纠正」：
   `28` / `1280`、`喜欢猫` / `不喜欢猫` 这类子串关系，靠字符判不出语义。
   报告里出现 `片段 ⚠` 就说明该把指纹写长，或改用 `expectIds`。
10. **`snapshotOf` 只取召回结果里有的字段**，故 `rrfK` / `bm25K1` / `bm25B` 恒为 `—`。
    这是刻意的「宁空不猜」，别为了让报告好看去 import O-014 的源码读配置。

## 多方案分支说明（§12）

| 能力 | 方案 | 默认 | 处理方式 | 为什么不拆文件 |
|---|---|---|---|---|
| `recall@k` 的口径 | ①命中真值数 ÷ 真值总数 ②至少命中一条即 1 | **两个都算，分别出表**（`recall` 与 `hitRate`） | 融：单真值题上两者相等，多真值题上回答不同问题，并列比拆分支更省事 | 两者用同一份 `hits`，拆文件会重复一遍遍历 |

## 隔离五问（§16.4）

1. **关掉我，谁受影响？**
   只有你自己。召回、记忆、对话链一律不知道本插件存在（没人 `ctx.get('ondra-recall-eval')` 之外地依赖它）。
   唯一影响是：**从此没有客观依据判断参数改动的好坏**（回到手册说的「玄学」）。
2. **我的状态存在哪？**
   `user/eval/` 下两类文件：`<题集名>.set.json`（用户手写）与 `<题集名>-<时间戳>.json|.md`（报告，0600）。
   进程内只留计数器（`runs` / `lastBaseline` / `lastRecall1`），不落盘。
3. **我崩了，界面怎么知道是我崩了？**
   日志命名空间 `ondra.recall-eval`（有 identity 时 `identity.loggerName('recall-eval')`）。
   `stats()` 回 `available` / `reason` / `canWrite` / `canResolveText` / `lastError`，
   `ondra-startup-check` 读一次就能说出「装了但召回不可用」。
4. **我依赖谁？缺席时我怎么降级？**
   见「服务键」表：召回缺席 → `available=false` + 原因码；内核缺席 → 只认 `expectIds`；
   路径缺席 → 报告只在内存；配置真源缺席 → 退回插件实例配置；身份缺席 → 用固定命名空间。
   四处都是 `if (x === undefined)` 后安静降级，**没有一处直接调用**。
5. **我和同域的谁共享了可变状态？**
   **没有。** 对 O-014 只调 `search()`、对 O-010 只调 `listFacts()`，两者都是只读。
   本插件不持有它们的引用做缓存，不共享连接、不共享定时器（本插件一个定时器都没有）。
