# ondra-channel-health

> O-057 · 通道公共层 · 档位〔研〕 · 服务键 `ondra-channel-health`

每个通道一个独立探针。它只回答一件事：**这个通道最后一次有动静是几时几分。**

---

## 一、职责

1. **取证**：接收适配器推来的六类证据（连上 / 断开 / 心跳 / 收 / 发 / 出错），带时刻与错误码。
2. **判定**：把证据折成五态（`ok / degraded / stale / down / unknown`）+ 一个原因码（八值），每个码对应一种排查动作。
3. **隔离**：一通道一份记录、一份状态，互不串；某个通道的数据坏了不影响其他通道。
4. **跨重启**：把「最后活动时刻 + 计数」落盘（`user/channels/health/<id>.json`，0600），重启后仍能说清上次活到几时。
5. **命名空间约定**：导出 `channelNamespace(id)`，所有适配器把日志写到 `channel.<id>`（手册 §16.2-3）。

## 二、明确不负责

| 不做 | 归谁 |
|---|---|
| 真的去连通道、重连、发消息 | 各适配器（O-058 ~ O-067） |
| 判「现在该不该主动说话」 | `ondra-proactive-gate`（O-042） |
| 判「这条来信该不该回」 | `ondra-router`（O-055） |
| 写日志、轮转日志、按命名空间读日志 | `ondra-log-zh`（O-004）——见「已知限制」第 1 条 |
| 自动重启挂掉的通道 | 进程托管（O-080）。探针只报事实，不动手 |

### 三条刻意的「不做」

1. **不调适配器的任何方法。** 一旦 `adapter.ping()`，探针就和被观测进程同生共死：它崩了、卡了、正在重连，三种情况全部超时，而它们的处置完全不同。
2. **不把「安静」当「死了」。** 夜里没人说话是正常的。只有 `heartbeat` 能证明活着，业务消息不能——所以适配器必须按 `expectMs` 的节奏上报心跳。
3. **不读日志文件。** 直接读文件会把探针绑死在日志的**行格式**上：哪天日志加了字段，探针会静默地把所有通道报成 `unknown`，且毫无线索。

## 三、服务键与方法

```
ondra-channel-health        ← 连字符，不是 ondra:channel-health
```

| 方法 | 说明 |
|---|---|
| `register(id, label?)` | 登记一个「应该被盯」的通道，只影响列举，**不参与判定** |
| `report(event \| events)` | 上报证据，返回采纳条数；非法条目丢弃并计数 |
| `probe(id)` | 读一个通道；没上报过返回 `unknown`，**不抛错** |
| `probeAll()` | 全部通道，按最后活动时间从新到旧 |
| `summary()` | 概况：各状态计数 + 最糟状态 + `logPort` |
| `channels()` | 被盯的通道 id 列表 |
| `forget(id)` | 忘掉一个通道并删记录文件 |
| `attachLogFeed(feed)` | 接一个日志端口（可选增强），返回摘除函数 |
| `flush()` | 立刻落盘 |
| `stats()` | 上报 / 采纳 / 拒绝 / 淘汰 / 恢复 / 落盘统计 |
| `dispose()` | 卸载：停定时器、落盘、清状态 |

### 证据长什么样

```ts
{ channelId: 'qq-official', kind: 'heartbeat', at: 1730000000000 }
{ channelId: 'qq-official', kind: 'error', code: '1200', detail: '平台返回风控' }
```

`kind` 六值闭集：`connected / disconnected / heartbeat / inbound / outbound / error`。

### 判定顺序（不能换）

| 序 | 条件 | 状态 | 原因 |
|---|---|---|---|
| 1 | 一条证据都没有 | `unknown` | `never-seen` |
| 2 | 时间戳在未来 60 秒以上 | `ok` | `clock-skew`（先照活算，但把话说明白） |
| 3 | 最后一条是 `disconnected` | `down` | `closed`（**终态**，直到再来 `connected`） |
| 4 | 距最后证据 > `expectMs × staleFactor` | `stale` | `stale` |
| 5 | 错误窗口内重连 ≥ `reconnectLimit` | `degraded` | `reconnect-loop` |
| 6 | 错误窗口内出过错 | `degraded` | `recent-error` |
| 7 | 其余 | `ok` | `ok` |

第 3 条排在「超期」之前是刻意的：一个明确的「它自己说断了」不能因为时间久了就降级成猜测。

## 四、配置

| 字段 | 默认 | 说明 |
|---|---|---|
| `enable` | `true` | 关掉后服务照常注册，一切报 `disabled` |
| `expectMs` | `60000` | 心跳期望间隔（5000–3600000） |
| `staleFactor` | `3` | `stale` 阈值倍率（1–20） |
| `errorWindowMs` | `300000` | 错误影响窗口（10s–1h） |
| `reconnectLimit` | `3` | 窗口内重连几次算风暴（1–10） |
| `maxChannels` | `64` | 上限（1–512），超了淘汰最久没动静的 |
| `intervals` | `{}` | 按通道覆盖 `expectMs`，如 `{"telegram":120000}` |
| `persist` | `true` | 是否落盘 |
| `flushMs` | `5000` | 落盘节流（1s–60s） |
| `verbose` | `false` | 每次上报打一行日志 |

**期望间隔归用户，不归适配器。** 让适配器在 `report()` 里带 `expectMs` 最省事，但那就把判定权交给了被观测方：一个刚崩过的适配器会把自己伪装成「一直很健康」。没配就取全局默认，不留空洞。

## 五、边界

- **只在 `user/channels/health/` 下写自己的记录**，不碰凭据、不碰别人的日志、不碰数据库。
- **不进提示词、不注册工具**：探针数据是给面板和排障看的，进上下文是纯噪声。
- **不主动重启任何东西**：报事实，不动手。
- **状态只写一份**：判定逻辑全在 `probe.ts`（纯函数），`service.ts` 只管容器与容量，`store.ts` 只管落盘。

## 六、已知限制

1. **日志命名空间读不到（上游缺口）。** 手册 §8.3 / master-plan §16.2-3 要求日志命名空间为 `channel.<id>`，但 O-004 `ondra-log-zh` 的契约只有 `tailHuman(limit)`（读单份中文日志的纯文本尾部，无时间戳、无命名空间维度），**没有按命名空间取条目的接口**。本插件因此不读日志文件、不解析行格式，只留 `attachLogFeed()` 端口；今天没有生产方，`logPort` 恒为 `false`，`summary().logPort` 会如实反映。**建议**：给 O-004 增加 `tailNamespace(namespace, limit): {at,text}[]`，本插件即可零改动接上。
2. **没有生产方就必须靠适配器自觉上报。** 适配器不报心跳，探针只能给 `stale` / `never-seen`——这不是误报，是「确实没有任何活着的新证据」。
3. **只记「最后一条」错误码。** 不做错误历史归档（历史在日志里），因此 `recent-error` 只说「最近出过错 + 码」，不回答「错了多少次」——总次数在 `counts.errors`。
4. **淘汰只按时间。** `maxChannels` 满了淘汰最久没动静的那个；一个刚出错但一小时没动静的通道，也可能被淘汰。记录文件不删，下次上报会重新读入。
5. **不判「卡住」与「进程已退」的区别。** 两者都表现为心跳超期（`stale`）。要区分它们需要进程托管方给出退出事实，那不是本插件的边界。

## 七、技术来源

| 能力 | 参考项目 | 许可证 | 借鉴了什么 | 引入代码 |
|---|---|---|---|---|
| 只读探针、不依赖被观测进程存活 | 手册 §8.3「日志纪律」原话 | — | 「适配器崩了界面不失明」的判据 | 否（本项目自研） |
| 通道隔离六条（独立目录/配置/日志/状态/失败/风险） | 手册 §16.2 | — | 一通道一命名空间、独立实例 | 否 |
| 状态机「先硬后软」的判定顺序 | 本项目 O-055 `decide.ts` 的对拍经验 | 自有 | 判定顺序即优先级，不合并布尔 | 是（自有资产） |
| 心跳式健康检查（不 ping、只读痕迹） | k8s liveness/readiness 的通用实践 | — | 用「最后观测时刻 + 超期阈值」而非同步探活 | 否 |

**档位判定〔研〕**：生态里的健康检查要么是「同步 ping」（本场景会被同生共死问题毁掉），要么绑死在自家日志格式上（本仓日志契约不具备命名空间读取）。这两条都不满足「不依赖被观测进程存活 + 不读文件字节」，故自研；体量约 700 行，仍在 §1.8 的 15 个自研额度内（本项计 1）。

## 八、多方案分支说明

本插件不涉及 master-plan §14.3 的任何多方案项，故无 `provider` 分支。唯一一处「口径选择」是判定顺序（第 3 / 第 4 条的先后），已在上文写明理由：**明确结论优先于推测**。

## 九、隔离自检五问（master-plan §16.4）

1. **关掉我，谁受影响？** 只有面板上的「通道健康」一栏消失。适配器照常收发，router 照常判定，记忆与人格不受影响。
2. **我的状态存在哪？** `user/channels/health/<id>.json`（0600，原子写）；`persist=false` 或没有 `path-layout` 时只在内存。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.channel-health`；面板读 `summary().logPort` 与 `stats().writeFailures`。落盘连续失败 3 次会打一条 `error` 并转仅内存。
4. **我依赖谁？缺席时我怎么降级？** `ondra-path-layout`（缺席→仅内存）、`ondra-clock`（缺席→系统时钟）、`ondra-config-schema`（缺席→本地校验）、`ondra-identity`（缺席→固定日志名）。四个全软，`if (!svc)` 后安静降级并各打一条说明。
5. **我和同域的谁共享了可变状态？** 没有。`ChannelRecord` 只在 `service.ts` 的 `Map` 里，`RecordStore` 只读写自己的目录，`probe.ts` 全是纯函数。
