# ondra-time-capsule · 时间胶囊

> 台账 O-101（第 17 组 · L9 扩展池，B13 批次）｜档位〔研〕自研｜**默认开启**（不被调用时什么都不做）

**一句话：写一封给未来某一天的信，封存期内一个字都读不到，到那天自己拆开。**

---

## 1. 它到底做什么

```
create()               封存期                    到期日
写正文 ──→ 存档里唯一副本 ──→ 视图里 text 恒为 null ──→ due() 提示「可以开了」
                                                        │
                                              open() 人手拆封
                                                        │
                              O-010 addFact() 成功 ──→ 本地正文置空，只剩 factId
                              O-010 addFact() 失败 ──→ 正文一个字没动，可重试
```

三件事，就三件：**写、等、开**。

| 方法 | 做什么 | 关键约束 |
|---|---|---|
| `create(input)` | 封一颗胶囊 | 最短 7 天、最长 3650 天；正文 10 字起、默认 2000 字上限；**不静默截断** |
| `list()` / `due()` | 看清单 | 未开封的 `text` **恒为 `null`** |
| `open(id)` | 拆封 | 未到那天抛 `not-due`；**没有提前开的口子** |
| `drop(id, {confirm:'drop'})` | 删未开封的 | **不可逆**（正文只有这一份），必须给确认令牌 |
| `stats()` | 统计 | 含 `writeFailures`：写记忆失败次数，不为 0 就是有事没办成 |

## 2. 四条硬纪律（每条都能单独否掉一种「更顺手」的做法）

1. **封存期结构性不可读，不是「不显示」。** 全插件只有 `viewOf()` 一处产出视图，`list()` / `due()` / `create()` 全走它，没有第二条路能拿到正文。为什么不做成「先存进记忆库、只是不注入」：记忆库的东西会被 O-014 检索、被 O-036 注入，那「到期才看见」的体验第一天就没了。**模型读得到的秘密不算秘密。**

2. **最短 7 天，且不是配置项。** 依据是 master-plan §9.3 承诺时间词闭集的最远跨度（「下周」≈7 天）。胶囊从 7 天起，与 O-021 待办**时段不重叠**。少于 7 天的一律拒收并说清「这条该写待办」——**悄悄按 7 天算比拒收更糟**，用户会以为它按自己说的时间开。

3. **到那天也不自动开。** 自动开封等于「到期那一刻正文进了上下文」：摘要一生成、检索一命中，用户还没自己看，秘密已经散出去了。开不开封是人的动作。

4. **开启时先写记忆、成功后才抹本地。** 顺序反了，一旦写失败信就凭空消失，日志里只有一行「写记忆失败」。反过来做最坏只是「多留一会儿本地副本」，下次还能重试。

## 3. 服务键与契约

**服务键：`ondra-time-capsule`**（连字符，符合 `^[a-z][a-z0-9_-]{1,63}$`）。全仓仅本插件 provide。

`TimeCapsuleService` 方法集：

| 方法 | 说明 |
|---|---|
| `create(input, at?)` | 封一颗。`openAt` 与 `afterDays` **二选一**，同时给或都不给抛 `bad-input` |
| `list(at?)` | 全部胶囊，未开封按开封日升序排前，已开封排后 |
| `due(at?)` | 今天及更早可开的（`text` 仍为 `null`） |
| `open(id, at?)` | 拆封，返回 `OpenOutcome`（`opened` / `factId` / `hint`） |
| `drop(id, {confirm:'drop'})` | 删一颗，缺令牌抛 `confirmation-required` |
| `stats()` | `counts` / `created` / `openedCount` / `writeFailures` / `storeFailures` |
| `available` / `reason` | 可用性（`disabled`） |

```ts
const capsule = ctx.get('ondra-time-capsule')
if (capsule === undefined) return

// 写
const view = capsule.create({ text: '三个月后的我，还在写代码吗？', afterDays: 90 })
// view.text === null  ← 自己刚写的也读不到，这是故意的

// 到期后
for (const item of capsule.due()) console.log(item.title, item.daysLeft)  // daysLeft 恒为 0

// 人点了「拆开」
const out = capsule.open(view.id)
if (!out.opened) toast(out.hint)        // 记忆服务没起来：信还在，下次再开
else console.log(out.text)              // 正文回来了；同时它已是记忆库里的一条
```

## 4. 明确不负责

| 不负责的事 | 归谁 | 为什么 |
|---|---|---|
| 7 天以内的提醒 | O-021 `ondra-memory-prospective` | 「明天提醒我」已有归属。胶囊也做就成了第四套提醒口径 |
| 到期推送通知 | O-042 ~ O-049 主动域 | 本插件插一脚就变成第二个提醒源，两处都响 |
| 胶囊记成记忆之后的衰减 / 召回 / 删除 | O-010 / O-014 / O-017 | 开封那一刻起它就是普通记忆，寿命与遗忘全归记忆域 |
| 写记忆本身 | O-010 `addFact()` | 本插件只在契约里镜像 `addFact` 一个方法，**不镜像 `revise` / `forget`**——镜像一个写方法，就一定有人从胶囊这边改记忆正文 |
| **渲染、三栏、设计令牌、主题、Toast、日历视图、胶囊卡片** | **应用外壳（`desktop/`）** | L8 界面 14 个插件已整批下线。插件只交结构化数据（`CapsuleView`），怎么画归外壳 |
| 什么时候检查「有没有到期的」 | 应用外壳 / 人 | 本插件**不装定时器**（常驻服务属违规形态） |

## 5. 配置

| 配置键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `enable` | boolean | **`true`** | 总开关。关掉后写操作拒绝、读操作照常（还能看到自己写过什么），已有胶囊不会被删 |
| `max-text-chars` | number | `2000` | 正文默认上限（10–8000）。超长**拒收并说明上限**，不静默截断 |
| `max-capsules` | number | `60` | 同时保留的胶囊上限（1–500）。到上限拒收新胶囊，**不静默挤掉最旧的** |
| `verbose` | boolean | `true` | 降级与上游缺席时打一行日志，只影响日志噪声 |

**刻意没有的配置项**：最短封存天数（做成可配就能把胶囊调成 1 天当待办用，两套机制立刻重叠）、到期自动开封（见 §2 第 3 条）、标题必填（会让人把第一句抄进标题，同一段话存两份）、过推送提醒（归主动域）。

## 6. 降级与缺席（一张表说清）

| 缺席的上游 | 表现 | 影响 |
|---|---|---|
| `ondra-path-layout` | 存档只在内存（`stats().stored === false`） | 重启后**未开封的信会丢**（见 §8 限制 1） |
| `ondra-clock` | 退回本机时区，**自然日定义相同** | 夏令时极端情形可能差一天 |
| `ondra-memory-core` | `create` / `list` / `due` 全正常；`open()` 明确失败 | 返回 `opened: false` + 中文 `hint`，**本地正文一个字没动** |
| `ondra-config-schema` | 退回插件实例配置 | 无感 |
| `ondra-identity` | 日志命名空间退回 `ondra.time-capsule` | 无感 |

> 缺记忆服务时**刻意不抛错也不静默**：返回 `opened:false` 并说清「信仍完好、下次再开」。抛错会让外壳以为胶囊坏了；静默成功则是骗人——正文根本没进记忆库。

## 7. 隔离五问（手册 §16.4）

1. **关掉我，谁受影响？** 只有我自己。默认开启但零副作用——不装定时器、不在 `apply` 里扫盘；关掉后依赖本服务的外壳面板拿不到胶囊，对话链完全不受影响。
2. **我的状态存在哪？** `user/time-capsule.json`（0600，临时文件 + `rename` 原子写）。**开启成功后正文置空**，只剩 `id` / 标题 / 开封日 / 时间戳 / `factId`。统计只在内存，重启归零。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.time-capsule`；`stats().storeFailures` 记存档读写失败、`writeFailures` 记写记忆失败；`open()` 的 `hint` 直接给中文原因。
4. **我依赖谁？缺席时怎么降级？** 路径（软）/ 时钟（软）/ 记忆内核（软）/ 配置（软）。逐项见 §6；初始化任一步失败都不抛。
5. **我和同域的谁共享了可变状态？** **没有**。只调 O-010 的 `addFact()` 一次，之后再不管那条记忆。**不直连任何表**，也不 import 任何 `ondra-*` 源码。

## 8. 已知限制（诚实清单）

1. **路径服务缺席时，未开封的信会丢。** 存档只在内存。这是「单一副本」的代价：把正文同时写进记忆库来「保险」，封存期就从第一天失效了。权衡后选**宁可丢，不可泄**。
2. **存档文件损坏时整份退化为空。** 不是逐条抢救：半条记录会在清单里显示一颗永远开不了也删不掉的胶囊，比没有更糟。损坏时记一条 `storeFailures` 并打 warn。
3. **交付语义是「至多一次」。** 写记忆成功之后、抹本地正文之前若进程被杀，下次重开会再写一条记忆，产生一条重复。代价是「可能多一条」，换来的是「绝不可能少一封」——反向取舍会丢信。
4. **不做全文检索。** 未开封的正文连本插件自己都不过滤，`list()` 只能按标题与日期找。
5. **`open()` 之后正文只经返回值给一次。** 想再看，去记忆库查（它有 `factId`）。本插件不留第二份。
6. **不判定「是不是同一天写的」。** 同一自然日内写两颗、开两颗都允许；胶囊按自然日算，不按小时算。
7. **删掉的胶囊不可恢复。** 没有回收站，`drop()` 不可逆，这是 `confirmation-required` 这道闸存在的原因。
8. **不做「剩余天数」的推送。** `daysLeft` 只有主动看清单时才被算出来。

## 9. 技术来源

| 能力 | 参考项目 | 仓库地址 | 许可证 | 借鉴了什么 | 本项目如何实现 | 是否引入代码 |
|---|---|---|---|---|---|---|
| 定时揭示 / 密封内容 | FutureMe、TimeCapsule 类产品（业界形态） | futureme.org | 服务条款 | 借「写入时封存、到期才可读」的产品语义，以及「到期不等于自动揭示，要人自己去取」这条边界 | 自研 `create()` / `due()` / `open()` 三段 | 否（仅语义参考） |
| 时间戳到期判定 | SQLite `date()` / `strftime()` 与日历三元组换算 | sqlite.org | Public Domain | 借「按日历日比较而不是按毫秒比较」的判据：毫秒比较会让「当天 00:00 后写的、当天开」在写入时就已过期 | 自研 `calendar.ts`（`dayNumber` / `dayKey` / `startOfDay`），与 O-003 同一套自然日定义 | 否（仅思想参考） |
| 原子写（临时文件 + rename） | POSIX `rename(2)` 语义 | pubs.opengroup.org | — | 借「写临时文件再原子替换，避免半截文件」的做法 | `store.ts` 的 `writeArchive()`，0600 权限 | 否 |
| 自然日与时区 | O-003 `ondra-clock` | — | — | **复用服务而非重写机制**：`dayNumber()` / `startOfDay()` 直接调 | `calendarOf()` 优先用时钟，缺席才退回本机 | 否 |
| 记忆写入 | O-010 `ondra-memory-core` | — | — | **复用服务**：开封时 `addFact()` 一条 `episode` / `self` | 只调一次，之后不管 | 否 |

**档位判定（master-plan §3.8）**：生态里有大量「定时提醒 / 密封消息」的通用实现，但它们都假定「到期由服务端推送给你」——而本产品的约束恰恰相反：**不做推送、不做常驻、不做自动揭示**，胶囊只在人打开界面的那一刻被看见。引一个推送型实现进来，第一件事就是要给它一个常驻进程与一个通知通道，两样都违反插件形态。故判定：**机制自研（薄，约 500 行纯逻辑），上游能力全部复用**（时间取 O-003、记忆写 O-010、路径取 O-002）。这是「薄封装」的实质：本插件只贡献「封存期不可读」这一条语义，不贡献任何调度机制。

## 10. 多方案分支（master-plan §12）

按 §14.1 三条判定顺序，**不跳级**：

| 分歧点 | 处理 | 理由 |
|---|---|---|
| 正文存放：单一副本 / 双写记忆库 | **只单一副本，不分支** | 双写等于封存期从第一天失效。留一个「备份到记忆库」的开关，就等于留了一条泄密路径 |
| 到期行为：自动开 / 等人开 | **只等人开，不分支** | 自动揭示的体验诱惑很大（「一打开就在那儿」），但代价是正文提前进上下文。正确 > 顺手 |
| 短期胶囊：拒收 / 自动拉到 7 天 / 允许 1 天 | **只拒收** | 自动拉长会让用户以为按自己说的时间开；允许 1 天则与待办重叠。拒收最诚实 |
| 时长表达：绝对日期 / 相对天数 | **两者都收，融合成一套入参** | `openAt` 与 `afterDays` 各有场景（「2027 年生日」vs「三个月后」），但**同时给就拒收**——同时给说不清按哪个算 |
| 开封失败：抛错 / 返回未开成 | **返回未开成** | 抛错会让外壳以为胶囊坏了并可能触发卸载流程；返回 `opened:false` + 中文 `hint` 才能让人知道「信还在，下次再开」 |

**稳定优先**：存档读失败退空存档而不是抛错（宁可「这次看不到」，不许「整个服务起不来」）；日历调用失败退本机算法（宁可差一天，不许看不了清单）。
