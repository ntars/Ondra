# ondra-multimodal-memory

> O-128 ｜ 手册 §1.5 ｜ P1 ｜ 档位〔薄〕薄封装 ｜ 服务键 `ondra-multimodal-memory`

把「看见的」与「听见的」记成记忆：视觉描述与语音转写按**普通记忆**入库，并记住它来自哪个文件。

---

## 一、职责

1. **入库**：把一份 `MultimodalDraft` 写成一条记忆，走 O-010 `ondra-memory-core` 的 `addFact()`。
2. **带来源**：手册要求「带 `modality` 与 `source_path`」。`memory_fact` 表里没有这两列，所以本包自建一张旁挂边表 `memory_multimodal`，按 `fact_id` 指向那条记忆。
3. **去重**：按内容指纹（`fnv1a64(modality + '\0' + sourcePath + '\0' + text)`）判「这份内容记过没有」。同一张图描述两次，只留一条。
4. **尊重遗忘**：入库前查墓碑。用户要求忘记过的内容，同一份文件再来也不入库。
5. **过证据闸**：入库前调 O-140 `judge()`。视觉描述是模型说的，不给它过闸就等于把猜测记成事实。
6. **条目短、全文留档**：手册 §2.2「条目 ≤200 字」，而三分钟语音的转写有上千字。进检索的是截断后的条目，全文留在边表，`fullText()` 按需取。
7. **视频合成**：按手册「视频→4 帧+音轨」拼成两条记忆——帧的画面描述一条、音轨转写一条。

**一句话边界**：本包只负责「把已经变成文字的东西记下来」，以及「记的时候别忘了它是从哪个文件来的」。

## 三、服务键与调用面

服务键 **`ondra-multimodal-memory`**（连字符，符合手册 §8.4 `^[a-z][a-z0-9_-]{1,63}$`）。全仓唯一归属。

```ts
const mm = ctx.get('ondra-multimodal-memory')
if (!mm) return                       // 软依赖：缺席就安静降级

const result = mm.ingest(draft)       // 同步，永不抛错
if (!result.ok) log.debug('%s: %s', result.reason, result.detail)

const video = await mm.ingestVideo({ path, audioPath })
mm.list({ modality: 'image', limit: 20 })
mm.fullText(result.factId)            // 要看全文时按需取
```

| 成员 | 同步/异步 | 说明 |
|---|---|---|
| `available` / `reason` | 属性 | 开关 + 记忆内核是否在位 |
| `ingest(draft, options?)` | 同步 | 一条入库 |
| `ingestMany(drafts, options?)` | 同步 | 逐条走同一条流水线，**不做批内判重** |
| `ingestVideo(input)` | 异步 | 调 O-126 抽帧、O-127 转写，再各自入库 |
| `get(factId)` | 同步 | 边表一行（不含全文） |
| `fullText(factId)` | 同步 | 留档全文 |
| `list(query?)` | 同步 | 查边表（默认 50 条，硬上限 500） |
| `seen(fingerprint)` | 同步 | 按指纹查 |
| `stats()` | 同步 | 计数、后端标识、最近原因 |
| `dispose()` | 同步 | 幂等；本包无定时器、无子进程 |

**不发工具**。手册给的是三个名词（图片 / 语音 / 视频），不是三个函数签名。凭空定一套参数，就是让模型照一份编出来的说明书调用——出错表现会是「多模态不好用」，而根因是签名不对。真正的调用方是代码。

## 四、配置

默认值的唯一真源是 `src/settings.ts` 的 `FIELD_SPECS`；`cordis.patch.yml` 刻意不写 `config`（抄一份就会漂）。

| `default-subject` | `user` | 工程取值 |
| `default-channel` | `fact`（4 天） | 工程取值，理由见 `settings.ts` 文件头 |
| `image-kind` / `image-category` | `episode` / `event` | 工程取值 |

| `max-text-chars` | `200` | **手册 §2.2「条目 ≤200 字」** |
| `max-title-chars` | `40` | 工程取值（契约里标题就是 ≤40 字） |
| `max-full-chars` | `200000` | 工程取值 |

| `respect-tombstone` | `true` | **手册 §2.4「合并时不许复活」** |
| `use-evidence-gate` | `true` | **手册 §2.2「无出处不入库」** |
| `video-frames` | `4` | **手册 §1.5「视频→4 帧+音轨」** |

**`quiet` 为什么与 O-127 相反**：语音转不出来，用户当场就知道（她没听见回复），再打日志只是噪音；而「这张图没记住」用户当场**不会**知道——她三天后问「我上次发的那个截图」才发现。所以入库失败必须留痕。

## 五、入库流水线（顺序即设计）

```
开关 → 内核在位 → 归一化 → 墓碑 → 去重 → 证据闸 → 截断 → 写记忆 → 写边表
```

五处顺序有理由，改动前请先读 `src/service.ts` 文件头。最关键的一条：

**墓碑必须在去重之前，而且要判两段。** 反过来的话，用户要求忘记的那条记忆还在墓碑里、边表行可能还在，去重会命中并回一句「已经记过了」——用户以为忘了，系统说「我记着」。先问「这段是不是被要求忘记过」，再问「是不是已经有」。

**两段是因为墓碑摘要的口径。** O-010 的 `forget()` 按**落库那一版正文**算摘要（`digest = digestOf(row.text)`），而本包会把正文截到 200 字。所以：

| 段 | 时机 | 判什么 |
|---|---|---|
| 第一段 | 去重之前 | 「这次大概会落库的那一版」＝截断后的全文（再补判一次全文，防用户改过 `max-text-chars`） |
| 第二段 | 写入之前 | 过完证据闸、截完断之后**真正要写进去的那个字符串** |

只判全文会漏掉「被截断过的那条被忘了」：同一张图再发一次，正文不同、摘要不同、墓碑判不中，忘掉的内容就复活了。这是本轮自查找出来的真问题，不是假想。

## 六、边表 `memory_multimodal`

| 列 | 类型 | 说明 |
|---|---|---|
| `fact_id` | TEXT PK | 指向 `memory_fact.id` |
| `modality` | TEXT | `image` / `audio` / `video` |
| `source_path` | TEXT | 原始文件路径（只读、不搬、不删） |
| `fingerprint` | TEXT | 内容指纹（索引，**不唯一**） |
| `title` / `provider` / `model` | TEXT | 标题与产出方 |
| `chars` / `full_chars` / `truncated` | INTEGER | 条目长度、全文长度、是否截断 |
| `frames` / `spans` / `boxes` | TEXT(JSON) | 帧路径、时间戳、检测框 |
| `degraded` | TEXT | 降级说明（逗号分隔） |
| `full_text` | TEXT | 全文留档 |
| `at` / `created_at` | INTEGER | 产出时刻、写入时刻 |

**它为什么不是第二份记忆库**：删掉整张表，任何一条记忆都仍能被检索、被注入、被忘记——只是「它来自哪张图」查不到了。删了不影响主流程、只影响解释力，这就是它不构成双真源的判据。

**为什么不建唯一索引**：`dedupe: false` 是合法配置，那时同一内容**本来就该**记两条；唯一索引会让这个配置写不进去，变成「关不掉的开关」。而且建唯一索引在历史数据有重复时会失败，建表失败会让整张边表不可用——为一个「不该发生」的重复，赔上全部元数据，不划算。去重靠 `ingest()` 的先查后写（同进程、同步，无竞态）。

## 七、契约消费纪律

`MultimodalDraft` 的**真源在 `cordis/ondra-vision/src/types.ts`**（§15.3 契约先行，O-126 是先做方）。本包 `src/types.ts` 是**结构对位镜像**：字段名、类型、语义逐字一致，**不 import**（§15.5）。

本包只按字段名消费，**不另立** `modality` / `sourcePath` / `fingerprint`。

两处本包自己的加工，都写在 `draft.ts` 文件头：

1. **指纹重算**。拿三个字段再哈希一遍，与上游给的比对；不一致就用重算值并记 `fingerprint-mismatch`。理由：去重的语义是「同一份内容只记一次」，而「同一份内容」必须由内容判定，不能由上游声称。重算错的方向只有一个——多记一条看得见的重复；用上游错值的方向是**悄悄吞掉一条记忆**。
2. **证据来源按 `modality` 定**：`audio` → `USER`（用户亲口说的，whisper 只是通道）；`image` / `video` → `TOOL`（那些字是模型说的）。标错会让 O-140 的归功闸要么拒掉用户真说过的话，要么让一张图的猜测替用户作证。手册 §2.2：「归属错误比记不住更伤信任」。

## 八、视频合成

```
vision.frames(path, 4)  → 4 张帧
  ├─ 每帧 vision.describe()  → 画面描述（可关）
  └─ 拼成一条 video 记忆（frames 字段带路径）
asr.transcribe(audioPath) → 一条 audio 记忆（spans 带时间戳）
```

- **不逐帧入库**：4 条几乎一样的记忆会挤爆注入预算，而它们说的是同一件事。
- **音轨单独一条**：转写是「说了什么」，帧是「看到什么」，两件事塞进一条会让 `modality` 说谎。
- **音轨由调用方给**：O-127 只收音频文件，不做「从视频抽音轨」；本包若自己再起一次 ffmpeg，就是在第三个地方重写同一套解码调用（§1.8「能复用却自研 = 违规」）。

## 九、隔离五问（master-plan §16.4）

1. **关掉我，谁受影响？** 只有「多模态内容不入库」。对话、记忆检索、注入、情绪全不受影响。
2. **我的状态存在哪？** 边表 `memory_multimodal`（在 O-006 的库里，随库落盘）；计数与 `lastError` 仅在内存。
3. **我崩了，界面怎么知道是我崩了？** 日志命名空间 `ondra.multimodal-memory`（经 `identity.loggerName('multimodal-memory')`）；`stats().lastError` / `byReason` 可查；服务始终注册，`available=false` 时 `reason` 直接读得到。
4. **我依赖谁？缺席时怎么降级？** 八个消费方全是软依赖：`ondra-memory-core`（缺席 → `no-core`，**不自己存记忆**）、`ondra-store-*`（缺席 → 记忆照写，`indexed:false`）、`ondra-evidence-gate`（缺席 → 记 `no-gate` 降级）、`ondra-vision` / `ondra-asr`（缺席 → 视频合成报 `no-vision` / `no-asr`）、`ondra-config-schema` / `ondra-identity` / `ondra-clock`（缺席 → 本地校验 / 默认日志名 / `Date.now()`）。
5. **我和同域的谁共享了可变状态？** 没有。边表归本包独有；不写 O-010 的表结构，只调它的公开方法。

## 十、多方案分支说明（master-plan §12）

**本包不分支，只有一个实现。** 判定顺序走完一遍：

1. **能融就融？** 三种来源（图 / 语音 / 视频）本来就是同一套流水线，差异只有「正文从哪来」「引文标哪类」「默认 kind/category 是什么」——全部参数化，不需要三个实现。
2. **能兼容就做兼容层？** 唯一的兼容点在这里：若将来 O-010 给 `FactInput` 加上 `meta`，边表可以退化为「只读视图」，`ingest()` 照旧写 `meta`、边表只用来查历史行。**那是兼容层，不是分支**，且不需要改本包的调用方。
3. **都不能才分支？** 没有「两套机制并存」的情形。去重要不要做、闸要不要过、帧要不要描述，都是**参数**，不是分支——把它们做成三个 `if (mode===…)` 正是 §12.2 明令禁止的写法。

**档位判定（〔薄〕薄封装）**：机制全在上游——理解归 O-126、转写归 O-127、存储归 O-010、闸门归 O-140。本包做的是**契约转换与护栏**：指纹重算、墓碑、去重、归属映射、截断策略、失败隔离。手册 §1.8 的自研清单（七阶关系弧 / 阈值漂移 / 语感统计 / 九步过滤 / 节制设计 / 器官 ABI / O-138~O-144）**不含 O-128**，故不按自研计。

## 十二、已知限制

1. **`memory_fact` 没有 `meta` 列，所以多模态元数据在边表。** 后果：O-014 的检索看不到 `modality`——想「只检索图片类记忆」，得先问本包 `list({modality:'image'})` 拿 `fact_id` 集合，再交给检索。这不是缺陷，是不改已 `done` 插件（§16.3）的代价。
2. **边表与记忆可能不在同一个后端。** 本包与 O-010 各自 `ctx.get('ondra-store-sqlite') ?? ctx.get('ondra-store-memory')`；若一边拿到 SQLite、另一边回落到内存，边表行会在重启后指向不存在的记忆。已记 `provider-mismatch` 降级并 warn，但**没有自动修复**——自动修复要跨插件搬数据，那比不一致更危险。
3. **说话人分离不存在。** O-127 明确不做（`diarized` 恒 false），所以音频条目一律用 `default-subject`。**群聊语音必须由调用方显式传 `subject`**，否则会把别人说的话记成用户说的——手册 §2.2 说这比记不住更伤信任。
4. **音轨分离不在本包。** 需要调用方提供 `audioPath`。理由见第八节。
5. **不校验源文件是否还在。** 描述入库后用户删了原图，记忆仍在（这是对的），但 `source_path` 会指向一个不存在的路径。要判断「文件还在不在」是调用方的事。
6. **同一段视频重复入库会重复花帧描述的钱。** 去重要先有正文，正文要先描述——鸡生蛋。指纹在描述之后才算得出来，所以重复视频仍会花掉 4 次模型调用，只是最后不会多记一条。要省这笔钱，调用方应先自己按文件哈希拦一道。
7. **`ocr` 与 `describe` 不区分。** O-126 的两个动作产出的都是 `image` 草稿，本包按同一路径入库。要区分得在 `MultimodalDraft` 上加字段——那要改契约，不在本轮。
8. **`full_text` 不进检索。** 它是留档，不是第二条可检索正文。全文里的词搜不到，只有条目（前 200 字）能搜到。这是「条目短」的必然代价。

## 十三、待裁决

1. **条目上限 200 字对多模态是否偏短？** 手册 §2.2 的 200 字是给「提炼条目」定的；一段语音的转写可能前 200 字还没说到重点。可选：按 `modality` 分档（图片 200 / 语音 500）。
2. **要不要给 O-010 加 `meta` 列？** 加了以后本包的边表可以退化成视图，检索也能按来源筛。但那要改一个已 `done` 的插件并做迁移（O-008 的地盘），需要主人裁决。
3. **`default-channel` 该不该是 `fact`（4 天）？** 现在是「一次性现场，快点淡」。若用户习惯「翻旧图回忆」，应当改成 `gist`。
4. **视频要不要逐帧入库？** 现在是「4 帧一条」。若将来要「按画面检索」，需要每帧一条，代价是注入预算。
5. **`no-gate` 时该不该入库？** 现在是「入库 + 记降级」。另一条路是「没有闸就不许写」，但那会让没装 O-140 的用户一张图都记不住。
